**Goal.** A reviewer judges a change against what the run is for, not only against its brief: it sees the run goal and what the plan leaves out, and when the brief itself is wrong it says so in a `brief` finding that goes to whoever planned the task instead of bouncing the worker. Every plan the orchestrator or a sub-planner submits states what it decided for the user and what is out of scope, and the user reads both at the plan gate. Planners serialise tasks that take the next number from a shared sequence. A re-planned task names the task it replaces, so history and statistics judge the work by the replacement, not as a failure.

**Architecture.** Four small changes along existing paths, each in new files so no file passes 600 lines. (1) The reviewer prompt gains the goal line `worker_head` already writes and an out-of-scope block read from the run's stored plan frame (or, in a design-flow run, from the approved spec's Non-goals). (2) `Finding` gains a `target`; the review gate leaves `brief` findings out of everything that bounces a worker and turns each into a task note of a new kind, `brief`, which reaches the orchestrator through milestone 9's note path (wake plus digest) and the user through the run's attention lines. (3) `edit_plan` with `submit` and `submit_epic` carry two structured lists, `decided` and `out_of_scope`; the engine refuses a submit without them, stores them per round and per epic, and the snapshot, TUI, CLI and report show them. (4) `PlanEdit::AddTask` gains `replaces`; validation, the task model and the history record carry it, and `run stats` leaves replaced tasks out of its rows.

**Tech stack.** Rust 2024 workspace; `serde`/`rmp-serde` wire types; `ratatui`/`crossterm` for the TUI; `fake-agent` for every test.

**Spec.** NA §7 and the decisions U1 and U18 in NA §1.1. Read both, and the research it condenses (decisions below restate every point this brief relies on), before task M9.17.2. NA §7 is a summary; the detail it leaves open is decided below, each ruling marked **(R)** and listed again under "Spec and brief defects".

**Naming.** The code base already says "M9.17" for milestone 9's task 17 (19 places, e.g. `cli/tests/run_e2e_large.rs:1`, `daemon/src/scout/service.rs:122`). This milestone's tasks are always written `M9.17.<k>`, and every comment it adds says "milestone 9.17", never bare "M9.17".

## Design decisions

Numbered and final. If one proves wrong or impossible, stop work on it, record the evidence under "Implementation notes", and continue with the tasks that do not depend on it. A decision marked **(R)** is a ruling on something NA §7 leaves open; each is also listed under "Spec and brief defects".

### The reviewer prompt (NA §7, first bullet)

1. **`Run goal:` is the reviewer prompt's second line**, right after `[anthrex] Review task …`, written by the same function that writes `worker_head`'s: `contract_scope::goal_line(run) -> String` (`format!("Run goal: {}", run.goal)`), which `worker_head` then calls, so the two can never differ. Whatever 9.3's rounds do to `run.goal` applies to both alike.
2. **The reviewer prompt's order after this milestone** (stated whole, because 9.15 and 9.17 both insert into it): `[anthrex] Review task …`; `Run goal: …`; `Base:`; `Head:`; `Test mode:`; the tier lines; the TDD line; the `small` line; `Acceptance criteria:` and its items; the diff and its clamp note; the last check; the weakening signals; the pair note; `Earlier findings to confirm fixed:` (round > 1); the messages; **known pitfalls** (9.15 decision 23); **the risk note** (9.15 decision 30); **the out-of-scope block** (decision 3, this milestone); the requirements block and `JUDGE_LINE` (9.6); a blank line; **the brief, last**. The goal sits with the other short facts at the top, as in `worker_head`; the out-of-scope block sits with the other run-level judging material just before the requirements, and the brief stays last as 9.15 decision 23 keeps it. With no frame and no Non-goals the block adds nothing, so the only change to an existing prompt is the goal line.
3. **The out-of-scope block** (`contract_scope::out_of_scope_block(run, task) -> Option<String>`, pure). Items, in order: the out-of-scope items of the frame of the task's round (`frame_for(run, task.round)`, decision 18), then those of the task's epic's frame (`EpicRecord.frame`, when `task.spec.epic` names one), exact duplicates dropped, each `messages::one_line`d and passed through 9.15's `dossier::break_markers`. Rendered as `OUT_OF_SCOPE_HEAD` and one `- <item>` line each. In a design-flow run whose approved spec has a non-empty `non_goals_section`, the block is `NON_GOALS_HEAD` and that text first, then the frame items (if the orchestrator gave any) under `OUT_OF_SCOPE_HEAD`. The whole block is at most `OUT_OF_SCOPE_MAX = 2048` bytes; a longer one is cut at a char boundary and ends `[cut: <n> bytes]`, as `requirements_block` does (`contract_design.rs:44-53`). `None` when there is nothing.
4. **Non-goals reach reviewers, not workers (R).** NA §7 says reviewers receive the out-of-scope list; the research also proposed adding Non-goals to `requirements_block`, which both workers and reviewers read and which is `None` for a task that covers no requirement. Neither happens: `requirements_block` is unchanged, and the Non-goals ride in decision 3's block, which only `reviewer_prompt` calls, for every task of the design run.
5. **Capturing the Non-goals.** `requirements::non_goals_section(spec) -> String`: the spec's `## Non-goals` section, trimmed and cut to `GOAL_CAP`, as `goal_section` is. `DesignState.non_goals_section: String` (`#[serde(default, skip_serializing_if = "String::is_empty")]`) is set beside `goal_section` at the approved spec's read-back (`design_review.rs:248`), cleared in `unapproved` (`:290-297`), saved in `DesignRound::starting` as `non_goals_before` and restored where `goal_before` is (`design_round.rs:165`).

### `brief` findings (NA §7, first bullet)

6. **`Finding.target: FindingTarget`**, `enum FindingTarget { Code, Brief }` (`snake_case`, `Default = Code`), `#[serde(default, skip_serializing_if = "FindingTarget::is_code")]`, so every finding written today serialises unchanged. The `submit_review` schema's finding gains `"target": one_of(["code", "brief"])` (not required). `parse_finding` reads it (`.target: must be one of code, brief`); a `brief` finding needs no file, line or input (the location rule at `tools.rs:126` applies to `code` findings only). Every `Finding` literal the compiler names gains `target: FindingTarget::Code`.
7. **A `brief` finding never bounces the worker and never blocks.** In `review::submit`: `APPROVE_WITH_BLOCKING` and `blocking` count only `code` findings of severity critical or important; `weakening::check_review` lets only `code` findings answer a signal; `review_changes_message` and `reviewer_prompt`'s "Earlier findings to confirm fixed" list only `code` findings. A `changes` verdict whose only critical or important findings are `brief` therefore goes to the merge queue, exactly as a `changes` verdict with only minor findings does today (`review.rs:333`, M9.17.1 pins it). The findings stay in `ReviewRecord.findings` whole, so the inspector, the report and `task_result` show them. **(R)** NA §7 says "instead of bouncing the worker" and nothing about merging; a brief finding is advice to the planner, who acts with a task, not a hold on this change. A reviewer that thinks the change must not merge files a `code` finding, as today (REVIEWER_CONTRACT rule 7, decision 27).
8. **Each `brief` finding becomes a task note** (`engine/review_brief.rs::record(run, i, round, findings, now)`, called once from `submit` after the record is stored and before the gate decision): a `WorkerNote { kind: TaskNoteKind::Brief, text: "review round <n> (<severity>): <text>" }` through `add_worker_note`, so it gets the run-wide `seq` and reaches the digest's `task_notes`, `task_result`, the snapshot's `task_notes`, the inspector and the report like every note. A note whose text equals one the task already has is not added again (a later round repeating itself). At most `BRIEF_NOTES_PER_TASK = 5` per task; a further one is dropped with the history line `brief finding dropped: 5 already noted`. Each one added logs the history line `brief finding: <first 120 characters>`. **The worker's `task_note` cap (`note_max_per_task`) counts only `Discovery`, `Risk` and `Progress` notes**, so reviewers never use up a worker's allowance, and a worker can never send `brief` (`parse_call`'s kinds are unchanged; M9.17.4 tests it).
9. **The route is milestone 9.9's orchestrator-first rule, applied to a note.** Each added note calls `wake::note(run, "<t>'s reviewer says the brief is wrong: <first 120 characters>")`. While the run has an orchestrator record that is the orchestrator's: it is woken and reads it in `run_status`'s `task_notes` (kind `brief`); a dead or stalled orchestrator gets it when it comes back, and 9.9's `OrchestratorStuck` alert already tells the user. A run with **no orchestrator record** (a plan-file run, the fast path) has nobody to plan with, so the note is the user's: decision 10.
10. **What the user sees.** For every run, `noted_lines` (`snapshot_orch.rs:72`) words a `brief` note `<t> review flagged the brief: <first 80 characters>` (the other kinds keep `<t> noted a <kind>: …`). For a non-terminal run with no orchestrator record, `attention` gains, per task with at least one `brief` note, the sticky line `<t>: the reviewer says the brief is wrong (<n> notes); read them in the task's notes` (`BRIEF_ATTENTION`), so a fourth later note cannot push it out of the three `noted_lines`. `anthrex run status` prints both through its attention lines; the TUI's inspector notes row labels the kind `brief`. No `AlertKey` is added **(R)**: the parent ask named 9.9's route, which is about alerts, but alerts are derived from state and have no dismissal (`app/alerts.rs`), and a brief note is history, not a state that clears.
11. **Counting.** The round is one review round in `GateTally.review_rounds` as any round is; `reviews_rejected`, `GateCounts.review` and the rung ladder move only when the round asked for changes with a `code` finding (they follow `blocking`). History: `severities` counts `code` findings only; `TaskRecord.brief_findings: u32` (`#[serde(default, skip_serializing_if = "is_zero")]`) counts the task's `brief` findings over all rounds. Review tasks and integration reviews (`is_reader_task`) record their `brief` findings as notes the same way; their report flow is unchanged.
12. **Displays.** `finding_line` writes a brief finding `- [<severity>] brief: <text>`; the TUI's `finding_text` writes `brief <severity> — <text>`, and `most_severe` (what the inspector shows as being fixed) skips `brief` findings; the report's `finding_line` (`report_orch.rs:117`) matches `finding_line`.

### The plan frame (NA §7, second bullet)

13. **Two structured lists, not headings in a summary (R).** NA §7 says "every plan summary lists"; `edit_plan`'s `summary` is the end-of-run summary (rule 33) and a submit has no summary of its own, and parsing headings out of free text is what the research warned is fragile. So `edit_plan` and `submit_epic` gain two keys: `decided: [{question, answer}]` (each item a `DecidedItem`, `question` 1–300 characters, `answer` 1–500, at most `DECIDED_MAX = 20` items) — **Decided for you**, every question the goal left open with the answer chosen — and `out_of_scope: [text]` (each 1–300 characters, at most `OUT_OF_SCOPE_ITEMS_MAX = 20`) — **Out of scope**. Displays call them by those two names.
14. **Enforcement is a refusal (R),** before any edit of the call applies (all or nothing, as today). An orchestrator `edit_plan` with `submit: true` whose submit goes 9.5's way (`design_plan.rs:129`: no design flow, or the flow off for this round) is refused with `PLAN_FRAME_MISSING` when the current round has no stored frame and the call lacks either key. A `submit_epic` lacking either key is refused with `EPIC_FRAME_MISSING` (recorded through `record_rejected` as other refusals are). Either key on an `edit_plan` without `submit: true` is refused with `FRAME_NEEDS_SUBMIT`. ### `replaces` (NA §7, fourth bullet)

22. **On the `add_task` edit, not on `PlanTask`.** `PlanEdit::AddTask { task: PlanTask, #[serde(default, skip_serializing_if = "Vec::is_empty")] replaces: Vec<String> }`, with a constructor `PlanEdit::add_task(task)` that every literal the compiler names switches to. Plan files have nothing to replace, and `PlanTask` stays as it is. The MCP `plan_edit` schema gains `"replaces": array(text(16), None, 12)`. Another op carrying `replaces` is refused (serde's `deny_unknown_fields` on the internally tagged enum; M9.17.7 tests it, and the daemon refuses with `replaces: only add_task takes replaces` if serde does not).
23. **Validation** (`run/edits_replaces.rs`, called by `Batch::apply`'s `AddTask` arm after the task is added; errors join the batch's list with rule `replaces`, so one bad id refuses the whole batch):
    - (a) each id names a task of this run: `replaces: no task <id> in this run`;
    - (b) after the earlier edits of the same batch, that task is `cancelled` or `blocked`: `replaces: <id> is <state>; only a cancelled or blocked task can be replaced`;
    - (c) no id twice in one list: `replaces: <id> is named twice`; at most 12 (the schema's bound, checked again);
    - (d) a sub-planner names only tasks of its own epic: `replaces: <id> is not in epic <e>`;
    - (e) no cycle in the replaced-by relation over the run after the batch: `replaces: <a> → <b> → … → <a> is a cycle`. A new task can only replace existing ones, so (e) cannot fire today; it guards a future edit kind and costs one walk.
    Two tasks may replace the same task (a split, decision 25).
24. **Effect.** A `blocked` task named in `replaces` is cancelled in the same batch through `cancel_at` (its dependents become `blocked(dep_cancelled)` as with `cancel_task`; nothing is re-pointed, see Out), with the history line `cancelled: replaced by <new>`; a `cancelled` one gains the history line `replaced by <new>`. The new task stores `Task.replaces: Vec<String>` (`#[serde(default, skip_serializing_if = "Vec::is_empty")]`). The replaced task is never changed otherwise.
25. **`split_task` records it itself:** each child of a split gets `replaces = [<original>]`. A model never sends `replaces` on a split child (`PlanTask` has no such field).
26. **Read side.** `TaskInfo.replaces` (the stored list) and `TaskInfo.replaced_by` (computed on snapshot: the tasks whose `replaces` names this one), both `skip_serializing_if = "Vec::is_empty"`; the inspector shows `replaces   t3` and `replaced by   t9, t10`; the report writes a replaced task's state `cancelled (replaced by t9)`; `task_result` gains `"replaces"`. **History**: `TaskRecord.replaces: Vec<String>` from `Task.replaces` (`#[serde(default, skip_serializing_if = "Vec::is_empty")]`); the replaced task's own record is never rewritten (it was written when it was cancelled, `history.rs:63`). **Statistics**: `aggregate` builds the set of `(run_id, task_id)` named by any record's `replaces` and leaves those records out of the class rows (beside `sessions == 0` and `reported`); `HistoryStats.replaced: u32` (`#[serde(default)]`) counts them; `run stats` and the TUI's stats page print `replaced <n> (judged by their replacements)` when it is above 0. **Refit** reads merged records only (`refit.rs:179,193`), and a replaced task is never merged (rule (b)), so it needs no change (a pinning test proves it). **9.15's lesson credit** counts `cancelled` as nothing (its decision 25), and a replaced task is always cancelled by the time its record is written, so it needs no change either (pinning test). M9.17.1 greps every reader of `TaskOutcome` and `TaskRecord` on the merged `main`; any 9.13–9.16 reader that counts a cancelled or blocked record against something applies the same exclusion, in M9.17.8.

## Risks and gotchas

- **A reviewer can hide a real bug behind `target: brief`**, and the change merges. Rule 7 says a change that must not merge needs a `code` finding; the orchestrator sees every brief note and can add a fix task; the report lists them. If real reviewers misuse it, the follow-up is to hold a task on a critical `brief` finding for the orchestrator; that is a change to decision 7, not a tweak.
- **Models will send empty lists to get past the refusal.** The gate says `none stated` in the attention colour, so the user sees it; the manual check records how often it happens.
- **173 scripted submits** must gain the keys before the refusal lands, or most orchestrator tests fail at once with `PLAN_FRAME_MISSING`. Decision 15's commit comes first in M9.17.5.
- **9.13 rewrites the `edit_plan` description**, 9.15 the reviewer prompt, 9.16 perhaps the orchestrator's first prompt. Interfaces "Contract texts" are written as appends and one substitution so they survive that; M9.17.1 records the texts they apply to.
- **Every reviewer prompt changes by one line** (the goal), so every reviewer-prompt golden changes in M9.17.3; each is listed with that one line, and nothing else in them may change.
- **`noted_lines` shows three notes**; a plan-file run's brief note survives through decision 10's sticky line, an orchestrator run's through the orchestrator.
- **A frame is up to 16 KB**; it is published only at the gate (decision 20). A test that expects it in a running run's snapshot is wrong.
- **`TaskNoteKind::Brief` and `Finding.target` in `run.json`** make it unreadable to an older binary; the `RUN_FORMAT` bump (U1) makes an older one skip it rather than drop fields.
