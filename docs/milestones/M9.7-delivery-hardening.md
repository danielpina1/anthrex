## Goal

In `pr` mode, what anthrex says about a run's PRs matches what happened on the host, and no work is lost without a word:
1. A merged top stage's unfinished fix tasks are cancelled with a reason, and a fix that lands after the merge says it was not delivered.
2. A merge whose head anthrex never viewed is judged by git (`merge-base --is-ancestor`), not reported as undelivered by default.

Four nearby defects are fixed alongside: decided holds that grow the digest without bound, a `run_status` read that can hide a hold approval, an open PR's stage reading `tier 3 ◌`, and a CI bisect that never searches below the head tier 3 passed. So are three small ones: the CI summary's log persisted three times, the CLI's unbounded `git`, and fix tasks that escalate onto uninstalled or just-failed runtimes.

## Design decisions

These are final. One that proves wrong is stopped and written up under "Implementation notes" (AGENTS.md).

### Structure

1. **Files at their limit take call sites only.**
   - `run/delivery/tests.rs` (601) is split first (DH §4.3).
   - `engine/delivery/land.rs` (559) cannot hold §1.1 and §1.2. Task M9.7.2 moves `unpushed` and `missed_merge` (`land.rs:133-195`) move-only into a new `engine/delivery/land_judge.rs`. Every new verdict function lives there (BR-10).
   - `run/delivery/mod.rs` (589) takes one field, `StageDelivery.undecided` (≤ 4 lines). The persistence-tests module is declared from `tests.rs`, not from `mod.rs` (BR-9).
   - New test code goes in new files wherever the host file is over 500 lines. "File sizes" lists each budget.

### A merged stage's fix tasks (DH §1.1)

2. **Cancel on a merged top stage.** In `land::merged` (`land.rs:100`), after `landed` is set: when `(n + 1..=stage_count(run)).find(|&m| sync::live(run, m))` is `None`, every task with `t.stage() == n && t.fixes.is_some() && !t.state.is_finished()` goes through `complete::cancel_task(run, i, &format!("stage {n} PR merged"), now, fx)`. This is the loop `closed` runs at `land.rs:241-246`, with its own reason.
   - `merged` gains `fx: &mut Vec<Effect>`. Its two callers in `landing` (`land.rs:84`, `:86`) pass it.
   - A stage with a live stage above keeps its fix tasks: propagate carries their commits up (DH §1.1).
3. **A deferred cancel that lands.** `cancel_task` defers a task whose `MergeCandidate` is in flight (`engine/complete.rs:40-55`, `cancel_deferred`). When that merge lands, `engine/merge.rs::candidate_done` logs `the cancel of <id> arrived too late: it merged` and calls `merged` (`merge.rs:183-193`). Right after that call, when the run is `pr` mode and stage `n` (`stages::stage_of_branch`, `merge.rs:132`) has `landed == Some(PrState::Merged)`, it calls `land_judge::merged_late(run, n, now)`.
   - *(Task M9.7.1, fact.)* The call is a tail expression today, `return merged(run, i, (before, commit), now, fx);` (`merge.rs:193`; this `merged` is `merge.rs`'s own, not `land::merged`). "Right after" means the `return` is split: call `merged`, then `merged_late`, then return. `engine/delivery/mod.rs` declares its modules private except `land` and `sync` (`pub(super) mod`, `:25`, `:31`), so `merge.rs` reaches `merged_late` only if `land_judge` is declared `pub(super) mod land_judge;` (as `land` is) or `merged_late` is re-exported there.
   - `merged_late` runs `unpushed(run, n, pr, <current stage head>, <merged head>, now)`, so the existing "not delivered" line (or "goes up with stage m") appears.
   - If the stage is undecided (decision 6), `merged_late` decides it as not delivered at once (BR-6).
   - Nothing is dropped silently.

### An undecided delivery (DH §1.2)

4. **Hold the verdict.** In `land::merged`, `head` is the local stage head and `at` the merged head (`land.rs:118-122`). The verdict is:
   - `head == at`, or `pr.confirmed == Some(head)`: delivered, as today (`land.rs:123`).
   - otherwise, when both `head` and `at` are object ids (`host::allow::is_object_id`): **undecided**. `StageDelivery.undecided = Some((head, at))`. Neither `reply::landed`, `unpushed` nor `missed_merge` runs yet (BR-3).
   - otherwise (an empty or malformed head): today's line at once. anthrex never claims a delivery it could not check.
5. **The question rides the base fetch.** `sync::pass` (`sync.rs:141-156`) also emits the base fetch while any stage is undecided and no base fetch is in flight. The oldest undecided stage (lowest `n`) is asked about, one per fetch, as `method_due` (`sync.rs:128-137`) asks for one merge commit's parents:
   ```
   HostOp::Fetch {
     stage: None, branch: <base>, into: base_ref(run), adopt: None, parents_of,
     contains: Some(Contains {
       stage: n,
       branch: remote_branch(run, n),               // anthrex/<run>/stage-<n>
       into: format!("refs/anthrex/{}/remote/stage-{n}", run.id),
       head,                                          // the local stage head
       merged,                                        // the merged head
     }),
   }
   ```
   The `into` ref is the one the adoption fetch already uses (`watch.rs:200-210`), and `allow.rs::fetch_spec` (`:363`) already admits it.
6. **The executor's two optional steps** (task M9.7.6, in `host/gh_git.rs::fetch_ref`, after the base fetch and `parents`; `gh_git.rs:98-105`). They run inside the same host op, so on the git queue:
   1. **Unless** the counted parents are ≥ 2 (a merge-commit merge, whose `merge_commit^2` the base fetch brought), fetch `+refs/heads/<branch>:<into>` with the same flags as the base fetch (`gh_git.rs:58-75`). A missing branch, or any failure, makes the answer `None`, never the op's error.
   2. `git merge-base --is-ancestor <head> <merged>` (allowed at `host/allow.rs:130`, used at `gh_git.rs:148-159`): exit 0 is `Some(true)`; a non-zero exit with empty stderr is `Some(false)`; anything else is `None`.

   The answer is `FetchOutcome::Fetched { contains }`. A request without `contains` answers `contains: None` and runs neither step.
7. **The verdict** (`land_judge::decided`, called from `sync::fetched`, `sync.rs:165`):
   - It applies only when `StageDelivery.undecided` of `contains.stage` still equals `(contains.head, contains.merged)`. Otherwise it is stale and ignored, and the next pass asks again.
   - `undecided` is cleared. Then `delivered = answer == Some(true)`, and the held judgment runs as `land::merged` would have run it: `reply::landed(run, n, &at, delivered)`, `unpushed` when not delivered, and `missed_merge` when replies were dropped.
   - `Some(true)`: delivered, no line. `Some(false)` and `None`: today's line, now true or unverified.
   - **A base fetch that answers without a `contains` answer** (`FetchOutcome::Missing`, or `Fetched` with `contains: None`) decides as `None`. **A failed op** keeps the stage undecided, and it is asked again after `base_fetch_retry_at`, as a failed base fetch is today (`sync.rs:158-161`). There is no hot loop (BR-4).
   - **Amended by the controller's ruling R1** (see BR-3/BR-4): the failed op no longer keeps the stage undecided forever. The third failed check in a row decides as `None`, with its own log line.
8. **What waits for the verdict.**
   - `land::settled` (`land.rs:541-544`) is false while any stage is undecided, so the run does not complete on an unjudged merge.
   - `land::delete` (`land.rs:431`) does not delete the merged branch of an undecided stage, so anthrex never removes what it still has to read (BR-16).
   - `land::reopened` (`land.rs:262`) clears `undecided`.
9. **A restart while undecided** needs nothing new. The lost host op is dropped (`restore_lost.rs`, the `_ => {}` arm), `undecided` is in `run.json`, and the next `sync::pass` emits the fetch again (DH §1.2).

### The orchestrator and the stage node (DH §2)

10. **Decided holds go first** (DH §2.1). `orch/digest_trim.rs::trim` (`:35`) gains a new first step, before `delivery::trim` (`:39`):
    - it drops `gate.holds` entries whose hold is `Approved`, `Rejected` or `Moot`, oldest `decided_at` first (ties: the order in `run.orch.gate_holds`), until the digest fits;
    - it never drops `Drafting` or `Awaiting`;
    - it counts each drop in a top-level `omitted_holds` key, written only when at least one hold was dropped (BR-1). While the digest fits, nothing changes and the key is absent;
    - the order comes from `run.orch.gate_holds`, since the digest's hold entries (`digest.rs:189-201`) carry no `decided_at`.
11. **`DigestRead` carries the clone's time** (DH §2.2).
    - `OrchEvent::DigestRead` (`engine/orch_event.rs:72-76`) gains `at: u64`. `driver/orch.rs::run_status` (`:424`) sends `at: now`, the `now` it built the digest with (`:430`).
    - `engine/orch.rs:138-143` passes it on. `wake::digest_read(run, notes_seq, at)` (`engine/wake.rs:95-98`) records `run.orch.digest_read_at = Some(at)`. The engine's own `now` no longer reaches it.
    - `OrchEvent` is not serialized, so there is no format change. A hold approved in the clone's own second is shown once more, which is harmless.
12. **The tier-3 mark of an open PR** (DH §2.3). `run/snapshot_stages.rs::full` (`:82-117`) keeps its order (bisecting, running, red on head, green on head). Where it answers `FullState::None` today, it answers instead, for a `pr`-mode run (`run.delivery.mode == DeliveryMode::Pr`) whose stage-`n` PR is `PrState::Open`, the latest tier-3 verdict, from a job that ran on an earlier head than the current one (it answers only where the on-head rule says `None`, so `last` is off-head there; ruling T9-1): `Green` when `s.full.last.ok`, `Red` when not, `None` when there is no last job (BR-13). The client's "stage n tier 3 red" alert is not raised for a red known to be on another commit (`full.commit` is `Some(c)` with `c != head`), so this stale red raises none (rulings T9-1, T9-2).
    - Local mode, and a `pr` stage before its PR opens, keep the on-head rule.
    - The digest reads the same `stage_infos`, so it changes with it.
    - The client is unchanged: `tui/src/graph/run_text.rs::stage_text_in` (`:163-184`) draws the state it is given, and the stage inspector shows `full.commit`.

### CI (DH §3)

13. **The CI bisect searches the whole line** (DH §3.1).
    - `engine/bisect.rs` gains `pub(super) enum BisectRange { SinceGreen, WholeLine }`. `range` (`:55-66`) and `start` (`:90`) take it.
    - With `WholeLine`, `range` ignores `green_at`: its base is `s.floor`, else `s.created_from`, and the candidates are every merge from the first up to `head`.
    - `full.rs::red` (`:447`) passes `SinceGreen`: tier 3's own reds keep today's range. `delivery/ci_repro.rs` (`:225`) passes `WholeLine`.
    - The early return at `ci_repro.rs:208-218` (ruling F1's `CI fails a test tier 3 passed on this head …` line) is deleted. The bisect's own start line, `stage <n>: CI red at <h7> reproduces; bisecting <k> merges` (`ci_repro.rs:238-241`), is the line (BR-12).
    - The usual assumption holds: the base is green for the failing test. A base that also fails takes the bisect's existing "no culprit" path. The search is bounded by the bisect's existing probe limits.
14. **The CI summary's log is not persisted** (DH §3.2).
    - `decider/ci.rs::CiSummaryInput.log` (`:37-38`) becomes `#[serde(default, skip_serializing)]`. The queued decider in `run.json`, the `Decide` op's journal intent and the pending op then hold no log text.

    - `engine/deciders.rs::dispatch` (`:51`) starts with one pass over `run.decider_queue`: every `DeciderRequest::CiSummary` whose `log` is empty is refilled with `ci::log_text(rec)` (`ci.rs:247`) of the CI record whose `decider == Some(q.decider_id)` and whose phase is `CiPhase::Summarising`. This covers the `Decide` emission (`:74-84`) and both fallback exits (deciders off, `:56-70`; no slot in time, `:85-101`), because `decider::ci::fallback` reads the log (`decider/ci.rs:62-66`) (BR-11).
    - *(Task M9.7.1, fact.)* `engine/delivery/mod.rs` declares `mod ci;` private (`:21`) and re-exports what the engine needs (`pub(crate) use ci::summarised as ci_summarised;`, `:35`). `deciders.rs` reaches `refill_log` only through a like re-export there (`pub(in crate::run::engine) use ci::refill_log;`), one line of `engine/delivery/mod.rs`'s budget.
    - `CiRecord.text` is kept until the summary (`ci.rs:396` clears it then), so a restored or lost op re-queued by `restore_lost.rs:117-130` with an empty log is refilled the same way.
    - With no record holding text, the decider runs with an empty log, which its prompt already handles.

15. **The CLI's bounded git** (DH §4.1). `cli/src/run_cmd/delivery.rs::bare_under` (`:349-384`) runs its `git -C <path> --no-optional-locks rev-parse --is-bare-repository --absolute-git-dir` through `daemon::subprocess::run(&mut git, 64 * 1024, daemon::host::HOST_READ_TIMEOUT)` (`subprocess.rs:97`; `HOST_READ_TIMEOUT` = 30 s at `host/mod.rs:444`, the bound the host's own local `git rev-parse` uses, `gh_git.rs:83-89`; BR-7), after `daemon::subprocess::scrub_inherited_git` (`subprocess.rs:456`).

16. **`escalate_for`** (DH §4.2), in `run/route_pick_step.rs`, re-exported from `route_pick.rs`'s `pub use step::{…}` (`:536-539`):

## Brief rulings

- **BR-1 (DH §2.1, "`omitted.holds` beside `omitted.scouts`").** The digest has no `omitted` object. Its count is the top-level `omitted_tasks` (`orch/digest.rs:112`); `omitted.scouts` belongs to `get_context` (`orch/context.rs:135`). The count is the top-level `omitted_holds`, beside `omitted_tasks`. It is written only when a hold is dropped, as `recipients_omitted` is (`digest.rs:167-170`). So "nothing changes while the digest fits" holds byte for byte, and `digest_fixture.json` is unchanged.
- **BR-2 (DH §2.3, "11i … pinned `tier 3 ◌`").** 11i never pinned it. `scripts/pty_smoke_pr.py:378-380` matches the prefix `stage 1/2  tier 3 ` and says in a comment that stage 1's mark is not asserted. The final task pins `stage 1/2  tier 3 ✓` there and replaces the comment.
- **BR-3 (DH §1.2, what "held" holds).** `land::merged` judges the replies too (`reply::landed(run, n, &at, delivered)`, `land.rs:124`), with the same `delivered`. An undecided stage holds that judgment and `missed_merge` with the line, so a reply is never sent or dropped on an unverified verdict. An undecided stage also holds `settled` (decision 8).
  - **Amended by ruling R1** (text under BR-4): the hold ends after 3 failed checks in a row, decided as `None`.
- **BR-4 (DH silent).** A base fetch that answers without a `contains` answer decides as `None`. A failed fetch op keeps the stage undecided until `base_fetch_retry_at`. Without this, a base branch gone from the remote would re-emit the fetch every pass.
  - **Ruling R1 (controller, `progress.md`, adopted 2026-10-05; amends BR-3 and BR-4).** An undecided delivery never blocks a run forever. After the `contains` check has failed 3 times in a row (failed fetch ops, each retried after `base_fetch_retry_at`), the stage decides as `None`: today's "not delivered" line, preceded by the log line `stage <n>: could not check whether <head7> is in the merge; treating it as not delivered`. Test: three failed ops decide `None`, and the run can complete.
  - *(Task M9.7.1, what R1 implies; not a new decision.)* BR-3's held judgment is released on that path too (as a `None` answer: `reply::landed` with `delivered = false`, `unpushed`, `missed_merge`), and BR-4's "keeps the stage undecided" holds for the first two failures only. The ruling does not say where the count lives. If it is persisted (it must survive a restart to stay "in a row"), it is a new `#[serde(default)]` field appended to `StageDelivery`, within `run/delivery/mod.rs`'s room (589 lines; `undecided` takes 4). "In a row" reads as: the count restarts wherever `undecided` is set or cleared. Task M9.7.5's engine side does it (controller addendum `task-5-brief.md`); task M9.7.6 only makes sure a failed check reports the op as failed.
- **BR-5 (DH §1.2's end-to-end, as literally worded, does not fail before the change).** A PR's `confirmed` is set to the opened head (`engine/delivery/open.rs:266`) and to any viewed head equal to `pushed_head` (`view.rs:332-335`). So user commits pushed onto an opened PR and merged before any view leave `head == confirmed`, and today already reads "delivered". The failure needs an anthrex push after the last confirming view. The end-to-end test therefore merges after a CI fix push (anthrex's push `H2`; the user's two `FakeGithubCtl::commit`s on top of it; a merge before anthrex views `H2`). That keeps DH's intent: two pushes, merged before anthrex viewed them.
- **BR-6 (DH §1.1 meets §1.2).** A deferred fix task that lands on an undecided merged stage decides that stage as not delivered (decision 3). Its commit was made after the host's merge, so the merge cannot contain the new local head.
- **BR-7 (DH §4.1, "the daemon's bound for a local git read").** The daemon has several bounds: `git::probe::PROBE_TIMEOUT` 5 s (status probes), `worktree::OPERATION_TIMEOUT` 30 s, `host::HOST_READ_TIMEOUT` 30 s. `bare_under` serves the fake host and runs the same `rev-parse` family the host bounds with `HOST_READ_TIMEOUT` (`gh_git.rs:83-89`), so that is the bound. Its test therefore waits about 30 s; it gets a `docs/timing-budgets.md` row.
  - **Ruling R2 (controller, `progress.md`, adopted 2026-10-05; amends BR-7).** No 30 s test. The bounded call is a function that takes its bound (`fn bare_under(…, bound: Duration)`, or a helper it calls), and the CLI passes `HOST_READ_TIMEOUT`. The unit test passes a bound of about 1 s with a `git` stand-in that sleeps 30 s, and asserts that the call returns within about 5 s with the message, which names the bound it was given (BR-8's `<n>` is `bound.as_secs()`, so `1` in the test and `30` in use). `HOST_READ_TIMEOUT` stays the production bound. The test's wall-clock bound still gets its `docs/timing-budgets.md` row (about 5 s). ## Review focus

1. **A verdict that never comes.** An undecided stage blocks completion and the branch delete. Every way out must exist: a `Some`/`None` answer, a `Missing` base, a reopen, a late merge, a restart. Ruling R1 adds one more: the third failed check in a row decides `None`. Tests in M9.7.5 cover each. A reviewer checks that no path leaves `undecided` set forever, and that `run cancel` still ends the run: `settled` gates completion, not cancellation.
2. **A false "delivered".** Only `Some(true)` from `merge-base --is-ancestor <local head> <merged head>` delivers. Check the argument order, the exit-code reading (1 with empty stderr is `false`; 128 is `None`), and that a stale answer (another head) is ignored.
3. **Git under a lock.** The two new git commands run inside the host op on `GitQueue::write`, through `GhHost::git` (the allow-list, `--no-optional-locks`, the scrubbed environment). Nothing calls git from the engine or under `daemon::lock`.
4. **Cancelling work that would have been delivered.** Only a merged stage with no live stage above cancels its fix tasks. A stage below a live one keeps them (propagate). The check uses `sync::live`, the same function `unpushed` uses.
5. **The log refill.** The request persisted without `log` must be refilled on every path that reads it (the `Decide` and both fallbacks), and only from the record whose `decider` is this request.

## Risks and gotchas

- **Positional formats.** `skip_serializing` on `CiSummaryInput.log` is safe because the run file and the journal are JSON (named fields). `CiSummaryInput` never goes over MessagePack (`git grep rmp_serde crates/daemon/src` finds nothing). Never add `skip_serializing` to a type that crosses the socket.
- **`confirmed` makes some merges "delivered" with no git at all** (BR-5). The end-to-end test must put an anthrex push between the last confirming view and the user's commits, or it proves nothing.
- **The adoption ref is shared.** `refs/anthrex/<run>/remote/stage-<n>` is also the adoption fetch's target. A merged stage is never adopted (adoption is due only for an open PR, `view.rs:337`), and both run on one queue, so they never interleave.
- **A squash with the branch deleted by GitHub** answers `None`: today's line, now honest that it could not verify. It is not a regression.
- **Older binaries.** One that loads a 9.7 `run.json` drops `undecided` (serde). It would re-judge nothing and could complete with an unjudged merge: the same class as the recorded 9.3/9.6 downgrade entries.
- **The tier-3 mark** can show ✓ for a PR whose later heads CI judges red. The row's `ci ✗` beside it carries that.
