**Goal.** While a run's orchestrator is alive, everything the run's agents and engine need goes to the orchestrator, which resolves it itself; the user is alerted only for approvals, acceptance, profile proposals, problems only the user can fix, the orchestrator's own `ask_user` questions, and the orchestrator being stuck. With no live orchestrator, today's alerts are unchanged.

**Architecture.** Routing is one pure TUI function, `alert_route`, re-evaluated on every draw from the snapshot; the daemon supplies the facts it reads (`BlockInfo.user_only`, `RunInfo.halt_user_only`, `DeliveryAlert.user_only`, `OrchestratorInfo.stuck`, `OrchestratorInfo.ask`). The orchestrator's five new `edit_plan` ops call the same engine cores as the user's requests, refactored to take an `Actor`; what it resolves is kept in `RunOrch.handled` and shown quietly. `ask_user` is a new orchestrator tool whose pending question rides in the snapshot; the user answers with a new `RunRequest::AnswerAsk`, delivered back to the orchestrator as a wake note.

**Tech stack.** Rust 2024 workspace; `serde`/`rmp-serde` wire types; `rmcp` for the MCP schemas; `ratatui`/`crossterm` for the TUI; `fake-agent` for every test.

**Spec.** `docs/superpowers/specs/2026-10-07-orchestrator-first-alerts-design.md`. Read it whole before task M9.9.2.

The user's decisions, which bind every decision here and are never reinterpreted (OFA §2):

- **D1** Questions and problems from subagents go to the orchestrator first.
- **D2** Autonomy "Everything": the orchestrator may retry, override (merge without approval), resume, approve holds and accept red stages on its own.
- **D3** The orchestrator escalates with an explicit `ask_user` tool; that is the user's only question channel during a run.
- **D4** The user still sees approvals (plan, design-doc gates, holds the orchestrator did not approve), ready-to-accept, profile proposals, user-only problems, and orchestrator-stuck alerts.
- **D5** Worker windows no longer toast or ring.
- **D6** What the orchestrator resolved on its own stays visible, quietly.

## Goal

During a run with a live orchestrator, the Alerts list holds no `Blocked`, `Halted`, `Stage` or `Delivery` entry the orchestrator could act on; every question the orchestrator puts to the user is one `orchestrator asks` alert; background workers never ring the bell (OFA §1). The orchestrator resolves blocks, halts, stage and delivery problems with `retry`, `override`, `resume_run`, `approve_hold` and `accept_red`, each with a reason, each recorded and listed quietly as `orchestrator handled N`.

In:

- Protocol 20: the five `edit_plan` ops, `AskInfo`, `HandledInfo`, `OrchestratorStuck`, `BlockInfo.user_only`, `RunInfo.halt_user_only`, `DeliveryAlert.user_only`, `FullInfo.accepted`, `RunRequest::AnswerAsk` (OFA §4.8).

### Protocol

1. **Protocol 20, not shared with 9.8** **(R)**. OFA §4.8 allows sharing 9.8's bump "if they ship together". They do not: 9.8 is built and merged first and may be released alone, and a 19 client must never meet a daemon that sends ops and fields it cannot decode. One more bump costs a constant and a test. New enum variants are appended **last**: `PlanEdit::{Retry, Override, ResumeRun, ApproveHold, AcceptRed}`, `RunRequest::AnswerAsk`. New fields are `#[serde(default)]` and left out while empty or false. Every new message, variant and field gets a JSON and a MessagePack round-trip test, and every client changes in the same task (AGENTS.md rule 4): the TUI (`app/replies.rs`'s match keeps its `_ => true` arm; `AnswerAsk` needs no form to free), the CLI client (`cli/src/run_cmd/status_orch.rs::orchestrator_lines` reads the new fields in M9.9.9; nothing else matches exhaustively, M9.9.1 checks with the compiler), `anthrex hook` and `anthrex mcp` (they never decode these; M9.9.1 checks).
2. **`PlanEdit` moves to `proto/src/plan_edit.rs`** before it grows: `run.rs` is 555 lines after 9.8. Move-only, its own commit, re-exported from `run.rs` by `pub use crate::plan_edit::{EditFile, PlanEdit};` so every path stays. Test counts before and after are recorded.
3. **The five ops** (OFA §4.2), wire names in `snake_case` under `op`:

   | Op | Fields | Engine core |
   |----|--------|-------------|
   | `retry` | `task_id`, `reason` | `requests::retry_on` |
   | `override` | `task_id`, `reason` | `gates::override_on` |
   | `resume_run` | `reason`, `stage?` | `restore::resume_on`, or `full::retry_stage` + `delivery::watch::release_stage` with a stage |
   | `approve_hold` | `hold`, `reason` | `gate_holds::decide_on` |
   | `accept_red` | `stage`, `reason` | `full_accept::accept_red` |

   **(R)** OFA writes `resume { reason, stage? }`; `resume` is the pause edit's wire name since M8a (`PlanEdit::Resume`, unit, `deny_unknown_fields`), so the halt resume is `resume_run`. **(R)** OFA writes `retry { task, reason }`; `task` is already `add_task`'s object key in the MCP schema, and every task op names its task `task_id`, so these do too.
4. **`user_only` lives on `BlockInfo`, not on `BlockReason::Environment`** **(R)**. OFA §4.4 says `Environment` "gains a `user_only: bool`"; `BlockReason` is a `Copy` unit enum compared by value in about forty places and written into every `run.json` and history line as a plain string, so a struct variant would break both. `BlockInfo { reason, text, user_only }` carries it, default `false`, left out while false; `BlockInfo::new(reason, text)` is the constructor every literal moves to (45 literal sites, mechanical).
5. **`RunInfo.halt_user_only`, `DeliveryAlert.user_only`** carry the same fact for a halt and a delivery alert, computed in the snapshot (decision 18).
6. **`accept_red` is new engine behaviour** **(R)**. OFA's table names "stage menu" as the user's path; no such entry exists (`actions/mod.rs:45` lists only `MessageStage` on a stage), and nothing accepts a red tier 3 today: the user's way out is `finish`, which ends the run. `accept_red { stage, reason }` records `StageFull.accepted_red = Some(<head>)`; every reader of "this stage's head passed tier 3" (`full::lacks_green`, `full::request`'s green check, `delivery/open.rs:158`) goes through one new `full_accept::passed_at(&StageFull, head)`, true for a green or an accepted red on `head`. The bisect's "since green" range keeps reading `green_at` only. A new head clears nothing: an acceptance names its commit, so a later red on a new head is red again. The snapshot sets `FullInfo.accepted` while the accepted commit is the head; the state stays `Red`. Precondition (`rules::accept_red`): the run is running, the stage exists, its head is red (`full::red_at_head`) and not already accepted. No user action is added.
7. **`RunRequest::AnswerAsk { run_id, ask: u64, choice: Option<u32> }`**, answered under `request::ANSWER_ASK = "run answer-ask"`. `choice` is the option's 0-based index; `None` means "answered in the window" (decision 14).
8. **`OrchestratorInfo`** gains `stuck: Option<OrchestratorStuck>`, `ask: Option<AskInfo>`, `handled: Vec<HandledInfo>` (newest last, at most `HANDLED_KEPT = 50`), `handled_total: u32`.

### Engine

9. **One core per action, with an `Actor`.** `engine/actor.rs` (new, pure): `pub(crate) enum Actor { User, Orchestrator }` with `who()` (`"the user"`, `"the orchestrator"`) and `label()` (`"user"`, `"orchestrator"`), `Default` = `User`, serde `snake_case`. Each user handler (`requests::retry`, `gates::override_task`, `gate_holds::verdict`, `restore::resume`) becomes a thin wrapper that looks the run up, calls its core with `Actor::User` and replies; every user-visible text is unchanged when the actor is the user (existing tests pin it). The cores take `&mut Run`.
10. **Same preconditions** (OFA §4.2): each op runs the user path's rule first (`rules::retry`, `rules::override_task`, `rules::resume(run, false)`, `rules::hold`) and refuses with its text. Three orchestrator-only refusals are added, each **(R)**:
    - an empty or blank `reason`: `<op> needs a reason the user can read`; one over `REASON_MAX_CHARS = 500`: `reason: at most 500 characters`;
    - a task, halt or stage whose problem is user-only (decision 17): `<target> waits on something only the user can fix, and they have been alerted: <first line>`. OFA §4.4 defines user-only as "a cause the orchestrator cannot fix"; letting it retry one in a loop burns tokens and repeats the block;
    - a paused run: the tool gate's existing `run <id> is paused; the user must resume it` (`orch.rs:251-254`) still applies to every op. A pause is the user's.

    The tool gate (`orch.rs:240-256`) refuses every orchestrator call on a halted or paused run today. `orch_ops::admitted` lets through, on a halted run, `ask_user` and an `edit_plan` whose only edit is one `resume_run`; on a paused run, `ask_user` only (M9.9.3). **(R)** Without it `resume_run` and `ask_user` would be unreachable exactly when they are needed.
11. **An op is alone in its call**, with no `submit`, `summary`, `responses` or `iterate`; otherwise `ACTION_ALONE` (`orch/contract.rs`): `retry, override, resume_run, approve_hold and accept_red each come alone in their edit_plan call`. The check and the dispatch live in `engine/orch_ops.rs` (`intercept`), called from `orch.rs::edit_plan` right after its complete-run check. A user's `run edit` or a sub-planner's `submit_epic` carrying one is refused in `edits.rs` / `planners.rs::forbidden` (M9.9.1) with `op <op> is the orchestrator's; you have anthrex run <cmd>` (`retry` → `retry`, `override` → `override`, `resume_run` → `resume`, `approve_hold` → `approve --hold`, `accept_red` → `finish`) and `op <op> is not available to a sub-planner`.
12. **Records** (OFA §4.2, §4.5). A successful op: the run log line `orchestrator: <verb> <target> — <reason>` (`retried t3`, `overrode t3`, `resumed the run`, `resumed stage 2`, `approved hold epic:ui`, `accepted the red tier 3 of stage 2`), one `HandledRecord { at, op, target, reason }` in `RunOrch.handled` (oldest dropped past `HANDLED_KEPT`; `handled_total` counts all), and an accepted entry in the plan-edit log (`edit_log::record`, described `retry t3`, `override t3`, `resume_run`, `resume_run stage 2`, `approve_hold epic:ui`, `accept_red stage 2`). A refused op: `refuse` (the JSON `{"error": …}` every tool refusal gets) and `record_rejected`. The task's history names the actor (`retried by the orchestrator at rung 2 (it was blocked(environment): …)`). **(R)** OFA says "recorded in the journal": the run's intent journal (`journal.jsonl`) holds ops only (`journal.rs:46`); the record is `run.json`'s `orch.handled`, which the same save makes durable, plus the run log.

14. **No wake note for the orchestrator's own act** (it knows): `decide_on` notes "the user approved hold …" only for `Actor::User`. `hold.decided_by` is `actor.label()`.

### `ask_user` (OFA §4.3)

15. **The tool.** `ask_user { question: String (1–500 chars), options: Vec<String> (0–9, each 1–200 chars), context: String (0–4000 chars) }`, `question` required. The orchestrator's only; allowed on a running, planning, gated, complete-but-not-accepted, halted or paused run (the tool gate admits it on a halted or paused run, decision 10); refused on a terminal one (`run <id> is <state>`). It stores `RunOrch.ask = Some(AskRecord { id, question, options, context, asked_at })` with `id = ++RunOrch.ask_seq`; an unanswered one is replaced, logged `orchestrator asks: <question> (replaces "<old>")`, and the reply says so. The reply returns at once: `asked; the answer arrives as a message` (or `asked, replacing your earlier question; the answer arrives as a message`). Text is kept as given (bounded); every client sanitises where it draws (`one_line`, `safe_text`).
16. **The answer.** `AnswerAsk { run_id, ask, choice }`: refused when the run has no pending question (`run <id> has no pending question`), when `ask` is not the pending one's id (`that question was replaced; answer the new one`), or when `choice` is out of range (`choose 1 to <n>`). `Some(i)` adds the wake note `the user chose: <option i>` and clears the question; `None` clears it with no note (the user typed the answer in the window, which the orchestrator reads directly). The question is dropped when the run leaves for `Complete`, `Accepted`, `Discarded` or `Failed` (OFA §5), in the post-step pass (`asks::drop_settled`).
17. **Answering in the window** **(R)**: OFA says "the next orchestrator turn start clears a question it was told about"; the daemon cannot tell a typed prompt from a pasted wake-up (both are `UserPromptSubmit`). The TUI, when it forwards bytes containing `\r` to a PTY window that is a run's orchestrator with a pending question, also sends `AnswerAsk { choice: None }` (`app/asks.rs::forward`). Other clients do not (Scope "Out").

### User-only problems (OFA §4.4)

### The stuck orchestrator (OFA §4.1, §5)

19. **Stalled** **(R)**: OFA says "stalled past `stall_after_secs`" without saying of what. It is: a wake note has been pending for `limits.stall_after_secs` with no anthrex tool call by the orchestrator since. `RunOrch` gains `acted_seq: u64` (the highest note seq, `run.orch.orchestrator`'s `OrchestratorRecord.last_note_seq` (`orch/mod.rs:182`), when it last called a tool or read the digest), `waiting_since: Option<u64>` and `stalled_at: Option<u64>`, all `#[serde(default)]`. `engine/orch_stall.rs` (new, pure): `pass(run, now)` in the post-step loop sets `waiting_since` once the record's `last_note_seq > acted_seq`; `tick(run, now)` in the `Tick` arm sets `stalled_at` once `now >= waiting_since + stall_after_secs` and logs `the orchestrator has not acted for <n> min; its alerts go to you`; `acted(run, now)` (from `orch.rs::tool` for the orchestrator's role and from `wake::digest_read`) sets `acted_seq = last_note_seq`, clears both, and logs `the orchestrator is acting again` if it was stalled. The flag's change bumps the run's revision, so the snapshot is republished (`engine::finish`, decision 47 of M8a).
20. **Dead**: the orchestrator's window is not live (`!o.live`), it has had one (`o.window_id.is_some()`), and the run is `Running` or `Halted`. `since` is `o.exited_at`.
21. **What it changes.** `OrchestratorInfo.stuck` is `Stalled { since }` or `Dead { since }`; `alerts_route::orchestrator_lives(run)` is `o.live && o.stuck.is_none()`, so every Orchestrator-routed alert returns to the user on the next draw (OFA §5), and `OrchestratorStuck(run)` is raised at priority 1: `orchestrator has not acted for <n> min; its alerts are yours`, or `orchestrator exited; its alerts are yours · anthrex restart <window> restarts it`. Enter focuses its window (as `Orchestrator`'s).

## Tasks

Do them in this order. Each task's tests are written first and must fail before its change (AGENTS.md rule 6), except those marked **pinning** (they pin today's behaviour and pass on today's code by design). One commit per task; a move-only split is its own commit inside its task.

**Why this shape** (the controller's ten-task outline, adjusted where the code argues): the engine ops are two tasks (M9.9.2 the three whose cores exist, M9.9.3 the two that need new engine behaviour and the halted run's tool gate), because `accept_red` is new behaviour (decision 6) a reviewer can reject on its own; the stuck orchestrator (M9.9.6) is its own task because OFA's "extended" `orchestrator_lives` needs daemon state the TUI cannot compute (decision 19); the quiet view and the bell rule share M9.9.9 because both are small, pure and in the same crate.

2. **The orchestrator dies or stalls with work routed to it**: everything it was holding must reach the user at once, with no snapshot change but its own (M9.9.8 `a_live_orchestrator_takes_the_environment_block_and_a_stuck_one_gives_it_back`; M9.9.6 `an_exited_window_on_a_running_run_is_dead`).
3. **An answer to a question that was replaced, or from a second TUI after the first answered**: the stale answer must be refused, never delivered as the answer to the new question (M9.9.7 `a_new_question_replaces_an_unanswered_one_and_the_old_id_is_refused`, `answering_in_the_window_clears_it_without_a_note`).
4. **Hostile or oversized text in `ask_user` and in a `reason`** (control characters, bidi overrides, ten options, 501 characters): the daemon bounds it again and every client draws it on one line (M9.9.7 `bounds_are_checked_again_by_the_daemon`, M9.9.2 `an_op_needs_a_reason_and_comes_alone`, M9.9.8 `an_ask_with_hostile_text_draws_on_one_line`, M9.9.9 `handled_rows_list_newest_first`).

## Risks and gotchas
