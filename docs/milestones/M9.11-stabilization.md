# Milestone 9.11: Stabilization

> **For agentic workers:** REQUIRED SUB-SKILL: use superpowers:subagent-driven-development (the user's standing choice) to implement this brief task by task, TDD. Steps use checkbox (`- [ ]`) syntax for tracking. Several implementers can work at once: see "Streams".

> Written 2026-10-10 against the code at `382259c1` (milestone 9.10's head, about to merge to `main`; protocol 21). Every `file:line` and line count below is on that commit and relative to `crates/` unless the path says otherwise. The input is the ranked stability inventory `.superpowers/sdd/stability-inventory.md` (categories A to F), whose every item was re-read in the code for this brief; "Checked and dropped" lists what was not kept and why. Task M9.11.1 re-checks every name and line on `main` once 9.10 has merged.

**Goal.** A stable release with no new features: nothing a user does loses data silently, nothing hangs or crashes the daemon, the suite passes five times in a row on macOS and twice in a row in CI on both systems, and every security gap the inventory found in isolation and environment handling is closed or documented.

**Architecture.** No new subsystem. Each fix is made at its root cause, in the module that owns the defect, with a test that fails before it. The work is split into eight streams whose files do not overlap, so they can be implemented in parallel worktrees, then one closing stream (docs, the PR #54 check, the release gate).

**Tech stack.** Rust 2024 workspace; `tokio`; `vt100` 0.16; `crossterm` 0.29; `ratatui`; `fake-agent` for every agent in every test.

**The user's rulings, which bind this milestone and are never reinterpreted:**

- **R1 Scope.** All of the inventory's categories A (data loss), B (crashes and hangs), C (flaky tests) and D (security and isolation), plus E items only where the fix is about one line. F is out of scope (listed under Scope, "Out").
- **R2 Environment (D1).** The user's own agent windows **keep** inheriting `CLAUDE_CODE_*`, `MCP_*` and `OTEL_*`. They are not scrubbed. The behaviour is documented in README (task M9.11.39).
- **R3 Milestone 7 is dropped.** Its four terminal-input items are in this milestone (M9.11.24, M9.11.26, and the paste policy in M9.11.24/M9.11.39), each re-verified in the code below. Removing milestone 7's references is **not** this milestone's job: a separate docs PR does it. This milestone never edits ROADMAP's milestone 7 row, `docs/milestones/M7-split-panes.md`, or any other milestone 7 text.
- **R4 C2** (`testexec` ETXTBSY) is fixed by PR #54 and is excluded; M9.11.40 verifies it after #54 merges and re-checks C5 then.
- **R5 No new features.** A fix may add an internal API, a constant, a log line or a refusal text. It adds no user-facing command, key, screen or config key, except where a decision below names one as the only way to close a defect (decision 32's `ANTHREX_CHECK_ENV_PASS`).
- **R6 No retries and no longer sleeps** fix a flaky test. A flaky test's fix is at its root cause; its "test first" is a deterministic reproduction (an injected collision, stall or race) where one is possible, and a test that merely loops is never one.
- **R7 Process-kill code** (B6) is changed only by exact pid, never by name or pattern, and every test of it signals only processes the test itself started (the user's standing rule after the M8a.21 mutant). No mutation testing of kill code.
- **R8 Tests never reach a real agent.** Every fixture pins `ANTHREX_CLAUDE_BIN`, `ANTHREX_CODEX_BIN` and `ANTHREX_DECIDER_BIN` to `fake-agent` or a nonexistent path.

## Goal

After this milestone: a long-lived daemon keeps sending runs to its clients however many have finished; a message to a worker survives the worker's replacement; a deleted task checkout's commits are salvaged; a panic in the driver costs one event, not the engine; the daemon process exits after `anthrex daemon stop` even with a stuck blocking task; the flaky tests the inventory names have deterministic reproductions and root-cause fixes; checks no longer see the user's cloud and registry tokens by default; and the four terminal-input items milestone 7 carried work in the single-pane client. The release is then "ready to tag"; tagging is the user's decision.

## Design decisions

Numbered and final. If one proves wrong or impossible, stop work on it, record the evidence under "Implementation notes", and continue with the tasks that do not depend on it. A decision marked **(R)** is a ruling on something the inventory or the followups leave open; the user's rulings of 2026-10-10 settled every one (Implementation notes, "User rulings").

### Structure

1. **Streams.** The tasks are grouped into streams E, D, G, P, T, S, X and C, each owning a disjoint set of files ("Streams"). A stream's tasks run in the listed order in one worktree; streams run in parallel; stream Z runs after all of them are merged into `m9.11-stabilization`. A file named in two streams' work is assigned to exactly one ("Cross-stream files"), and the other stream does not touch it.
2. **No protocol change.** Every fix here is inside the daemon, inside the client, or in `run.json`. Where a fix could have been made on the wire (A7, D5), the wire-free alternative was chosen (decision 22 and "Checked and dropped"). M9.11.1 confirms `PROTO_VERSION` is 21 and records it; any task that finds it needs a wire change stops and records it instead.
3. **Move-only commits first.** A file at or near 600 lines that a task must grow is split by a move-only commit inside that task, its test count recorded before and after (equal): `run/driver.rs` (572, M9.11.7), `run/engine/signals.rs` (597, M9.11.6), `tui/src/app/mod.rs` (599, M9.11.21), `cli/src/main.rs` (596, M9.11.27).

### Engine (stream E)

4. **A worker's waiting messages are carried, never dropped** **(R)** (A2, A4). `ladder::drop_queued` (`ladder.rs:102-106`) becomes `take_queued(run, i) -> Vec<String>`: it removes the task's undelivered outbox messages and returns their texts in queue order, leaving out any that `worker_messages::carries` already puts in the notes section (so nothing is said twice, as `worker_messages.rs:143-198` pins). Rung 2 (`:278`) accumulates them into its new `FreshSession.append` with `outbox::accumulate`. Rung 3 (`:309`), rung 4 (`:344`) and `race::lane_out` (`race.rs:377`) no longer remove anything: a blocked task holds its mail (M8a.6 ruling N5, `outbox.rs:115-122`), and `requests::retry`'s fresh session (`requests.rs:494-497`) takes it with `take_queued` into its `append`. `outbox::resumed`'s failure path (`outbox.rs:372-383`) takes the task's delivered-but-unconfirmed messages' texts (`delivered_at.is_some()`, not in `carried`) **before** `ladder::supersede` removes them, and accumulates them after the carried ones. `launch`'s own `supersede` (`dispatch_session.rs:110`) is unchanged: a launch's first turn is built before it.
5. **The orchestrator may not cancel a user-only task** (A5). `Batch::cancel` (`edits.rs:324`) refuses, for `EditSource::Orchestrator` and a sub-planner, a task whose `block.user_only` is set, with `user_only::refusal(&format!("task {id}"), &block.text)` — the text `retry` gives (`orch_ops.rs:137-150`). The user's `cancel_task` is unchanged.
6. **A digest read answers only the notes it held** (A8). `orch_stall::acted` gains a `seq` argument: `acted_seq = max(acted_seq, seq.min(last_seq))`. A tool call passes `last_seq` (unchanged behaviour); `digest_read` (`wake.rs:110-114`) passes its `notes_seq`. The post-step `pass` (`orch_stall.rs:30-40`) then restarts the clock when a newer note is left.
7. **A broken sandbox blocks the task with its cause** (A10). **OPEN (pre-flight P13): M9.11.6 waits for the user's answer; E's other tasks do not depend on it.** The scout, the only consumer today, does *not* fail on a sandbox-failed tool result: it records the first note (`scout/machine.rs:261-263`, `get_or_insert`) and names it only when the session later fails or times out. This decision blocks a worker at the first such result, which also blocks a worker whose agent would have recovered (a retried command, a different tool). Option (a): as written below, block at the first one. Option (b): as the scout does, record the note on the round and add it (`with_sandbox_hint`) to the reason of the task's next block, stall or failure, blocking nothing new. `sandbox_command_failure`'s note already ends with `USERNS_HINT`, so in either option `with_sandbox_hint(note)` is `note` unchanged (it adds only `SANDBOX_HINT`, and only to a `SANDBOX_UNAVAILABLE` text, `headless/failure.rs:98-109`). `translate` (`observe.rs`) maps a failed `SessionEvent::ToolResult` whose text `failure::sandbox_command_failure` recognises to a new internal `AgentSignal::SandboxBroken { note }`; every other `ToolResult` stays `Activity`. The engine blocks a worker's, reviewer's or research session's task `blocked(environment)` with `failure::with_sandbox_hint(note)`, once per round, killing nothing beyond what `block` already does. The handler lives in a new `run/engine/sandbox_broken.rs`; `signals.rs` gains only its dispatch arm after a move-only split. `AgentSignal` is internal (not serialised to clients); `early.rs`'s match gains the arm too.

### Driver and daemon core (stream D)

8. **A panic anywhere in an event's handling costs that event** (B1, B3). The loop (`driver.rs:295-299`, moved to `driver/event_loop.rs` by M9.11.7) runs each `service.handle(kind)` as its own `tokio::spawn` and awaits it; a `JoinError` that `is_panic()` is logged at `error` with the event's kind, and the waiting caller, if any (`guard::reply_of`, taken before the spawn), is answered `guard::EFFECTS_PANICKED` (new: `the run engine failed while carrying out this request (a bug; see the daemon log); the run may not match what was saved`), not `STEP_PANICKED`, whose `the runs are as they were` is false once a step has been committed and only its effects failed (pre-flight P12). Events stay strictly sequential (each awaited before the next is received). On a second panic in `prepare_guarded_with` (`guard.rs:63-66`), the state is put back to the pre-step clone and the caller answered `STEP_PANICKED`, so memory never holds a step whose saves did not run: `guarded_step` returns the `before` clone with the effects, and `handle` restores it when `prepare_guarded` reports the double panic (`Option<Vec<Ready>>`, `None` on the second panic).
9. **A lagged session feed is caught up from the manager** (A12). The manager keeps, per headless window and per process id, how many `TurnEnded` events it applied and the last one, and that process's `ProcessExited` once applied (`apply_session_event`, `manager/headless.rs:389`). `forward` keeps the same two facts for what it forwarded. On `RecvError::Lagged` it asks the manager (`WindowManager::headless_terminal_events`) for every window's record and forwards, translated, each `ProcessExited` it has not forwarded for that `(window, pid)` and, where the manager applied more `TurnEnded`s for a pid than it forwarded, that pid's last `TurnEnded` (lost intermediate turn ends are coalesced into the last; the engine needs only the latest to move on). `WindowSignal` itself is unchanged (its literals are in other streams' files: `run/driver/observe.rs`, `daemon/tests/support/headless.rs`). The channel capacity becomes `ManagerConfig.signal_capacity` (default `SIGNAL_CHANNEL_CAPACITY`) so a test can force a lag.
10. **The snapshot carries at most `TERMINAL_RUNS_SHOWN = 50` terminal runs** **(R)** (A1). `snapshot` keeps every non-terminal run and the 50 terminal runs (`RunState::is_terminal`, `proto/src/run.rs:412`) whose `created_at` is newest, ties by `run_id` — the order `snapshot` already sorts by (`snapshot.rs:34-39`); `Run` has no last-change time (`model.rs:180-330` holds `created_at` and no finish time), and adding one would be a `run.json` field in stream X's file (pre-flight P3); older terminal runs stay in memory and on disk, unchanged, and leave every snapshot (pushed and `List`). 50 is `SNAPSHOT_BOUND`'s own run count (`snapshot.rs:507-509`, 50 runs of 20 tasks under 1.25 KiB a task). Then, as the frame's last guard, `publish` and `current` encode the snapshot once and, while it exceeds `MAX_FRAME - FRAME_MARGIN` (64 KiB), drop the oldest remaining terminal run; if only live runs remain and it is still too large, they send it as is and log `error` naming the largest run (the writer's existing `warn` at `server.rs:198-202` stays as defence in depth). The guard runs on the snapshot as sent, after `with_scouts` and the queued goals are added (`driver.rs:319-323`). `resolve_run` (`cli/src/run_cmd.rs:488-505`, used by every `run` subcommand) keeps its `no run matches '<run>'` text, which five tests pin (`run_cmd/tests.rs:72,76`, `run_cli.rs:348`, `run_cli_delivery.rs:152,266,473`); only when the list it searched holds `TERMINAL_RUNS_SHOWN` finished runs does it append ` (only the 50 most recent finished runs are listed)` (pre-flight P4).
11. **A brief is capped where the daemon validates it** (B5). `validate.rs` refuses a brief over `BRIEF_MAX_CHARS = 1_000_000` characters (the TUI form's own cap, `tui::run_edit::BRIEF_MAX_CHARS`) with `brief: at most 1000000 characters`, and a plan whose briefs total over `PLAN_BRIEFS_MAX_BYTES = 4 MiB` with `the plan's briefs total <n> bytes; at most 4194304`. Both run for a plan file, `run edit` and `edit_plan`. The test of decision 10 proves the largest accepted plan's gate snapshot fits one frame.
12. **A wake's `\r` is held when the user typed during the gap** **(R)** (A9). `deliver_wake` notes `Instant::now()` before the paste; after `SUBMIT_DELAY` it reads `manager.last_client_input(window_id)`, and if an input is newer than the paste it does not send `\r` and returns `Ok(Delivery::Unsubmitted)`. The driver logs `the user typed during the wake-up; it was pasted and left for them to submit` and still reports `OrchestratorWoken` (the notes reached the window, and the digest keeps them), so the same notes are never pasted twice. The body is `deliver_wake_with(manager, window_id, paste, delay)`; `deliver_wake` calls it with `SUBMIT_DELAY`, and the test passes a long delay so its input lands inside the gap by construction, not by a sleep racing 200 ms (pre-flight P11).

### Git and worktrees (stream G)

13. **A checkout deleted by hand is salvaged from its repository** (A3). `salvage_in` (`cleanup.rs:79-95`), when `path` is gone and the checkout's repository (`checkout_repo_dir`) has a `HEAD`, calls a new `git::salvage_gone(g, root, repo, reference, message, timeout)`: it imports the objects reachable from the repository's `HEAD` and not from the task branch into the user's repository (the `import_revs` path, `import.rs:177`), then creates `reference` at `HEAD` unless `HEAD` is already the task branch's tip. Only then does `remove_checkout` remove the repository.
14. **A nested repository keeps its checkout** **(R)** (A14). Before removing a task checkout, salvage lists untracked directories holding a `.git` and the index's gitlinks; if any has a working tree with changes or commits not in the salvage, the removal is skipped, the checkout and its repository are kept, and the run log says `kept <path>: it holds a nested git repository (<sub>) whose work anthrex cannot salvage; remove it yourself when done`. M8a decision 20's `add -A` is unchanged.
15. **A task checkout commits as the user's repository would** (A15). When `ensure` writes a task repository's config, it resolves `user.name` and `user.email` in the user's repository (`git config --get` in `root`, where `includeIf "gitdir:…"` matches) and writes them into the task config after the include. An identity git cannot resolve is left out, as today (the identity check at `run/git/mod.rs:427-441` still refuses). The `git config --get` calls here and decision 14's nested-repository probes run through the run git helpers, with `--no-optional-locks` and the scrubbed environment (AGENTS.md rule 11, the pathspec variables included), inside the existing blocking git path and its timeout (rule 2) (pre-flight P16).
16. **The Linux grant's windows are closed** (D8). The grant refuses, rather than sweeps, a symbolic link at a denied path (`sandbox.rs:171-185`): `the checkout's git directory has a link at <name>; anthrex will not grant it`. A daemon git call in a task checkout re-runs `pinned::check` after the call (`worktree.rs:383`'s wrapper); a failure discards the call's result and returns the check's refusal.
17. **`restore_owner_access` walks by descriptor** (D9). It opens `path` with `O_DIRECTORY | O_NOFOLLOW`, then each child with `openat(dirfd, name, O_DIRECTORY | O_NOFOLLOW)`, and changes modes with `fchmod` on the opened descriptor; a child that is not a directory is left alone. Nothing is ever reached through a path re-resolved after a step.
18. **Git watches on Linux skip what the deny list rejects** (B12). On Linux, `watch::build` walks the root once, skipping every directory `watch::accepts` rejects (`DENY_COMPONENTS`, `git.ignore`, and the git dir's `objects/` and `lfs/`, `watch.rs:56-60` — `objects/` alone is up to 256 directories), and watches each kept directory `NonRecursive`; a directory created later (or renamed in) is walked with the same `plan` on its `Create` event, its accepted directories are watched, and only **then** is the event forwarded, so an event forwarded for a new directory means it is watched. The walk is never followed through a symbolic link. macOS keeps one recursive FSEvents watch (no descriptor per directory there). The walk is a function `watch::plan(root, git_dir, ignore) -> Vec<PathBuf>` that applies `accepts` (pre-flight P10); `build` already runs on a blocking thread (`git/mod.rs:333`) and the `Create` handler on notify's own thread, never on a tokio worker.

With a mouse mode on, the wheel's report is encoded as the app asked (`mouse_protocol_encoding()`): `Sgr` → `\x1b[<b;x;yM`; `Default` → `\x1b[M` and three bytes `32+b`, `32+x`, `32+y` (a coordinate over 223 sends nothing); `Utf8` → `\x1b[M` and the three values as UTF-8 code points `32+v` (over 2015 sends nothing).
