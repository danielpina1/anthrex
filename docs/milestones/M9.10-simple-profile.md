**Goal.** Starting a goal in a repository with no profile never refuses: anthrex sets the profile up, asks for one review, then starts the goal. The Profile screen is one page that explains itself in plain words, and an edited command is checked once and saved without a separate confirm step.

**Architecture.** The daemon's `ProfileService` gains a per-repository goal queue (`<repo_dir>/queued_goals.json`, mirrored in memory), drained by a starter callback into `RunService::start_goal` whenever the profile is stored; the snapshot carries the queued goals and their setup state, and the profile status carries the verification's progress, so the TUI and the CLI read one status. Edits become row edits: a command row is verified once through today's re-verification path and stored on ✓, or held as a failed row edit the user saves anyway or reverts. The TUI's Profile screen, its card and its words are pure state and rendering over the status and the two `Shown` sides, as today.

**Tech stack.** Rust 2024 workspace; `serde`/`rmp-serde` wire types; `toml` for the profile; `ratatui`/`crossterm` for the TUI; `fake-agent` (its `scout-onboarding-<n>` scripts and decider scripts) for every test.

**Spec.** `docs/superpowers/specs/2026-10-07-simple-profile-design.md`. Read it whole before task M9.10.2.

The user's design rules, which bind every decision here and are never reinterpreted (SP §2, and the conversation that approved SP):

- **D1** Automatic set-up with one review card: **Use this** / **Edit**. A goal in a repository with no profile is queued, never refused for that reason.
- **D2** Plain sections (**How anthrex checks your work**, **Your repo**, **Delivery**) and an **Advanced** section collapsed; plain labels, each row's config key dimmed beside it; one plain status line; no tabs, no hidden toggle, no raw-TOML confirm page.
- **D3** An edited command is verified once: ✓ saves at once; ✗ shows the output with **Save anyway** / **Revert**. Edits work on a proposal as well as on the stored profile.
- **Profile changes stay user-confirmed.** Nothing stores a detected profile without the user's **Use this**, `anthrex profile use|confirm`, or a `--yes` the user typed.
- **Tests never reach a real agent.** Every fixture pins `ANTHREX_CLAUDE_BIN`, `ANTHREX_CODEX_BIN` and `ANTHREX_DECIDER_BIN` to `fake-agent` or a nonexistent path; no test changes program selection.
- **No new kill or signal code.** A running scout is stopped only through `ScoutService::stop` and a verification only through its `CancellationToken`, as `profile reject` does today.

## Goal

`anthrex run start --goal` (and the TUI's goal form) in a repository with no stored profile starts detection and answers `queued`; once the proposal is ready, one alert opens one review card; **Use this** (or `anthrex profile use`, `confirm` kept as its alias) stores it and starts every queued goal. The Profile screen (`C-b P`) is one page: one status line, three plain sections, a collapsed Advanced section, each row's key dimmed beside its plain label, a one-line hint under the list. `e` on a command row checks the new command once and saves it on ✓; on ✗ the row shows ✗ with its output one key away, and `s` saves anyway, `r` reverts. Edits work on a proposal too. `anthrex profile status` prints the same status line.

### The queue (SP §4.1, §5)

4. **Stored beside the proposal, in its own file** **(R)**. SP says queued goals are "persisted with the proposal record". They are kept in `<repo_dir>/queued_goals.json` (`queue::QUEUE_FILE`), next to `proposal.json`, written under the service's `writes` mutex. Not inside `ProposalRecord`: every phase of a detection writes its own clone of the record (`service_run.rs::advance`, `job.record`), so a goal queued while the scout runs would be lost on the next phase's write. The file holds `GoalQueue { goals: Vec<QueuedGoal>, dropped: Vec<DroppedGoal> }`, written atomically (temp file and rename, as `store::save_proposal` does), and removed when both lists are empty. `Table.queued: BTreeMap<PathBuf, GoalQueue>` mirrors it in memory (`restore` fills it), so the snapshot never reads a file.
5. **A queued goal** keeps the whole request: `id`, `project`, `dir`, `goal`, `queued_at`, `yes`, `trust_project`, `unconfined_checks`, `orchestrator`, `delivery`, `design`. Its id is `q-<unix nanos>-<n>` (`n` a process-wide counter, as `TRIAGE_SEQ`). At most `MAX_QUEUED = 8` per repository; a ninth is refused: `<name> already has 8 goals waiting for its profile; review it first (C-b P, or anthrex profile status)`.
6. **Draining** (SP §4.1). Whenever a review proposal becomes the stored profile (`confirm`, which **Use this** and `profile use` send; `after_ready`'s `--yes` store, decision 9), the service takes the repository's goals out of the queue (written before any start, so a crash never starts one twice **(R)**: at most once), then starts them one after another, in queue order, through the starter callback (`GoalStarter`, installed by `wire` with a weak `RunService`, as `set_live_runs` is). Each start is `RunService::start_goal` with the stored request. A start the daemon refuses (the base branch is gone, the directory is gone, a start check) records `DroppedGoal { goal, reason, at }` (the last `DROPPED_KEPT = 5` kept) and logs `dropped the queued goal "<goal, first 60 chars>": <reason>`. `confirm`'s reply adds `; starting 1 queued goal` or `; starting <n> queued goals`.
7. **Failure** (SP §5). A detection that fails keeps the queue; the snapshot's queued goals carry `SetupState::Failed { reason }`, which the TUI shows as one set-up alert per repository (decision 18). **Retry** sends `Detect` with the first queued goal's `trust_project` and `unconfined_checks`. A detection the daemon restart interrupted is failed with `RESTART_REASON` as today, and the queue is kept the same way.
8. **Discard** **(R)**. `profile reject` (the screen's `x`, `anthrex profile reject`) on a repository with queued goals drops them all, each recorded as a `DroppedGoal` with reason `the proposal was discarded`; the reply adds `; dropped <n> queued goal(s)` and the discard page says so first (decision 30). SP does not say; a goal cannot start without a profile, and leaving it queued behind no detection would wait forever.
9. **`--yes`** (SP §4.1). A goal with `yes` and a **ready** review proposal stores it at once (`confirm` without `shown`, today's `confirm --yes`), and starts normally (its reply is `Triaged`, its message prefixed `stored the proposed profile for <name> (--yes); `). Queued with `yes` while detection runs: when the proposal turns `Ready` (`service_run.rs::verify_phase`, the `advance(Ready)` point), `after_ready` stores it only if `dropped` is empty and some queued goal has `yes`, then drains; otherwise the review alert is raised as for any ready proposal. Restore never stores (decision 11).
10. **Progress** (SP §4.1, §4.4). `CheckCounter { done: AtomicU32, total: AtomicU32 }` lives in `Active` for a running proposal; `verify::planned(&RepoProfile) -> u32` (pure) sets `total` before verification, and `Steps` adds one to `done` after each command it runs (`run_as`, `capture`). `ProfileStatus.checking` and the queued goals' `SetupState::Checking { progress }` read it (`done.min(total)`). The snapshot moves when it does: `ProfileService::snapshot_generation()` is `ready_generation` plus the sum of the running counters' `done`, and `proposals_moved` compares that.
11. **Restart** (SP §4.1). `restore_repo` loads each repository's queue into `Table.queued`. `spawn`, after today's staleness checks, drains every repository whose profile is stored (it was stored after the goal was queued and before the drain finished), and drops a queued goal whose `dir` no longer exists (`the repository is gone`). Nothing at restore stores a proposal.

### Goal start (SP §4.1)

12. **`goal_ready` no longer refuses an absent profile.** It returns `Err(GoalNotReady::NoProfile { pre, proposal })`, and `start_goal` calls `queue_goal_start`:
    - no proposal, or a `Failed` one: `start_detection(&pre, ProposalOrigin::Goal, trust_project, unconfined_checks)` — the explicit detection, **whatever `[orchestrator.onboarding] auto` says** **(R)**: SP says "as `profile detect` would", and the user asked for the goal; `auto` keeps governing only the stale re-detection. Its synchronous refusals (detection cannot be confined, `settings_refusal`) refuse the goal with that text and queue nothing **(R)**: a set-up that cannot start would only fail later.
    - `Preparing`, `Scouting`, `Verifying`: queue.
    - `Ready`: with `yes`, decision 9; without, queue (the review alert is already up).
    The reply is `RunReply::Queued { goal_id, project, message, request_id }` (exact messages: Interfaces "Exact user-visible text").
13. **A continued goal** (`chain_goal.rs`, `--continue`) with no stored profile keeps a refusal **(R)**: `this repository has no stored profile any more; start a new goal (anthrex run start --goal) to set it up`. SP covers starting a goal, and a chain's next goal reuses a running orchestrator that cannot wait in a queue.
14. **Gone:** `DETECTION_STARTED`, `DETECT_FIRST`, `PROPOSAL_READY`, `detection_running`, `no_profile`. Every test that pinned them is rewritten (Implementation notes lists each).

### Row edits (SP §4.3, §5)

15. **One mechanism for both targets.** `ProposalRecord.edit: Option<RowEdit { key, value, state }>` is the row edit, `RowEditState::Verifying` or `Failed { reason, tail, secs }`.
    - **On the stored profile** (`on_proposal: false`): as today, the edit becomes an `Edit`-origin proposal; it now also carries `edit`. With a command key (`apply_edit`'s `reverify`), verification runs (`verify_in_background`); at `Ready`, when nothing was dropped and the request had `yes`, it is stored (today's `may_auto_confirm`) and the record deleted; otherwise `edit.state` becomes `Failed` (decision 17) and the record stays `Ready`. A non-command key with `yes` is stored at once, as today.
    - **On a review proposal** (`on_proposal: true`): the proposal must be `Ready` with no row edit verifying. `apply_edit` runs on the proposal's `profile` (the verified one); a non-command key is written into `record.profile` at once. A command key sets `edit = Verifying` and registers a job (`register`), whose verification runs on the edited profile; on ✓ `record.profile` and `record.verification` become the edited ones and `edit` is cleared; on ✗ `record.profile` is unchanged and `edit.state` is `Failed`. The proposal stays `Ready` throughout and still needs **Use this**. `yes` has no meaning here.
16. **The TUI always sends `yes: true`** (SP §4.3: "✓: the edit is saved at once"). The CLI's `profile edit` keeps its meaning: without `--yes` the edit is a proposal to confirm, with `--yes` it is stored if verification passes (SP §4.3).
17. **✗** is: the edited key's check failed or timed out (SP §5: a timeout counts as ✗), or verification dropped any other command, or verification itself failed (`Stop::Failed`). `reason` is the dropped entry's reason for the key, else `another command stopped passing: <key>` for the first other dropped key, else the verification's failure; `tail` the key's `CommandCheck.tail` (empty when none); `secs` its time.
18. **Save anyway** (`s`; `--anyway`) is `Edit { anyway: true, yes: true, … }`. When the repository's record has a `Failed` row edit of the same key and value, the edit is applied without verifying again: on the stored profile, `record.proposed` (the edited profile as typed, nothing dropped) is stored with `record.verification` (its ✗ kept); on a proposal, the value is written into `record.profile` and the key's ✗ check into `record.verification`. Otherwise (the CLI's first `--anyway`), verification runs once and the result is applied whatever it found. `--anyway` implies `--yes`.
19. **Revert** (`r`) is `ProfileRequest::RevertEdit { dir }` **(R: SP names no message for it)**. A `Failed` row edit on the stored profile deletes its `Edit`-origin proposal (the stored profile is untouched); on a proposal it clears `edit`. Refused with `the edit of <key> is still being checked; wait for it` while `Verifying`, and `no failed edit to revert for <dir>` without one.
20. **During a live run** (SP §5): every edit (both targets, `anyway` too) and `RevertEdit` on the stored profile is refused with exactly `finish or cancel the run in this repo to change its profile` (replacing `service_requests.rs::live_run`'s text). An edit of a review proposal changes no run's profile, but SP says "edits during a live run … stay refused", so it is refused too.
21. **Whole verification** (SP §4.3: "today's `REVERIFY_KEYS` path"). A command row's check verifies the whole edited profile, as `verify_in_background` does today; only the edited key decides ✓ or ✗ under decision 17.
22. **Not an alert.** `note_proposal` lists only review proposals (`origin` not `Edit`) as ready: a failed row edit on the stored profile is shown on its row, never as "review how anthrex will work here".

### The plain words (SP §4.4)

23. **One status line**, computed by `tui::profile_words::status_line(&ProfileStatus, now)` for both the screen and `anthrex profile status`; the first rule that matches wins:
    1. `unparseable` → `Can't read the profile file — ⏎ shows it`;
    2. a review proposal in progress: a stored profile with `stale` → `Out of date — <files> changed · re-checking`; else `Preparing`/`Scouting` → `Setting up… reading the repo`, `Verifying` → `Setting up… checking commands (<done>/<total>)` (`Setting up… checking commands` while `checking` is `None`);
    3. a review proposal `Ready`: a stored profile with `stale` → `Out of date — <files> changed · review the changes`; else `Needs review — anthrex has a proposal`;
    4. a stored profile: `stale` → `Out of date — <files> changed · press d to check again` **(R: a ninth line; SP's eight leave a stale profile with no re-detection running — `onboarding.auto` off, or one failed within the hour — without a line)**; else `Ready · verified <age> ago`;
    5. none → `Not set up — press d to set up` (a failed set-up's reason is the screen's error row, `setting up failed: <reason>`).

    `<files>` is the first stale path, then ` and <n> more`. `<age>` is `profile_words::age(now - verified_at)`: `<n>s`, `<n>m`, `<n>h`, `1 day`, `<n> days`. `verified_at` is `ProfileStatus.verified_at` **(R)**: the stored meta's `verification.at`, else `confirmed_at` (an edit-only profile has no verification record). The TUI draws the line through `theme::fold` (ASCII: `—` `-`, `…` `...`, `·` `-`, `⏎` `enter`).
24. **Sections and labels** (`profile_view::SECTIONS`, replacing `GROUPS`): Interfaces "Sections, labels and hints", every `EDIT_KEYS` entry but `env.<NAME>` exactly once (`sections_cover_every_key_once`). SP's Advanced list is followed; two rulings place what it leaves out **(R)**: `languages`, `modules`, `manifests`, `conventions` under a sub-head `repo details`, and `delivery.remote` under `delivery remote` (SP's Delivery row is `delivery.mode` alone).
25. **Hints** name only real placeholders **(R)**: SP's example hint says `{crate} and {test} are filled in`; no command fills `{crate}` (the profile's placeholders are `{test}`, `{module}`, `{modules}`, `{worktree}`), so `single_test`'s hint is `how anthrex runs one test; {test} is filled in`.
26. **Delivery's text** **(R)**: SP's mock reads `pull request to main`; the profile holds no base branch (a run's base is chosen when it starts), so `Pr` reads `pull request · remote <remote>` and `Local` (or no `[delivery]`) `merge here, no pull request`.

### The screen and the card (SP §4.2, §4.4)

27. **One page.** `ProfileTab`, `ProfileScreen.{tab, proposed, store_on_pass}`, `ProfilePage::Confirm`, the `s` key and its line, `c`, `p` and Tab are removed. The screen shows **the card** while the status has a review proposal `Ready` (`ProfileScreen::showing_card`), else **the profile**: the stored profile's rows, or, with none, the status line alone and `d set up`.
28. **The card** (SP §4.2). With no stored profile, the **fresh card**: title `anthrex learned how to work in this repo`, then the three main sections' rows that have a value, each with its check cell (`✓ 12s`, `✗ 3m10s`, from `profile_words::took`), one `couldn't verify: <label> (<command>) — <reason>` line per dropped command, and Advanced folded (`a` opens it). With a stored profile, the **changes card** **(R: SP gives the out-of-date card no title; a user's own `d` on a stored profile gives the same card, since the stored profile stays in use until **Use this** either way)**: title `anthrex found changes in how to work in this repo`, only the rows whose value differs (`Row.mark`), each `<old> → <new>` (`—` for none), whatever their section, nothing folded. SP's mock draws `source` and `tests` on one line; the card has one row per key **(R)**, because `e` edits the selected row.
29. **Keys.** The card: `⏎` **Use this** (`Confirm { dir, shown: Some(<the proposal's Shown.toml>) }`, so only what was shown is stored, as today), `e` edit the row (on the proposal), `u` unset it, `a` Advanced, `o` the row's output, `x` discard, `esc` later (leaves the screen; the proposal, its alert and the queue stay). The profile: `j`/`k` move, `⏎` open (the row's detail page; on `Advanced ▸` it toggles; with an unreadable profile, the raw file text), `e` edit, `u` unset, `a` Advanced, `d` detect again (`d set up` with no stored profile), `o` output, `x` discard proposal (only while a review proposal exists, SP §4.4), `esc` back; with a ✗ row selected, `s` save anyway and `r` revert. Hints, in that order, in the status bar as today (milestone 9.0.6 decision 6), dropped from the right as they do not fit.
30. **Pages.** The detect page's two toggles read **Trust this repo's agent settings** (`let agents use the settings files this repo tracks, like .claude/ and .mcp.json`) and **Run checks outside the sandbox** (`only needed on systems where anthrex can't confine commands`), title `set up` or `detect again`, `y` starts. The discard page: `the proposal for <dir> is deleted; a running scout or verification stops`, plus `; <n> queued goal(s) are dropped` when there are any, `y` discards, destructive. The raw-text page (`ProfilePage::RawText { text, scroll }`, today's `Confirm` page's scrolling and hard wrap) shows `ProfileStatus.unreadable_text` exactly, sanitised (`multi_line`). The row page (`ProfilePage::Row { key }`): the label, the key dimmed, the value (a list one item per line), the hint, the check line and, after a ✗, its output. The editor and the unset page stay; the editor's `from_proposal` note goes.
31. **A row's cell** on the profile: `✓` / `✗` from its check, `checking…` (`Role::Working`) while its row edit verifies, `✗` with the hint line replaced by `couldn't verify: <reason> · o output · s save anyway · r revert` after a ✗; on ✓ the screen's message row says `saved <label>`.
32. **The unreadable profile's text** comes from `ProfileStatus.unreadable_text` **(R: SP §4.6 does not list it, but SP §4.4's `⏎ shows it` needs the text, and `Show` refuses an unparseable profile)**: the file's text, at most `UNREADABLE_TEXT_MAX = 64 KiB` (cut at a character boundary, ending `\n… (cut at 64 KiB)`), set only with `unparseable`.

### Alerts and the goal form (SP §4.1, §4.2)

33. **The review alert** keeps `AlertKey::Proposal(project)`, priority 4; its text becomes `review how anthrex will work here` (the who is the project's name, so it reads `<repo>: review how anthrex will work here`); its detail `anthrex learned how to work in this repo; ⏎ opens the review` and, per queued goal, `waiting: <goal> (profile needs review)` (SP §4.2's "queued goals keep waiting with `profile needs review` in their alert"). Enter and `o` open the screen, which shows the card.
34. **The set-up alert** **(R)**: `AlertKey::Setup(project)`, appended to `AlertKey`, one per repository with queued goals and no ready review proposal. SP's "goal view" names no view; the Alerts box is where the TUI shows what waits on a repository, and SP §4.2/§5 already give queued goals an alert there. While setting up: priority **5** (new, the lowest; glyph `Glyph::Checking`, style `Role::Working`), text `setting up anthrex · reading the repo` or `setting up anthrex · checking commands (2/4)`; Enter and `o` open the Profile screen. After a failure: priority 3, text `setting up failed: <first line of reason>` (SP: `setting up <repo> failed: <reason>`, the who being `<repo>`), Enter **Retry** (decision 7; the alert stays until the next snapshot), `o` **Open profile**. The detail lists `waiting: <goal>` per queued goal. Milestone 9.9's `alerts_route::route_kind` maps `AlertKey::Setup(_)` to `RouteKind::Proposal` (the user's).
35. **The goal form** on `RunReply::Queued` (its own tagged reply): the form closes, its draft is cleared, and the message is toasted (`Info`), as a started goal's is; `pending_open` is not set (there is no run yet).

### CLI (SP §4.5)

36. **`profile use`** with `confirm` kept as an alias (`#[command(alias = "confirm")]`) **(R: SP says "`profile confirm` is kept as the CLI's Use this"; the user asked for `confirm` "kept as an alias" — both hold)**; help `Use the ready proposal: store it, then start any queued goals`. Daemon texts that name `anthrex profile confirm` keep naming it (it still works); new texts name `anthrex profile use`.
37. **`profile edit --anyway`**: help `Store it once verification has run, even if a check fails (implies --yes)`.
38. **`profile status`** prints, after `profile: <project>`, the line `  <status line>`, then today's lines unchanged (`stored`, `stale`, `detection`, `verification`), then one `  waiting: <goal>` per queued goal and one `  dropped goal "<goal>": <reason>` per recent drop.
39. **`run start --goal`** on `Queued`: nothing on stdout, the message on stderr, exit 0 **(R)**: there is no run id to print, and a script reading stdout must not mistake the queue id for one.

## Tasks

Do them in this order. Each task's tests are written first and must fail before its change (AGENTS.md rule 6), except those marked **pinning**. One commit per task; a move-only split is its own commit inside its task.

**Why this order.** The wire types come first (M9.10.2), so each daemon task can be tested through `ProfileService::request` and the snapshot; the daemon's progress (M9.10.3), queue (M9.10.4), goal start (M9.10.5) and row edits (M9.10.6) come before any screen, because the screen only draws what the status says. The words (M9.10.7) come before the screen (M9.10.8–9), because both the screen and the CLI (M9.10.11) print them.

**Shared test rules.**

- Every test uses `fake-agent` only: the onboarding scout through `RunHarness::onboarding_report` / `onboarding_script` (`scout-onboarding-<n>`), triage through `RunHarness::decider`; daemon unit tests through `tests_ready.rs`'s `Rig` (its `claude_bin`/`codex_bin` point at `/nonexistent/anthrex-test/…`). No test changes program selection, and no test signals a process it did not start.

- **Timing.** This milestone adds no new wall-clock bound in Rust: end-to-end waits use `PROFILE_WAIT`, `RUN_WAIT` and `REQUEST_WAIT`, and daemon tests wait on the snapshot or the status with those bounds. The smoke stage's waits (M9.10.12) are each derived in a comment from the constants they wait on, per `docs/timing-budgets.md`, and get a row there. A fixed sleep is never the only synchronisation.
