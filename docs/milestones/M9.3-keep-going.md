The user's design rules, which bind every decision here and are never reinterpreted:

- **Only the orchestrator is an interactive PTY window.** Everything else stays headless and watch-only. A chain keeps one orchestrator window across runs; it never opens a second one for the same chain.
- **The engine stays deterministic.** Every new transition (a round, a next goal) starts from a user request or from an orchestrator tool call the engine checks. The engine never starts a round or a goal by itself.
- **Orchestrator-started work always stops at the plan gate**, whatever the run's options (KG §2.4 step 4, §3.3, §8).
- **Nothing reaches the user's branch until the user accepts**, and in `pr` mode anthrex never merges, approves or lands anything (9.2's rules, unchanged).
- **Headless agents load only the user's own settings.** Nothing in this milestone changes an agent's settings or tools beyond the orchestrator's MCP tool list.
- **User text is data.** A round's request and a next goal are cleaned by `safe_text::multi_line`, capped at 16,384 characters, and reach the orchestrator only fenced (KG §8).
- **The client's state stays pure** (AGENTS.md rule 5). The goal draft, the cut buffer and the editor's position are client state only; nothing is written to disk.
- **No blocking work under a lock** (AGENTS.md rules 2 and 10). Renaming and rebinding the orchestrator's window, reading history lines for a fresh session and every git call run off the engine lock and the manager lock, on `spawn_blocking` with a timeout.
- **Tests use `fake-agent` only**, every `*_BIN` pinned (including `ANTHREX_GH_BIN`), temp dirs and deadline loops; the `pr`-mode round runs on `FakeHost` through `PrRig`.

## Goal

The "start a goal" dialog becomes a large, nano-like editor: `min(cols − 4, 120)` wide, `rows − 2` high, with nano's keys, a cut buffer, a position row and a per-project draft kept in client state; Ctrl-S starts the goal. A complete run (or a settled `pr` run) can be iterated in the same run: the user (from the run's action menu or `anthrex run iterate`) or the orchestrator (with `edit_plan`'s `iterate`, checked by the engine) adds a round; the engine records it, wakes the orchestrator with the fenced request, accepts only new tasks in new stages after the existing ones, stops at the plan gate (always, for an orchestrator-started round), runs the round from the run's current head, and returns the run to `complete` (or delivering) with every round intact; one accept or discard covers every round. When a run is accepted or discarded, its orchestrator stays as the project's idle orchestrator, the head of a chain `o-<h4>`; the user (from the goal dialog's orchestrator row or `anthrex run start --goal … --continue <run>`) or the orchestrator (with the new `start_goal` tool) starts a new run on the same session, one goal at a time. Tool calls from a chained orchestrator resolve to the chain's current run; an idle orchestrator may only read its last run and call `start_goal`. Protocol 15 carries the new requests, fields and the snapshot's idle orchestrators.

3. **Words.** A **round** is one request a run works on: round 1 is the goal it started with, and each iterate adds one. A round is **settled** when KG §2.3 allows a new one (decision 9). A chain is **active** while its current run is not terminal, **idle** once that run is accepted or discarded, and **ended** once its session is gone (the window closed or exited, or the daemon restarted while it was idle). `<h4>` is `Run::short()` (`model.rs:388`), the run id's last four characters.

### The editor (KG §1)

4. **One widget.** The editor is `TextArea` (`tui/src/text_area.rs:16`) with two new fields, `cut: String` and `cutting: bool`, and new methods in `tui/src/text_area_editor.rs`: `on_editor_key(key, width, page) -> EditorKey`, `position(&self) -> (usize, usize)` (1-based logical line and column in grapheme clusters), `at_cap(&self) -> bool`. `TextArea::on_key_in` (`:130`) and every existing caller (the task edit form's brief, the action forms, the profile pages) are unchanged: the editor's keys apply only where a caller asks for them (KG §1.5: the goal, iterate and next-goal dialogs).
5. **Keys** (KG §1.2, exactly):
   - a character inserts it; Enter and Ctrl-J insert `\n`; Backspace and Delete delete before and after the cursor;
   - ← → move by grapheme; ↑ ↓ move by drawn row through `text_area_rows::move_row`, and ↑ on the first drawn row and ↓ on the last stay put (today's goal form moves the focus there instead; that changes, decision 7);
   - Home, End, Ctrl-A, Ctrl-E: start and end of the logical line; PgUp, PgDn: by `page = text rows − 1` drawn rows; Ctrl-Home, Ctrl-End: start and end of the text;
   - Ctrl-K cuts the current logical line, its `\n` included, into `cut`; a Ctrl-K right after a Ctrl-K appends to `cut`, any other key first sets `cutting = false` and the next Ctrl-K replaces it;
   - Ctrl-U inserts `cut` at the cursor, through the same capped insert;
   - a bracketed paste keeps its line breaks and drops control characters, as `TextArea::on_paste` does today (`TextArea::clean`, `:25`).
6. **The cap.** The cap stays 16,384 characters (`run_edit::TEXT_MAX_CHARS`). An insert or paste past it stops at the cap and sets `at_cap`, which shows KG §1.3's text in the position row until the next key that inserts nothing past the cap. Wrapping is for drawing only; the text sent is exactly the text typed.
7. **The goal dialog** (`tui/src/run_goal.rs`, `tui/src/ui/goal_editor.rs`).
   - **Size.** At least 60 columns and 16 rows: width `min(cols − 4, 120)`, height `rows − 2`, centred, leaving the status bar and one margin row. The interior is `height − 2` rows; the text area takes `interior − options − 3` rows, the three being one blank row above the options, the position row and the footer, where `options` is the option rows shown (seven, plus the custom-model row when `Custom` is chosen). At 80×24 that is 10 text rows, at 120×40 26 (KG §1.1).
   - **Compact fallback.** Below 60 columns or 16 rows the dialog is drawn exactly as today (`ui/run_goal.rs`: `kit::dialog_area`, `GOAL_ROWS = 4`), with the same editor keys, and the status bar's dialog body reads KG §1.1's `widen the terminal for the editor` (`ui/statusbar_modes.rs::modal_bar`, `:42`), computed from the terminal size the frame is drawn at. Pure.

### Rounds (KG §2)

9. **When a run can be iterated** (KG §2.3). `engine/actions/rules.rs` gains `iterate(run: &Run) -> Option<String>`, the one source of every refusal text below, called by the request handler, by `edit_plan`'s iterate and by the action menu's `check`, so the three never drift (9.0.6 decision 8). In order:
   1. a run being finished: `rules.rs`'s existing `being_finished` text;
   2. a run with no orchestrator record (`run.orch.orchestrator.is_none()`: a plan-file run, a fast-path run never promoted): `run <h4> has no orchestrator; start a new goal for more work` (brief text);
   3. `ROUNDS_MAX` reached (`run.rounds.len() == 20`): KG §2.1's text;
   4. `Halted`: KG §2.3's `run <h4> is halted; resume or cancel it first`;
   5. `Accepted`, `Discarded`, `Failed`: `run <h4> is <state label>; start a new goal for more work` (brief text);
   6. local mode: `Complete` is settled;
   7. `pr` mode: `Complete` and not `cancelled` is settled (every PR merged or closed, `delivery::may_complete`); `Complete` and `cancelled` is refused with `run <h4> was cancelled; start a new goal for more work` (brief text, defect D7); `Running` is settled when `delivery::pr(run)`, `run.delivery.delivering(stage_count(run))`, every task is finished, the merge queue is empty, `propagate_due` and `base_sync_due` are empty, and no stage has `held` set (KG §2.3's "nothing in progress");
   8. any other state (and a `Running` `pr` run that is not settled): `run <h4> is <state label>; iterate it when it completes` (KG §2.3's pattern).
10. **Starting a round** (KG §2.2, §2.4 steps 1–2). `RunRequest::Iterate { run, goal }` reaches the engine as `EventKind::Iterate { reply, run_id, goal }`; `edit_plan`'s `iterate` reaches it as `PlanEdit::Iterate { goal }` inside `OrchCall::EditPlan` (decision 30). Both call `goal_rounds::iterate(run, goal, origin, now, fx) -> Result<String, String>`:
    1. a blank request is refused with `triage::blank_goal`'s text (`run/triage.rs:312`); a request over 16,384 characters with `the request is longer than its 16,384-character limit` (brief text); then `rules::iterate`;
    2. the current round, when it has no outcome yet (round 1 of every run that completed), ends as `Completed` with its history line (decision 17);
    3. the request is stored as `safe_text::multi_line(goal)` in a new `Round { n: last + 1, origin, started_at: now, first_stage: highest planned stage + 1, windows_before: run.windows_created, scouts_before: <run scouts so far>, .. }`;
    4. a `Single` run is widened (decision 13);
    5. the run moves to `Planning` (from `Complete`, or from `Running` in `pr` mode); `run.cancelled` and `run.finish_edit` are cleared (decision 16);
    6. `RunOrch.request_wake` is set to the round wake (Interfaces "Messages"), the request fenced by `quote::fence` (D1); a dormant orchestrator (`!o.live`, after a restart) is relaunched with `orch_window::relaunch` (`orch_window.rs:160`);
    7. the reply is `Done("run <h4> round <n> started; its orchestrator plans it")` (brief text); the orchestrator's own call is answered as an accepted `edit_plan`.
11. **The round wake is delivered whole.** A note is cut at `WAKE_MAX_BYTES` (2 KiB) and joined with others, so the round wake (and the next-goal wake, decision 23) cannot be a note (D3). `RunOrch.request_wake: Option<String>` holds it; `wake::effect` (`engine/wake.rs:96`) emits `Effect::WakeOrchestrator` whenever `request_wake` is set and the window is live, with `text = request_wake`, followed by a blank line and `wake_text(notes)` when notes are pending; `OrchEvent::OrchestratorWoken` clears it with the notes it covered. The request lives on the run (`RunOrch.request_wake`) until an `OrchestratorWoken` for that request: `Effect::WakeOrchestrator` and `OrchEvent::OrchestratorWoken` carry a daemon-internal `request: Option<u32>`, the round whose request it is (not a wire field), and the engine clears `request_wake` only on `OrchestratorWoken { request: Some(n) }` for its own round n (D13, ruled; amended in task M9.3.4a's fix round 1). The driver (`driver/wake.rs`) still waits for a quiet, idle window, and takes the request path: its `Pending` keeps `request`; `encode_paste` sends a request wake whole, with its own cap (the 16,384-character request, fenced, plus the fixed text and the notes), in bounded chunks if the PTY needs them, never cut at `WAKE_MAX_BYTES`; `Seen` gains `request: Option<u32>` (`run.round()` while `request_wake` is set), and `keep_live` drops a judged request wake only once the engine no longer holds that round's request (the second guard notes have), so it is never pasted twice; `Wakes::read` and `deliver`'s post-paste removal never drop a request wake for want of notes. When the orchestrator's window is not live the driver may drop its pending copy, and the engine emits the request again once the window is live: "never dropped until delivered" holds for the run, not for the driver's copy.
12. **The plan gate per round** (KG §2.4 steps 4–6).
    - `submit_plan` (`engine/orch.rs:441`) skips the gate only when `run.orch.yes` **and** the current round's origin is `User`; a round the orchestrator started always goes to `AwaitingApproval`.
    - `requests::approve` (`:143`) on a round ≥ 2 does not call `stages::fix_layout` (the layout was widened when the round started) and leaves `approved_at` as round 1 set it.
    - `requests::reject` (`:175`) on a round ≥ 2 (in `Planning`, `AwaitingApproval`, or paused from `Planning`) does not discard the run: every task of the round is cancelled (`complete::cancel_task`, reason `run reject (round <n>)`), the round ends `Rejected`, `request_wake` is cleared, sub-planners and run scouts of the round are halted, and the run returns to `Complete` (local) or `Running` (`pr`), with no summary wake. Reply: `run <h4> round <n> rejected; the earlier rounds are unchanged` (brief text). Round 1's reject is unchanged (it discards the run).
13. **New stages only** (KG §2.4 steps 3, 7; §2.5). A round's tasks go in stages `first_stage..`; `Task.round` and `StageRecord.round` record the round.
    - **Widening.** At a round's start a `Single`-layout run becomes `Multi` (`goal_rounds::widen`): `stage_layout = Multi` and `run.stages` cleared, so `create_pass` (`stages.rs:201`) creates `anthrex/<run>/stage-1` from `run_head` on the next running pass, then the round's first stage from it (9.1 decision 48, unchanged). Delivery records are kept: they live in `run.delivery.stages`, not `run.stages`. `single_layout_rule` (`validate_stages.rs:140`) therefore no longer applies. Stage 1's tier-3 record is lost with the old record, so a tiered local run may run tier 3 on stage 1 once more at completion (Risks).
    - `fix_layout` (`stages.rs:129`) runs for round 1 only.
    - **A dependency on an earlier round is satisfied** (KG §2.4 step 3): in `stages::ready_in_stage`, `dep_in` and `engine/schedule.rs`'s `deps_done` (`:193`) and `unfinished_deps` (`:173`), a dependency whose task has `round <` the dependent task's round counts as met, whatever its state. Every cross-task validation rule treats earlier rounds' tasks as decided; a rule that refuses a new task only because of an earlier round's task is a defect to record under "Implementation notes".
    - **Bases.** Local mode: the round's first stage is created from the top stage's head, which is `run_head` (`integration`). `pr` mode: while a lower stage's PR is open, from the top stage's head, and its PR is based on that stage's branch (9.2's `delivery::body::stacked_on`, `body.rs:60`, unchanged); when every earlier stage's PR has landed, a base fetch is made due first (9.2's `RunDelivery.base_fetch_due`) and the round's first stage is created from `RunDelivery.base_synced`, so its PR is based on the base branch (KG §2.5).
    - A round that would need a stage above `STAGES_MAX` (32) is refused by 9.1's existing `check_stage_fields` text (D6).
    - Fix tasks the engine adds (9.1's bisect and sync, 9.2's CI and review) take the round of the stage they fix.
14. **Limits per round** (KG §2.6, D5). There is no run-level budget of tool calls or minutes; the run-wide caps a long run would exhaust are `max_tasks` (`validate_graph.rs:82`), `max_windows` (`engine/dispatch.rs:409`) and `max_scouts` (`engine/run_scouts.rs:43`). Each counts from the current round's start: `max_tasks` counts tasks with `round == run.round()`, `max_windows` compares `windows_created − round.windows_before`, `max_scouts` compares the run scouts started since `round.scouts_before`. The limits are the run's frozen `RunLimits`. Per-task budgets are unchanged; the run's totals are the sums of its tasks', as today.
15. **Earlier rounds are read-only** (KG §2.4 step 3). `validate_rounds::earlier_round(run, edits, source) -> Option<String>`, called first in `edits::apply_edits` (`:60`), refuses an `add_task` (or a `split_task` child) whose stage is below the current round's `first_stage`, and any edit naming a task of an earlier round, with KG §2.4's `stage <s> belongs to round <r>, which is done; put new work in a new stage` (`<s>` the stage named or the task's stage, `<r>` that stage's round). Engine-made fix tasks do not go through edits and are unaffected.
16. **Cancel during a round** (KG §2.4). `run cancel` on a run whose current round is ≥ 2 cancels only that round (`goal_rounds_end::cancel_round`): every unfinished task of the round is cancelled as `complete::cancel` cancels tasks today, the round's sub-planners and run scouts are halted, `run.finish_edit` is set so nothing new starts (`orch::ending`'s refusal applies to the orchestrator's edits), and the round's outcome is set to `Cancelled`. Neither `run.cancelled` nor 9.2's `delivery.watching = false` and `land::cancelled` apply, so earlier rounds' PRs stay watched. Reply: `run <h4> round <n> cancelled; it ends once its sessions have ended` (brief text). A round-1 cancel is unchanged.
17. **The end of a round** (KG §2.4 step 9, §2.6). `goal_rounds_end::pass(run, now, fx)`, called once per run in `step`'s per-run loop (`engine/mod.rs`), ends the current round when it is unended and:
    - local: the run is `Complete` (M8a's completion, unchanged, including its summary wake `the run is complete; write your summary with edit_plan summary`); or
    - `pr`: every task is finished, every stage of the round has a PR or was skipped, and no merge or propagate is in flight; the pass then adds the wake note `round <n> is done; write its summary with edit_plan summary` (brief text).
    The outcome is `Cancelled` when decision 16 set it, else `Completed`; `ended_at = now`; `finish_edit` is cleared; one `HistoryLine::Round` is appended through `engine/history.rs::append` with `record_id` `<run>/round/<n>`: `tasks` the round's tasks, `merged` those merged, `calls` the sum of their `spent_total.tool_calls`, `minutes` `(ended_at − started_at) / 60`. `write_summary` (`engine/orch.rs:424`) also stores the summary on the current round. One `run` history line is still written at accept or discard (M8b, unchanged).
18. **Loading old runs** (KG §2.1). `Run.rounds` defaults to empty; `goal_rounds::ensure_first(run)` pushes round 1 (`goal` = `run.goal`, origin `User`, `started_at = created_at`, `first_stage = 1`, no outcome) when it is empty. It is called from `requests::start` and from `restore::prepare` (`restore.rs:97`) beside `stages::ensure_first`. `Task.round` and `StageRecord.round` default to 1.

### Chains (KG §3)

19. **The chain table is derived from runs.** `Run.chain: Option<String>` is the only new persisted chain state. `EngineState.chains: BTreeMap<String, Chain>` is built by `chain::rebuild(&state.runs)` at `EventKind::Restore` and kept by `engine/chains.rs` as runs start and end; no new file is written (KG §3.1's "stored in the daemon's state next to the runs"). `Chain` is KG's struct plus `ended: bool` (D8).
    - **Creation.** `requests::start` gives every run that gets an orchestrator (a planned run, and a promoted one in `promote.rs`) `chain = Some(chain_id(run))` (`o-<h4>`) unless it continues one, and inserts the chain `Active`.
    - **Idle.** When a chained run becomes `Accepted` or `Discarded`, its chain becomes `Idle`. The project keeps one idle orchestrator: any other idle chain of the same project is dropped from the table (its window stays as a plain window, as today); an active chain of the same project is untouched (KG §3.1).
    - **Failed.** When a chained run fails, its chain is dropped and its window released as today (KG §3.1).
    - **Window.** The idle orchestrator's window is released exactly as a finished run's is today (`orch_window::ended`, `release_ended_orchestrators`), so the user can close it with `C-b x` and the manager's orchestrator refusal (`server/headless_guard.rs:20`) no longer applies.
    - **Ending** (KG §3.2). `driver/chain_ops.rs::idle_windows` runs in `check_orchestrators` (`driver/wake.rs:267`) for every idle, unended chain: a window gone from the manager's list, or `Exited` for `EXIT_CONFIRM` (1 s), sends `OrchEvent::ChainWindowGone { chain, window_id }`, which sets `ended = true`. At `Restore`, every idle chain is `ended` (KG §3.6).
20. **Which run a tool call reaches** (KG §3.4). `McpTarget.chain` is set by `orchestrator_role` (`orch/launch.rs:124`) from `run.chain`; `mcp_args` passes `--chain <id>`; `anthrex mcp` puts it in `McpOptions.chain` and `forward` in `ToolCall.chain`. The driver resolves first, in `driver/orch.rs::orch_tool_within` and `read`, before any other check, with the pure `chain::resolve(&chains, &call) -> Result<Option<String>, String>`, taking the engine lock only to look up:
    - no `chain`, or a role other than `Orchestrator`: `Ok(None)`, the call is unchanged;
    - the chain's runs contain `call.run_id`: `Ok(Some(current run id))`, and `call.run_id` is replaced (resolved forward);
    - otherwise: `Err` with `this window is the orchestrator of <chain>; run <id> is not one of its runs` (brief text), never redirected;
    - an unknown chain: `Err` with the same text.
    After resolution, decision 15's caller check (`caller`, `driver/orch.rs:59`) applies unchanged against the current run, whose `OrchestratorRecord.window_id` is the chain's window.
21. **Idle tool limits** (KG §3.2). After resolution, `chain::idle_refusal(chain, tool) -> Option<String>`: while the chain is idle, only `get_context`, `run_status` (both read-only, for the last run, as the driver's read path already answers in every state) and `start_goal` pass; every other tool is refused with KG §3.2's `run <h4> has ended; start a new goal with start_goal when the user gives you one`.
22. **Starting the next goal** (KG §3.3). `RunRequest::StartGoal { continue_from: Some(run), .. }` and the `start_goal` tool both reach `driver/chain_goal.rs::continue_goal`, which:
    1. refuses, with exact texts (Interfaces "Messages"), when `run` names no chain (`run <h4> has no orchestrator to continue; start a new goal without --continue`), is not its chain's last run (`run <h4> is not the last run of <chain>; continue from run <last h4>`), the chain is active (KG §3.5's `run <h4> is still going; finish it before starting another goal`), or `dir` resolves to a different project (`<chain> belongs to <project>; start this goal there, or with a new orchestrator`) (all brief texts but KG §3.5's);
    2. runs `start_goal`'s steps 1–2 (`adapt_goal.rs:104`: the blank-goal check, `confine::start_refusal`, `git::preflight` with its reserved-branch guard, the stored profile) and `freeze_delivery`, unchanged; **triage is skipped**: a continued goal is a planned run on its chain's orchestrator (`path = plan`, `triage = None`);
    3. builds the run through `build_delivered` with `Shape::Planned` (as `start_planned`, `adapt_goal.rs:356`), `run.chain = Some(chain)`, and `run.log`'s first line `based on <branch> at <sha7>` (KG §3.3); `Planned.triage` becomes `Option<TriageInfo>` and `make_planned` takes it (D14, ruled): a continued run has `None`, and every reader handles `None`;
    4. from the tool: `delivery` is the previous run's `RunDelivery.mode`, `trust_project` and `unconfined_checks` the previous run's, `yes = false`; from the request: its own fields, and `orchestrator` is ignored (the chain's runtime and model hold);

**Deviations and readings.**
- *The pass ends rounds after the first only.* Decision 17 says the pass ends "the current round when it is unended" once the run is `complete`, and decision 10, step 2 says an iterate ends "the current round, when it has no outcome yet (round 1 of every run that completed)". Both hold only if round 1 is not ended at completion; task M9.3.4a's `iterate_on_a_complete_run_starts_round_two` pins round 1's line at the iterate. So `pass` ends round `n ≥ 2`, and round 1 ends (with its line) when round 2 starts. A run that is never iterated writes no `round` line, which is what `run stats`' `rounds: <total> · <iterated runs>` (printed only when a round line exists) expects.
- *`end_round` keys on `ended_at`, not `outcome`.* Decision 16 sets a cancelled round's outcome while its sessions end, and decision 17 ends it later with that outcome; `goal_rounds::end_round` now ends a round whose `ended_at` is unset, keeping an outcome already set. One `round` line per round still holds: the line is written exactly when `ended_at` is set. The test fixture `goal_rounds_start::pad_rounds` gave its padded rounds an outcome but no `ended_at` (a round the model never has); it now sets `ended_at` too.
- *A defect fixed (decision 13's widening).* A widened run's stage 1 was created from `run_head` with an empty `tasks_in` (`stages::created` copied its parent's, and stage 1 has none), so round 1's merged tasks counted as undelivered (`propagate::undelivered`) and a widened run's round 2 could never complete. `created` now gives a stage with no parent every merged task, which `run_head` holds; a round-1 `Multi` run creates stage 1 before any merge, so it is unchanged there. `engine/stages.rs` is outside this task's file list; `the_end_of_a_round_writes_one_round_line` pins it.
- *Round reject.* Besides decision 12's list, it clears `paused_from`, sets the orchestrator's `plan_submitted` back to true (the earlier rounds' plan was submitted; `rules::promoted_unsubmitted` would otherwise treat a `pr` run back in `running` as unsubmitted), logs `round <n> rejected by the user`, and adds the wake note `the user rejected round <n>; the earlier rounds are unchanged` (invented; no summary is asked for). The reasons of the sub-planners and run scouts it halts are `the round was rejected` and, for a cancel, `the round was cancelled` (invented, `goal_rounds_end::{ROUND_REJECTED, ROUND_CANCELLED}`).
- *Round cancel* does what `complete::cancel` does to the run besides its tasks: a paused run runs again and `restored` is cleared; a task whose merge is in flight is deferred, and the reply gains `complete::deferred_note` for it, as the run cancel's does. It logs `round <n> cancelled by the user`.
- *`max_tasks`* is read as the highest `round` among the tasks (the brief's second option), so `validate_tasks_with`'s signature and its three callers are unchanged. An engine fix task of an earlier round's stage, added while a later round runs, therefore counts toward neither round.
