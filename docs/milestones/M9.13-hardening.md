> **For agentic workers:** REQUIRED SUB-SKILL: use superpowers:subagent-driven-development (the user's standing choice) to implement this brief task by task, TDD. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal.** A run can no longer change what judges it or what runs after it without the user seeing it. CI, git-hook, cargo and toolchain files are protected like agent configuration. The scripts the gate itself runs are pinned to the base commit. The orchestrator cannot retry a task forever. Once the orchestrator has read text that came from outside the run (a pull-request comment, or a fix task's output about one), its `override` and `accept_red` become a question to the user and its `approve_hold` is refused.

**Architecture.** Four independent guards, each daemon-side and each in a pure engine function where it can be. (A) The built-in protected list grows a second class, and the two paths that today skip decision 56 (the orchestrator's `override`, and holds the orchestrator approves) learn to refuse it. (B) At run start the daemon reads which tracked files the profile's commands name (`Run.gate_files`), protects them, and before every gate command hashes them in the checkout; a mismatch halts the run for the user. (C) `TaskOrch.orch_retries` counts the orchestrator's retries; past two, the task's next block is the user's. (D) The driver tells the engine when an orchestrator read carried untrusted text (`OrchEvent::UntrustedRead`), before it answers; the engine keeps it in `RunOrch.untrusted` for the rest of the run and its chain, and `orch_ops::intercept` downgrades the risky ops. Only (D) changes the wire: protocol 22.

**Tech stack.** Rust 2024 workspace; `serde`/`rmp-serde` wire types; `rmcp` for the MCP schemas; `ratatui` for the inspector row; `fake-agent` and `FakeHost` for every end-to-end test.

**Spec.** `docs/superpowers/specs/2026-10-10-nucleos-adoptions-design.md` §2. Read it whole before task M9.13.2.

**User decisions** (2026-10-10, binding; they override NA §2's first draft where they differ, and are never reinterpreted):

- **U1** A task may change a gate file only when its `owns` names it literally; the user approves that grant with the plan. A granted gate file is then not pinned for that run. (This replaces the draft's "gate files take no owns grant".)
- **U2** Taint is sticky for the orchestrator's session and its run. There is no command to clear it.
- **U3** `package.json` is not pinned by `npm test` / `yarn test` (no implicit file for `npm`, `yarn`, `pnpm`).
- **U4** A5 and A6 (the orchestrator's `override`, mid-run edits and `approve_hold` on protected paths go to the user) are in scope.
- **Tests never reach a real agent.** Every fixture pins `ANTHREX_CLAUDE_BIN`, `ANTHREX_CODEX_BIN` and `ANTHREX_DECIDER_BIN` to `fake-agent` or a nonexistent path; no test changes program selection.
- **No new kill or signal code.** Nothing in this milestone writes `kill`, `signal_group`, `SIGKILL`, `SIGTERM` or `SIGHUP`.

**Integration-test paths.** Since milestone 9.12 the daemon's and the CLI's integration tests are one binary per crate (`autotests = false`). This brief writes their paths as `daemon/tests/it/<f>.rs` and `cli/tests/it/<f>.rs`; a new one needs a `mod <f>;` line in `tests/it/main.rs`; only a file that mutates the process environment gets its own `[[test]]` entry. `source_rules::every_integration_test_file_is_compiled` fails on a file no target compiles.

## Goal

When this milestone is done:

- A worker that edits `.github/workflows/ci.yml`, a git hook, `.cargo/config.toml` or `rust-toolchain.toml` without its `owns` naming that file exactly is bounced at `task_done` with a line that says why.
- The orchestrator cannot `override` a task whose branch changes a protected file it was not granted, and cannot `approve_hold` a hold that grants one; both go to the user.
- A run whose task rewrites `scripts/check.sh` (named by `check`) halts before the rewritten script ever runs, and only the user can resume it.
- After two orchestrator retries of a task, its next block is the user's.
- After the orchestrator reads a pull-request comment, its `override` and `accept_red` are asked of the user, and `anthrex run status` and the run inspector say so.

4. **A literal grant is noted** (NA §2 A4). `validate::protected_notes` (`validate.rs:521`), for a tracked protected file `owns` names literally, pushes `owns names protected {path}; the user approves this grant with the plan` where it skips today (`:532-534`). The covering note is unchanged. Every caller (`build_run`, `Batch::resolve`, `engine/fixes.rs:98`) gets it.
5. **The orchestrator's override of a protected change is refused** (NA §2 A5).
   - `OpKind::CountCommits` gains `#[serde(default)] owns: Vec<String>` and `#[serde(default)] protected: Vec<String>`; `OpResult::Commits` gains `#[serde(default)] protected: Vec<String>`. `override_on` fills them from the task's `owns` and `run.profile.protected`; the turn-end fallback (`fallback.rs:71`) leaves them empty. The executor, when `protected` is non-empty, lists the changed paths of `<run_head>...<head>` that `ProtectedMatcher::guards_change` matches and `names_literally(owns, _)` does not, one more bounded `git diff` behind the same `service.write`. **(R)** One rule, two callers (pre-flight ruling C16): the protected split becomes the pure `globs::split_protected(paths, owns, &ProtectedMatcher) -> Vec<String>`, which `verify_done_spilling` applies to the diff it already has (no second diff there), and `git::done::protected_changes` is that diff plus `split_protected`, used by the count only.
   - In `override_counted` (`gates.rs:461`), for `Actor::Orchestrator` with non-empty `protected`: the result is `Err("task {id} changes protected {paths}; only the user can merge it unchecked")` (`paths` joined by `, `), the task's `block.user_only` becomes `true`, and `override_landed` records the refusal.
   - For `Actor::User` with non-empty `protected`: the override goes through, its reply gains `; it changes protected {paths}`, and the run log gains `the user overrode {id}, which changes protected {paths}`. **(R)** For each of those paths that is still pinned (`gate_pins::pinned(run)`, decision 11), the reply then gains `; {path} stays pinned until a task's owns names it (run edit)`: the override lets the change through `done`, but the next gate command will refuse the rewritten script and halt, and the way out is a `run edit` that amends a task's `owns` to name the file (pre-flight ruling C25). This clause lands in M9.13.6, with `gate_pins`.
   - A task in `review` needs no count (`gates.rs:395-397`): its claimed head already passed decision 56 at `done`, so nothing is checked again there. A pinning test says so.
6. **Mid-run grants go to the user** (NA §2 A6). A protected path an `owns` entry names literally is a *grant* (`protected_grants::literal(owns, protected) -> Vec<String>`: each literal entry, without `*`, `?` or `[`, that `ProtectedMatcher::new(protected)` matches, trailing `/` trimmed). **(R)** That filter already exists in `triage::owned_protected`; both call one pure `globs::literal_protected(owns, &ProtectedMatcher) -> Vec<String>` (pre-flight ruling C16).
   - **An orchestrator or sub-planner batch past the plan gate** (`gate_holds::past_gate(run)`) that adds a task with a grant, or amends a task so its grants grow, is refused with `owns names protected {p}; ask the user (ask_user)` (first new grant), **unless** that task ends the batch under a hold that is not `Approved`. **(R)** Before the gate the check does not apply: the draft's grants are approved with the plan (U1), and `gate_holds::assign` gives a pre-gate task no hold, so without this the orchestrator's own initial plan could never carry a grant (pre-flight ruling C4; NA §2 A6 says "after the plan gate"). A user's `run edit` is not checked.
   - **A hold whose tasks carry a grant** is the user's: the orchestrator's `approve_hold` is refused with `hold {id} grants protected {paths}; only the user can approve it`. This covers the engine's own review-fix holds too: a comment on an unowned `.github/workflows/ci.yml` gives a fix task that owns it exactly (`review_fix.rs:30`) under a `Fix` hold (`:116`), which today the orchestrator may approve. Computed when asked, never stored.
   - **(R)** NA §2 places the refusal in `edits.rs::Batch::resolve` (`:267`). It cannot be decided there: a batch's holds are assigned after `apply_edits` returns (`engine/orch.rs:438-441`, `planners.rs:520`). The check is one pure function, `engine/protected_grants.rs::unheld(edited, before, added) -> Option<String>` (it returns `None` unless `gate_holds::past_gate(edited)`), called right after hold assignment in both places; on `Some(text)` the batch is refused as any other (`record_rejected` and `refuse`), and nothing of it is kept.
7. **No new hold kind, no wire change** (NA §2 A, rejected alternatives).

### B. The gate's own scripts

8. **Gate words** (NA §2 B1). `daemon/src/run/gate_words.rs` (pure): `pub fn gate_words(profile: &Profile) -> Vec<String>` over `check`, `setup`, `single_test`, `tiers.build_check`, `tiers.module_test`, `tiers.module_tests`, `tiers.module_graph` when it is `GraphSource::Command`, and `tiers.toolchain_id`, in that order. Each command is split on whitespace and on `;`, `&`, `|`, `(`, `)`, `<`, `>`; from each word every `'` and `"` is removed, a leading `NAME=` (`[A-Za-z_][A-Za-z0-9_]*=`) is cut off (the value stays a word), and leading `./` is removed repeatedly. A word is dropped when it is empty, starts with `/` or `~`, contains any of `$ * ? [ ] { } \``, or has a `..` component. Words are kept once, first-seen order, at most `GATE_WORDS_MAX = 64`. **Implicit files**, appended when a word equals the program: `make` → `Makefile`, `makefile`, `GNUmakefile`; `just` → `justfile`; `tox` → `tox.ini`; `nox` → `noxfile.py`. Nothing for `npm`, `yarn` or `pnpm` (U3).

## Tasks

Do them in this order. Each task's tests are written first and must fail before its change (AGENTS.md rule 6), except those marked **pinning** (they pin today's behaviour). One commit per task; a move-only split is its own commit inside its task.

**Why this order.** The fact check and the wire come first, as every brief's do. A (M9.13.3–4) comes before B (M9.13.5–6) because B's gate files become protected paths and reuse A's texts and grant rules. C (M9.13.7) is independent and small. D's record and sources (M9.13.8) come before the downgrade (M9.13.9) that reads them. ## Risks and gotchas

- **Line endings and filters.** `verify` hashes the working tree's bytes. A gate script with a `.gitattributes` `eol=crlf`, `text` conversion under `core.autocrlf`, or a smudge filter differs from its blob, and every check halts. Record it under the first such report; the user's way out is to grant the file (U1) or drop the attribute. Not seen in anthrex's own repository.
- **`cd sub && ./run.sh`** resolves `run.sh` relative to `sub` and is not pinned (NA §2 B risks); the user can add it to `protected`. Over-matching is safe: only tracked blobs count.
- **`Justfile`, `.justfile`, `gmake`** are not implicit (decision 8 keeps NA §2's list); a profile using them is pinned only by what its words name.
- **Rebaseline** (`run resume --rebaseline`) does not re-read gate files; a gate script changed on the base branch then halts the run. Follow-up.
- **A base sync can bring in a gate-file change.** An upstream base commit that edits a pinned gate file halts a `pr`-mode run's base sync for the user, since the sync's gate command is refused as if the run had changed the file. Granting the file with `run edit` resumes it (the refused sync is due again, task 6 review I-1).
- **Persistence downgrade.** M9.13.4 bumps `RUN_FORMAT` to 2 (C3), so a 9.11 or 9.12 daemon leaves a 9.13 run alone (it skips a format-2 `run.json` and writes nothing in its directory). Only a binary from before 9.11, which has no format guard, can load a 9.13 `run.json` and drop `untrusted`, `orch_retries`, `gate_files`, `AskRecord.proposal`, `OverrideCount.proposal` and `CountCommits.{owns, protected}` when it saves (NA §2). CHANGELOG says so. Follow-up.
- **Redirect and `tee` targets are gate words** (C27, decision 8 is final). Splitting on `<`, `>` and `|` keeps `tee out.txt` and `> report.txt` targets as words. If such a file is tracked, it is pinned; gate commands run in the checkout (`step.dir`), so a gate command that writes it makes the next gate command refuse it and the run halts. The way out is to grant the file in a task's `owns` (U1) or not to track it. Dropping the word after `>`, `>>`, `2>` and `tee` would be the user's ruling. Recorded in the follow-ups.
- **The orchestrator's `Read` tool** can open `run.json`, which holds raw comment text; nothing taints on it (NA §2 D risks). Follow-up: a PreToolUse hook.
- **An ask replaces a pending one** (9.9 decision 15): a proposal can replace the orchestrator's own question, or be replaced by it. Logged, as today.
- **A conflicted hand-back** makes the override count's `<run_head>...<head>` include merged lower-stage paths; a protected one there is refused to the orchestrator (safe), and the user's override lists it.
- **`ProtectedMatcher` folds ASCII case**: `.GitHub/Workflows/x.yml` is protected; the grant must still name the path as git spells it.
- **`engine/orch.rs` (593)** must be split before any line is added (M9.13.4's move).

I tested on a temporary repository (with `GIT_CONFIG_GLOBAL=/dev/null GIT_CONFIG_NOSYSTEM=1`): a base commit with `scripts/check.sh` (100755), `Makefile`, a directory `test/`, a symlink `link.sh`, `tools/lint.py` and a file named `:(glob)x`. `git --no-optional-locks --literal-pathspecs ls-tree -z <base> -- scripts/check.sh test link.sh Makefile make tools/lint.py nothere` prints, without `-r`:
- `100644 blob … Makefile`
- `120000 blob … link.sh`
- `100755 blob ca916d0… scripts/check.sh`
- `040000 tree … test`
- `100644 blob … tools/lint.py`

The blob id equals `git rev-parse <base>:scripts/check.sh`. Unknown words and `make` give nothing. Entries come in tree order, not word order. Other cases:
- Two levels deep, `scripts/sub/x.sh` lists its blob.
- `:(glob)**` matches nothing under `--literal-pathspecs` (exit 0). Without the flag, git fails with `pathspec magic not supported by this command: 'glob'`.
- The literal word `:(glob)x` lists that file.
- `scripts/*` matches nothing.
- `Scripts/check.sh` matches nothing (case-sensitive).
- `./scripts/check.sh` and `tools/../Makefile` resolve; git normalises them. Decision 8 drops `..` words and strips `./` before git sees them anyway.
- **A word ending in `/` (`scripts/`) lists the directory's direct entries** (`scripts/check.sh` as a blob, `scripts/sub` as a tree). Decision 8 does not strip a trailing `/`, so a command naming `scripts/` pins that directory's top-level tracked files. This over-match is safe, as Risks says ("only tracked blobs count"), and is recorded here for M9.13.5's tests. A word without the slash (`test`) gives the tree entry, which decision 9 does not pin.

All of decision 9's filters (blob type, modes `100644`/`100755`, symlink `120000` excluded) are visible in this output. The engine's `Git` wrapper (`worktree.rs:332-345`) already scrubs the pathspec environment variables (AGENTS.md rule 11). `NO_HOOKS`' `-c` pairs come first (`git/mod.rs:240-244`), and `--literal-pathspecs` is a global option that may follow them.
