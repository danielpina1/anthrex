**Goal.** anthrex stops starting new agent sessions when the user's subscription is nearly used up, lets the user stop all new sessions with one switch, and moves a long-lived orchestrator to a fresh session at a goal boundary before its context fills up. Sessions already running are never killed.

**Architecture.** Three brakes, one gate. The **quota brake** reads the usage figures the CLIs already print — Claude's `rate_limit_event` stream line and the `token_count` lines in a Codex session's own rollout file — into a pure `QuotaBook` in the engine state. The **hold** is a daemon-wide switch persisted in `<data_dir>/brakes.json`. Both feed one pure `brakes::Gate` that the scheduler's new-session entry points consult per runtime. Where the gate refuses a fresh session for a quota trip, `failover::admit` may start it instead on its role row's fallback model when that model is on the other, unbraked runtime (U17). The **context handoff** measures the orchestrator's context fill from its own transcript tail when a goal continues a chain, and starts a fresh session (milestone 9.3 decision 24's path) instead of adopting the old window once the fill crosses the threshold.

**Tech stack.** Rust 2024 workspace; `serde`/`rmp-serde` wire types; `ratatui`/`crossterm` for the TUI; `fake-agent` for every test.

**Spec.** NA §5 and the decisions U11–U13 in NA §1.1. Read both before task M9.16.2. NA §5 is a summary; the detail it leaves open is decided below, each ruling marked **(R)**. Where this brief cites "NA §5 A<n>", "B<n>", "C<n>" or "Protocol impact", it means the numbered points of the approved design research that NA §5 condenses (`.superpowers/nucleos-design/m9.16.md`, outside the repository: A the context handoff, B the quota brake, C the global hold); each point this milestone relies on is restated in full in the decision that cites it, so the brief stands without that file.

## The user's decisions

These bind every decision here (NA §1.1, recorded from the user's design gate of 2026-10-10) and are never reinterpreted:

- **U11** The quota brake is **on by default**, pausing at **90 % of the 5-hour window** and **95 % of the 7-day window**.
- **U11** (continued) Readings come **only** from the CLIs' own output: Claude's stream `rate_limit_event` and Codex's rollout. The daemon **never** reads an OAuth token, `~/.claude/.credentials.json` or the macOS Keychain, and makes no HTTP request to a vendor.
- **U12** The hold stops **new sessions only**. Merges, delivery (pushes, pull requests, CI and review polling), gates and every open turn continue.
- **U13** The handoff fires at **whichever comes first: 80 % of the context window or 300,000 tokens**. Both are configurable; 0 disables. A **Codex orchestrator also hands off automatically** when its rollout gives a fill.
- **U17** **Cross-runtime failover.** While a runtime is quota-braked, a **fresh** session (never a resumed one) whose role row's fallback ("if it struggles") model is on the **other** runtime, and that runtime is not braked, starts on the fallback instead of waiting. A reviewer never receives the author's model this way. The run's attention line names the switch (NA §5 "Cross-runtime failover"; decisions 36–45).

## Goal

When a runtime's subscription window reaches its threshold, no new session of that runtime starts anywhere in the daemon until the window resets or a fresher reading shows it below, except that a fresh session whose role row names an "if it struggles" model on the other, unbraked runtime starts on that model instead (U17); tasks already running keep their reviewers and fix rounds. `anthrex hold on` (or `C-b H`) stops every new session of every runtime until `anthrex hold off`, across daemon restarts, without pausing any run. A goal continued on a chain whose orchestrator's context is past the threshold starts with a fresh orchestrator session that is told what came before, and the old window stays open for the user to close.

## Design decisions

### Facts and units

1. **Fixtures are captured by the controller, never by the implementer.** Every new fixture in M9.16.1 is captured by the human or controller with the real `claude` and `codex` on `PATH` and checked in with a `.meta.json` (`{"runtime", "cli_version", "captured", "redactions"}`, the existing convention). Tests read only checked-in fixtures and drive only `fake-agent`. Where a capture has not landed, the tests named here use the existing fixtures listed in "Starting point", which already carry every shape this milestone parses except Codex's 5-hour window and a `[1m]` `modelUsage` key.
2. **One canonical unit: per mille, as `proto::brakes::Permille(u16)`, 0 to 1000.** Claude reports a **fraction** (`utilization: 0.53`), Codex a **percentage** (`used_percent: 99.0`). They are converted in exactly one place, `Permille::from_fraction(f64)` and `Permille::from_percent(f64)` in `proto/src/brakes.rs`, the only two functions in the workspace that multiply a usage figure: `from_fraction(x) = round(x × 1000)`, `from_percent(p) = round(p × 10)`, each clamped to 0..=1000, and `None` for a NaN, an infinity or a negative value (an unmeasurable reading, never a wrong one). Every threshold comparison is `used.0 >= u16::from(percent) * 10`. **(R)** NA §5 keeps `used: f64`; `RunsSnapshot` and `RunInfo` derive `Eq`, which an `f64` cannot, and an integer cannot be mistaken for the other unit. Displayed percentages are `used.0 / 10` (floor).
3. **Two windows**, `QuotaWindow::{FiveHour, SevenDay}`, wire `five_hour` / `seven_day`, labels `5h` / `7d`, lengths `FIVE_HOUR_SECS = 18_000` and `SEVEN_DAY_SECS = 604_800`. Claude: `rate_limit_info.unifiedWindows.five_hour` / `seven_day`, each `{utilization, resetsAt}`. Codex: `rate_limits.primary` and `rate_limits.secondary`, each `{used_percent, window_minutes, resets_at}`, mapped **by `window_minutes`** (300 → `FiveHour`, 10080 → `SevenDay`), never by position: the checked-in rollout has its 7-day window as `primary` and `secondary: null`. Any other window or key is ignored.

### The quota brake (NA §5 B)

4. **`SessionEvent::Quota(QuotaSample)`** from a Claude `rate_limit_event` line: `QuotaSample { windows: Vec<(QuotaWindow, Permille, Option<u64> /* resets_at */)>, rejected: Option<QuotaWindow> }`. `rejected` is set when `rate_limit_info.status == "rejected"`, to the window `rateLimitType` names (`five_hour` / `seven_day`); that window then counts as 1000 ‰ whatever its `utilization`. `allowed` and `allowed_warning` change nothing (the utilization decides). A line with no usable window yields `SessionEvent::Other { kind: "rate_limit_event" }` as today. The parser stays pure; the reading's time is the engine event's `now`.
5. **Codex readings come from the session's own rollout.** On a headless Codex window's `TurnEnded`, the driver reads the tail of that session's rollout (decision 9) for the last `event_msg` whose `payload.type == "token_count"` and turns its `rate_limits` into a `QuotaSample` (`transcript/fill.rs::codex_limits`). At most one rollout read per `ROLLOUT_READ_EVERY = 60 s` daemon-wide, so many Codex workers do not each read a file per turn.
6. **The `QuotaBook`** (`run/engine/quota_book.rs`, pure) lives in `EngineState.brakes`, daemon-wide, one entry per runtime, fed by `EventKind::Quota { runtime, sample }`. **(R)** NA §5 says "on the run service": the engine owns the gate, so the book is engine state (in memory, never persisted; a restart starts unmeasured, decision 8). For each window it keeps the newest reading `{used, resets_at, read_at}`. A reading at or over its threshold **trips** the window: `Trip { window, used, threshold_percent, until, read_at }` with `until = resets_at` or, when absent, `read_at + window length`.
7. **Release (the deadlock guard, NA §5 B4).** While braked no session of that runtime runs, so no new reading arrives. A trip is cleared only when `now >= until`, or when a reading of that window **newer than the trip's** is below the threshold. A trip never clears because its reading went stale.
8. **Fail open (NA §5 B5).** With no trip, dispatch is allowed: also when there is no reading or the newest is older than `quota_fresh_secs`. That state is `QuotaState::Unmeasured` (no reading since the daemon started) or `Stale`. The first time per daemon start that the gate lets a session of a runtime start while that runtime is `Unmeasured` or `Stale` and the brake is enabled, the engine logs to that run `<runtime> quota is unmeasured; dispatch is not braked` (`QUOTA_BLIND_TEXT`), once per runtime (`Brakes.announced`).
9. **Locating a rollout.** The rollout of thread `<id>` is the one file whose name ends `-<id>.jsonl` in `<sessions>/<YYYY>/<MM>/<DD>/`, where `<sessions>` is `transcript::rollout::codex_sessions_dir` and the dates searched are the session start's date and the day before and after (three directories listed, no recursive walk), cached per thread once found. **(R)** NA §5 says "reads the targeted file and walks no directories": the file name carries a timestamp the daemon does not know, so one listing per candidate day is the least that finds it. M9.16.1 confirms the name shape and whether the date directories are local time or UTC.
10. **Config** (`[orchestrator.brakes]`, settings-owned, applied live): `quota_brake = true`, `quota_pause_5h_percent = 90` (1..=100), `quota_pause_7d_percent = 95` (1..=100), `quota_fresh_secs = 600` (60..=86_400). **(R)** NA §5 names the table `[brakes]`; every settings-owned key today is under `[orchestrator]` and the settings code (`doc_of`, `apply_owned`, `changed_since_loaded`, `swap_owned`) is built on `config::Orchestrator`, so the table is the sub-table `[orchestrator.brakes]`, as `[orchestrator.design]` is. After every config load and every settings save, the driver sends `EventKind::BrakesConfig(BrakeConfig)`; on it the book re-derives every trip from its stored readings under the new thresholds.

### The hold (NA §5 C)

15. **`DispatchHold { since: u64, by: String }`**; `BrakesInfo.hold: Option<DispatchHold>` (`None` is off). `by` is `"user"` for a request, `"corrupt brakes.json"` or `"unreadable brakes.json"` when decision 16 fails closed. **(R)** NA §5 writes `Hold { on, since, by }`; `proto::orch::HoldInfo` already names a plan approval hold, and an `Option` cannot hold `on: false` with a `since`.
16. **`<data_dir>/brakes.json`** = `{"v": 1, "hold": {"since": <u64>, "by": "<text>"}}` or `{"v": 1, "hold": null}`. Written by `run/driver/brakes_io.rs::save` on `spawn_blocking` within `BRAKES_IO_WAIT = 5 s`: a temp file in the same directory, mode 0600, `fsync`, rename. Loaded once at `RunService` start the same way. Missing: hold off. Unparseable or `v != 1`: renamed to `brakes.json.corrupt-<unix>` and **hold on** with `by = "corrupt brakes.json"` (fail closed: the user asked for it). A read error or a read that does not finish in time: hold on with `by = "unreadable brakes.json"`, logged; the file is left as it is. Never in `state.json`.
17. **The request.** `RunRequest::Hold { on: bool }`, answered under `request::HOLD = "hold"` with `RunReply::Held { hold: Option<DispatchHold>, message: String, request_id }`. The driver writes the file first; if the write fails the request is refused (`RunReply::Refused`, `the hold was not saved: <error>`) and nothing changes. Then `EventKind::Hold { reply, hold }` sets `EngineState.brakes.hold`. Idempotent: `on` while on keeps the first `since` and answers `dispatch was already held since <HH:MM> UTC`; `off` while off answers `dispatch is not held`. Messages: on `dispatch held daemon-wide; running sessions continue · anthrex hold off releases it`, off `dispatch released`.
18. **The hold changes no `RunState`** (NA §5 C3): runs stay `Running`, `paused_secs`, `paused_from` and the estimates are untouched. The orchestrator's `resume_run` (9.9) and the user's `run resume` cannot lift it: neither touches `EngineState.brakes`.
19. **What the hold stops.** Decision 11's gate for **every** runtime, and these requests, refused in the driver **before** any decider, scout or session starts, with `HOLD_TEXT = "dispatch is held daemon-wide · anthrex hold off"`: `RunRequest::Start` (a plan file), `StartGoal` (new and `--continue`), `Promote`, `Iterate`, the orchestrator's `start_goal` tool (`chain_goal.rs::start_goal_tool`, `driver/orch.rs:255`), and a queued goal's start (`goal_queue.rs::start_queued_goal` returns `Err(HOLD_TEXT)`). The driver reads the flag with `crate::lock(&self.state).brakes.hold.is_some()` — a lookup, nothing else under the lock. Still allowed: approve, reject, retry (it only requeues), override, cancel, finish, resume, deliver, watch, orchestrator wakes, reads and `edit_plan`.
20. **A queued goal stays queued under the hold** (controller ruling, 2026-10-10: dropping a goal the user asked for is worse than waiting). The drain checks the hold first and, while it is on, leaves every queued goal in place and records nothing as dropped. Turning the hold off (`RunRequest::Hold{on:false}`, and a hold file found absent or off at daemon start) triggers the same drain 9.10 runs on profile confirmation, so held goals start then, in queue order, each still subject to its own profile checks.
21. **Every non-terminal run shows `HOLD_TEXT` as an attention line** while the hold is on (NA §5 C3).

### The context handoff (NA §5 A)

22. **Fill is measured from the session's own transcript tail**, the last `TRANSCRIPT_TAIL_BYTES = 262_144` bytes, read on `spawn_blocking` within the run's `git_timeout_secs` (as `history_lines` does), never under a lock:

### Cross-runtime failover (U17, NA §5 "Cross-runtime failover")

36. **Where, and only where (R).** Failover happens at decision 11's **gated** entry points and nowhere else, and only when the gate refuses the session's own runtime for a **quota trip** (`Gate::refusal(runtime) == Some(Refusal::Quota(trip))`), never for the hold. Every session those entry points start is a **fresh** session: a `Queued` task's first session (`dispatch_writers`), a `Preparing` task's first session (`launch_ready`), a research or review task's first session (`kinds::dispatch`), a sub-planner, a document reviewer, a run scout (`planners::dispatch`'s starters). Every session that resumes or continues work is on decision 11's "Not gated" list — `restore::relaunch` (a `--resume`, and the fresh session after a failed resume, `outbox::resumed`), `pair::launch_due`, rung 2 and fix rounds, reviewers of dispatched tasks, deciders, the orchestrator — so it never fails over: a resumed session stays on the CLI that started it (its session id is that CLI's), and in-flight work keeps its runtime. The **orchestrator never fails over** (its launch and relaunch are not gated, Scope "Out").
37. **The candidate.** `failover::candidate(run, role, current) -> Option<Route>` (pure, `run/engine/failover.rs`): the row's fallback from the run's **frozen** `RunModels` (`run.limits.models().choice(role).fallback`) at its default effort (`RunModels::route_of(f, None)`, as escalation and the racer take it, M9.8 decisions 28–29), when **all** of these hold, else `None` and the session waits exactly as decisions 11 and 13 say:
    - (a) `current` is the row's own model (`models.same_model(current, &models.route(role))`). A route the **user** set to another model (M9.8 decision 10) or one already on the fallback (rung 2, `run retry`) waits: failover moves a row's model to its fallback and nothing else.
    - (b) a fallback is set and `fallback.runtime != current.runtime`. **A fallback on the same runtime does not fail over**: that runtime is the braked one; the session waits as before. No fallback: waits.
    - (c) `gate.allows(fallback.runtime)`: that runtime is not braked and the hold is off. `Unmeasured` or `Stale` counts as allowed (decision 8, fail open) and announces `QUOTA_BLIND_TEXT` for that runtime once, as any start there does.
    - (d) the fallback's runtime is installed for the run (`!model_roles::missing(&run.orch.installed, …)`).
    - (e) for a task's session, the fallback did not fail in this task (`model_roles::failed_in(models, &failed_routes(task), …)`, ruling RL-1).
    - (f) the overlap rule (decision 39) and (g) the reviewer rule (decision 40) allow it.
    - (h) **(R)** the fallback's runtime has room: `concurrency::has_room(run, fallback.runtime)` for a writer, the reader-slot count for a reader, checked exactly where the session's own runtime would have been. No room: the session waits this step and is tried again next step.
38. **Which roles fail over.**

    | Session (entry point) | Row | Fails over |
    |---|---|---|
    | A `Queued` or `Preparing` task's worker (`dispatch_writers`, `launch_ready`; a hub task too) | `RunModels::task_role(task)`: `implementer.small`, `.medium`, `.hub` | Yes; overlap rule as `Mover::Worker` |
    | A paired task's first session, its test writer (`dispatch_writers` → `pair::begin`) | `test_writer` | Yes; overlap rule as `Mover::Transient`, as `model_roles::writer_route` |
    | A paired task's implementer (`pair::launch_due`) | — | No: not gated (decision 11) |
    | A racing task (`spec.race`), either lane | — | **No (R)**: lane 2 is already the row's fallback (M9.8 decision 28); moving lane 1 there would race a model against itself. A braked lane waits as decision 11 says. |
    | A research task (`kinds::dispatch`) | `research` | Yes |
    | A review task or an integration review (`kinds::dispatch`) | `reviewer` | Yes; reviewer rule |
    | A sub-planner (`planners::dispatch`) | `planner` | Yes |
    | A run scout (`run_scouts::start_next`) | `research` | Yes |
    | A brainstormer (`design_agents::start_next`) | `brainstorm` | No: the row is a pair of models with no fallback (`BrainstormChoice`) |
    | A document reviewer (`design_agents::start_next`) | `reviewer` | Yes; reviewer rule |
    | A reviewer or fix round of a dispatched task, rung 2, a relaunch or resume, a decider, the orchestrator | — | No: not gated (decisions 11, 36) |

39. **Rule 9 holds** (no two runtimes on overlapping `owns`, M9.8 decision 33). A worker that fails over moves its task to the other runtime, so it does so only when `model_roles::runtime_open(run, i, fallback.runtime, Mover::Worker)`: no unfinished task on another runtime overlaps its `owns`. Validation's rule 9 put every task that overlaps it on its own (braked) runtime, so **a task with an unfinished overlapping task never fails over; it waits**. A test writer uses `Mover::Transient`, exactly as `writer_route` does (rulings FW-1, FW-5). Readers (research and review tasks, sub-planners, run scouts, document reviewers) have no worktree and write nothing, so no overlap check applies. After a worker fails over, `task.route` names the runtime it really runs on (decision 41), so every later `runtime_open` (another task's rung 2, a racer, a test writer, a failover) counts it on the right runtime.
40. **The reviewer rule (M9.8 decision 27, D3).** A `reviewer`-row session fails over only when the fallback is **not the same model** (`RunModels::same_model`) as any of its possible authors: the run's orchestrator route (when it has one) and the route of every writing round (`model::writes`) of every task in the run. **(R)** A review task records no author, and an integration review's author is not kept once `integration.rs:176` resolves its route, so the set is every author the run has: a superset, never fewer. When the fallback is an author's model the session waits. A **worker** that failed over is reviewed by the existing rule: `review.rs:158-167` picks the reviewer against the route of the last writing round, which is the fallback the worker really ran, so its reviewer is never that model (`reviewer_at_launch`, unchanged). Reviewers of dispatched tasks are not gated and never fail over: they start on their own route even on a braked runtime (decision 11).
41. **The route and the escalation ladder (R).** A failover is **not a rung**: `task.rung`, `failures`, `bounces` and the session number move as for a start on the row's model, and the first turn is the normal first prompt (the worker prompt, the test writer prompt, …), not a hand-over. It writes the fallback route where the session's route lives: `task.route` (a worker, a research or review task), `pair.writer_route` after `pair::begin` (a test writer), and the built spec's `route` for a sub-planner, run scout or document reviewer (as `planners.rs:291` sets a sub-planner's). A worker's `task.review_route` is recomputed against the new route, as `ladder.rs:336` does. Because the task's route is now its row's fallback, M9.8 decision 29's ladder **continues from the fallback**: rung 2 climbs the fallback's effort list, then `None` and the later rungs apply; it never returns to the row's model or its efforts. When the brake releases, a failed-over task **stays** on the fallback; nothing switches back.
42. **Visibility and the record.**
    - The run log gets, per failover, `<who>: <runtime> braked (<window> at <n>%); started on <model label> (fallback)` (`FAILOVER_LOG_TEXT`), where `<who>` is the task id (`t3`), `planner <epic>`, `scout <id>` or `doc review <label>`.
    - `Run.failovers: Vec<FailoverRecord { who, from: Route, to: Route, at }>` (`#[serde(default, skip_serializing_if = "Vec::is_empty")]`, the newest `FAILOVERS_KEPT = 32` kept). The run's attention has, for each record whose `from.runtime` is braked **now**, `<runtime> braked: <who> started on <other runtime> (fallback)` (`FAILOVER_ATTENTION_TEXT`; e.g. `claude braked: t3 started on codex (fallback)`), the newest three, then `… and <n> more failovers`. The lines go when the brake releases; the log lines stay. A session that failed over is no longer waiting, so decision 13's `dispatch held` line does not count it.
    - History: `RoutingDecision.failover` (task sessions) and `RoleRoutingDecision.failover` (sub-planners, run scouts, document reviewers), each `Option<Route>` with `#[serde(default, skip_serializing_if = "Option::is_none")]`: the braked route the session moved **from**; `chosen` is the route actually used; `source` is `quota_failover`; the row's own route stays in `candidates` before the fallback, and `selected_index` points at the fallback. `HISTORY_VERSION` stays 5 (no `deny_unknown_fields`, `history.rs:4-5`).
43. **The hold blocks failover too.** `Gate::allows` is false for every runtime while the hold is on (decision 19), so (c) never holds; and the refusal under the hold is `Refusal::Held`, never `Quota`, so failover is not even tried.
44. **Within the user's models (M9.8 D2).** The candidate is only ever the session's own row's fallback from the run's frozen `RunModels`. Failover never edits `RunModels`, `run.limits`, the global or repository table, or another row, and never picks a model the table does not name. A run started before the brake tripped and one started after behave the same.
45. **No switch, no wire change (R).** U17 names no setting; none is added (`SETTINGS_KEYS` stays 15). A user who does not want a role to fail over keeps its fallback on the same runtime or leaves it empty (decision 37 (b)). The protocol stays **25**: the attention line is a string, and the two history fields are folded into M9.16.2's protocol-25 change.

## Risks and gotchas

- **The rollout and `rate_limit_event` shapes are undocumented.** A changed shape must yield no reading (unmeasured, fail open), never a wrong number. M9.16.1's captures are the evidence; re-capture when a CLI's major version changes.
- **Codex ephemeral sessions have no rollout.** Deciders and scouts run `codex exec --ephemeral` (`headless/argv.rs:505-506`); they never give a Codex reading. A worker always has one unless the user's runtime command redirects `CODEX_HOME` away from the daemon's environment.
- **Readings exist only while sessions run.** After a daemon restart every runtime is unmeasured until the first turn; that first wave is never braked (decision 8).
- **80 % of a 1M window is 800k tokens**, past where long sessions degrade; U13's 300,000 cap is what fires there.
- **The handoff loses in-session nuance** beyond the summary and the last ten history lines (decision 24 of 9.3).
- **The old window after a handoff is no longer the chain's**; if the user types in it, nothing anthrex does follows. Its name says so.
- **A hold left on by mistake** stops everything quietly: the badge, the alert, the attention line on every run and `anthrex run status` all say so.
- **`HoldInfo` already exists** (a plan approval hold). Every new name in this milestone says `DispatchHold`, `Hold { on }` (a request) or `brakes`; the TUI's `AlertKey::Hold` and `RouteKind::Hold` are the approval hold and are untouched.
- **Failover spends the other provider's quota, often on a stronger model.** The fallback means "if it struggles" and is usually stronger (and slower, and more expensive per turn); a braked Claude can send a whole wave of medium tasks to the Codex fallback and trip Codex's window in turn, after which both wait. The other runtime's brake still applies to every failed-over session (decision 37 (c)), so the quota is never overspent past its threshold, but the user's other subscription is what pays. The attention line and the run log name each switch; a user who does not want it keeps the row's fallback on the same runtime (decision 45).
- **A failed-over task does not come back.** After the brake releases it keeps the fallback, and its rung 2 climbs the fallback's efforts only (decision 41); the row's own higher efforts are skipped for that task.
- **A failed-over worker's reviewer can land on the braked runtime.** Reviewers of dispatched tasks are not gated (decision 11), and decision 27 of M9.8 often puts a Codex author's reviewer on Claude. That is in-flight work finishing, as for any task.
- **`app/mod.rs` (599), `cli/src/main.rs` (596), `planners.rs` (589) and `engine/orch.rs` (592)** are at the size limit before this milestone; the move-only splits come first.
