> Written 2026-10-01 against `docs/superpowers/specs/2026-10-01-tui-end-to-end-design.md` ("the spec", "§n" below), §§1–5, which bind this milestone. §6 is milestone 9.0.7 (TUI polish) and is out of scope here except where §5.2 says 9.0.6 touches a screen anyway. Read `AGENTS.md` first.

**Goal.** From one TUI, with no second terminal, a user takes a repository from no profile to a confirmed profile, sets their models and run limits, starts a goal, reviews and approves the plan, answers a blocked worker, steers, retries or overrides tasks, and accepts or discards the finished run. Each step shows what it will do, with exact names, before it is committed.

**Architecture.** The daemon computes, for every run, stage and task in the live snapshot, the list of actions the user can take there (`ActionInfo`), from one pure engine function whose predicate is the very check the request handlers run, so the menu and the daemon cannot disagree. The TUI renders that list as a menu (`.`), collects input in kit-built forms, ends every state change on a confirmation page, and sends only requests the CLI can already send, plus one new request pair, `RunRequest::Settings`, whose `Put` validates, writes `config.toml` line by line (comments kept, atomic rename), and swaps the daemon's live orchestrator settings outside the manager lock, so new runs use them and running runs keep their frozen roster and limits. Two new full-body screens, Profile (`C-b P`) and Settings (`C-b S`), and a stats screen, are built only from a small design kit (roles, glyphs with ASCII twins, width-aware hints, one dialog grammar) that the status bar, the goal form and the confirm modals also move to.

**Tech stack.** Rust 2024 workspace; `ratatui` + `crossterm` (TUI), `tokio` (daemon), `serde` + `rmp-serde` named maps (wire), `toml` 1.1 (config; no `toml_edit`, decision 30), `fake-agent` for every agent in tests.

**Spec.** `docs/superpowers/specs/2026-10-01-tui-end-to-end-design.md` §§0–5 and §7's 9.0.6 row.

## Global Constraints

These bind every task. A reviewer rejects a change that breaks one, whatever the brief's task text says.

1. **Only the orchestrator is interactive.** Workers, reviewers, scouts and sub-planners stay headless and watch-only. The daemon already refuses input, kill and terminal subscribe for them (`daemon/src/server/headless_guard.rs:22-50`); nothing in this milestone sends `ClientMsg::Input`, `Kill` or `Subscribe` to a headless window, and the action menu has no entry that would.
2. **The engine stays deterministic, and the TUI only sends requests the CLI can send.** Every action maps to one existing `RunRequest` (§1.1's table, reproduced in `actions_request_tests.rs`, task 10). The only new request is `RunRequest::Settings` (decision 25), which is configuration, not run control. No model decides anything new.
3. **Nothing reaches the base branch until the user accepts.** Accept is a destructive-grade confirmation (`y` only, never bare Enter) whose page names the base and the head that will be merged.
4. **No blocking work under the manager lock or on a tokio worker thread** (AGENTS.md hard rules 2, 10 and 11). The config read, write and rename run on `tokio::task::spawn_blocking` with `SETTINGS_WRITE_TIMEOUT`, outside the manager lock and outside the engine lock. The live-settings handle is a `std::sync::Mutex<Arc<Live>>` held only to clone or replace an `Arc`. No git command is added. `actions::available` and `actions::check` are pure.
5. **Mutexes through `daemon::lock(&m)`** (`crate::lock` inside the daemon), never `.lock().unwrap()` (rule 3).
6. **The client's state stays pure** (rule 5). `app/**`, `ui/**`, `actions_request.rs`, `text_area.rs` and `profile_view.rs` do no I/O; every update returns `Vec<Effect>`; every renderer takes `&App`.
7. **Every displayed string passes `safe_text`.** Agent- or git-written text (a question, a block reason, a halted reason, a note, a model name, a profile command, a check's output tail, a daemon refusal) goes through `proto::safe_text::one_line` (a row) or `multi_line` then `one_line` per wrapped line (a pane). The kit's widgets sanitise their own inputs (decision 21), so a screen cannot forget. The daemon also sanitises and caps every `ActionInfo.effect` and `refused_why` it builds (decision 8).
8. **Protocol changes bump `PROTO_VERSION`** to 13 in one task (M9.0.6.5) with a MessagePack and JSON round-trip test for every new message, variant and field, and every client compiles in the same change: the TUI, the CLI client (`cli/src/client.rs`, `run_cmd.rs`) and `anthrex hook` (`cli/src/hook.rs`). Every new field is `#[serde(default)]`; new enum variants are appended last.
9. **Files stay under about 600 lines** (rule 8). "File sizes this milestone must respect" gives each touched file's bound; new files stay under 600.
10. **Tests use `fake-agent` only.** Every test that starts a daemon points `ANTHREX_CLAUDE_BIN` and `ANTHREX_CODEX_BIN` at `fake-agent` and `ANTHREX_DECIDER_BIN` at `fake-agent` or a nonexistent path (`RunHarness`, `cli/tests/support/run_harness.rs:196-205`, already does), `ANTHREX_CONFIG` at a temporary file, and `ANTHREX_SOCKET` and `ANTHREX_DATA_DIR` under a temporary directory. **No test reads or writes the user's `config.toml`** (§4.5): every config-writer test writes under `tempfile::tempdir()`. No test changes program selection or signals a process it did not start.
11. **Wait loops have hard deadlines**; a fixed sleep is never the only synchronisation (rule 6). **Read `docs/timing-budgets.md` before any wall-clock bound**: every bound is derived from the constants the code runs against (standing rule 1), and a TUI reply timeout is tested by moving the request's `sent_at` into the past, never by sleeping (as `App::set_runs_received_at`, `tui/src/app/runs.rs:434`, does).
12. **macOS first-exec stall.** A freshly built executable can stall seconds on its first exec (`docs/timing-budgets.md`, "Fixed, from the `server_restore_git.rs` flake"). Share `fake-agent` through `RunHarness` and warm stub executables before the timed part of a test; never widen a timeout to absorb it.
13. **Never touch a live daemon** (rule 1): manual runs set `ANTHREX_SOCKET`, `ANTHREX_DATA_DIR` and `ANTHREX_CONFIG` under `/tmp` and end with `anthrex daemon stop`.

## Goal

Every step of a run is reachable and decidable from the TUI. `.` on a run, stage or task opens a menu of the actions the daemon says are possible there, each with a one-line effect naming exact things (`accept: merge 3 tasks into main@59705dc`); actions the user would expect but cannot take now are listed muted with the daemon's own reason, and pressing Enter on one only toasts it. Input actions open a form (answer, message, override reason, resume with rebaseline, promote with an orchestrator picker); every state change ends on a confirmation page that repeats the effect and the details that matter; destructive ones (reject, cancel, discard, cancel task) are drawn in the failure colour and confirm only on `y`. An alert's Enter opens that menu with the matching action preselected. `C-b P` opens the project's profile: its status and proposal (with live polling while a detection runs), every key grouped with each command's verification, a `+ − ~` diff of a proposal, per-key editors, and a confirm page showing the exact TOML that will be stored. `C-b S` opens Settings: per-runtime model tables from shipped lists plus custom models, the orchestrator default, and the run limits with their ranges; `w` saves through the daemon, which validates with config's own rules, writes `config.toml` keeping every other line, and reloads in place, so new runs use the settings and running runs keep theirs. A small design kit makes all of this one visual language at 80×24.

## Design decisions

Numbered and final. If one proves wrong or impossible, stop work on it, record the evidence under "Implementation notes", and continue with the tasks that do not depend on it.

### The design kit (§5)

1. **Roles.** `theme::Role { Accent, Attention, Working, Done, Failed, Muted, Paused }` and `theme::role(r: Role, palette: Palette) -> Style`, `Palette { accent: Color, truecolor: bool }` (built by `App::palette()` from `UiSettings`). With truecolor off every role is one of the 16 ANSI colours: `Accent` `LightBlue`, `Attention` `LightMagenta` bold, `Working` `Yellow`, `Done` `Green`, `Failed` `Red`, `Muted` `DarkGray`, `Paused` `Cyan`. With truecolor on: `Accent` is `UiSettings.accent`, `Attention` `Rgb(0xfa,0xb3,0x87)` bold (today's attention, `theme.rs:20`), `Working` `Rgb(0xf9,0xe2,0xaf)`, `Done` `Rgb(0xa6,0xe3,0xa1)`, `Failed` `Rgb(0xf3,0x8b,0xa8)`, `Muted` `Rgb(0x6c,0x70,0x86)`, `Paused` `PAUSED_COLOR` (`theme.rs:38`). `Working` is never `Attention` (principle 1). The old `status_color`/`task_color`/`alert_color` stay as they are for the screens 9.0.7 moves.
2. **The truecolor decision.** A new `[theme]` table in `config.toml` with one key, `truecolor = "auto" | "on" | "off"` (default `"auto"`), read by a new `config/src/theme.rs` (`config::Theme { truecolor: Truecolor }`, `Config.theme`), unknown keys reported as everywhere. `theme::truecolor(setting, colorterm: Option<&str>) -> bool`: `On` true, `Off` false, `Auto` true exactly when `COLORTERM` is `truecolor` or `24bit` (ASCII case-insensitive). The CLI reads `COLORTERM` once in `attach`, beside the locale, and calls `UiSettings::with_colorterm` (the client stays pure; `cli/src/main.rs:382` changes on that one line, the file must not grow).
3. **Glyphs.** `theme::Glyph { Passed, Failed, NotStarted, Idle, NeedsYou, Collapsed, Selection, Separator, Warning }` and `theme::glyph(g, ascii) -> &'static str` with the table of §5.1 principle 4 exactly (`✓ +`, `✗ x`, `◌ .`, `○ o`, `⚑ !`, `▸ >`, `▌ >`, `› >`, `⚠ !`); `theme::spinner(frame, ascii)` cycles `SPINNER` or `- \ | /`. `ascii` is `UiSettings.badges.ascii` (`ui/badge.rs:38`), the one switch `force_ascii` and the locale already drive. New screens draw runtimes as text tags `cl`, `cx`, `sh` (`theme::runtime_tag`).
4. **The kit widgets** live in `ui/kit/` and take already-built strings; each sanitises its text inputs with `safe_text::one_line` (decision 21). Exactly the functions in Interfaces "tui / kit". `hints(width, &[Hint])` drops whole hints, lowest `priority` first and the rightmost among equals, until the line fits `width`; a hint whose key is `esc` is never dropped (it is dropped last only if `esc` alone does not fit, which leaves an empty line). Keys are drawn in `Accent`, words in `Muted`, separated by two spaces.
5. **One dialog grammar** (principle 9) for every new dialog, the goal form and the confirm modals: lower-case labels; `‹ value ›` choices; hints `⏎ <action> · tab next · esc cancel`; one column of padding; width `min(64, area.width)`; text wrapped at 60 columns; a destructive dialog's title and action word in `Failed`, its body naming what is lost, confirming only on `y` (bare Enter does nothing and toasts `press y to <action>`). `dialog_frame` draws the one accented border of the frame (principle 2): while a dialog is open, the new screens beneath it (Profile, Settings, Stats) draw their borders muted; the older screens follow in 9.0.7.
6. **The status bar** (§5.2): mode badges ` MENU ` (any `Modal::Action`), ` PROFILE `, ` SETTINGS `, ` STATS ` (the three screens), ` PLAN ` (the plan review, replacing ` REVIEW `), ` ALERTS `, ` CHAT ` (the conversation view open), ` RUN ` (the run view, replacing ` TREE ` there), ` TREE `, ` FILTER `, in that precedence after ` PREFIX `. While the prefix is pending the hints are the prefix list `<prefix> › a alerts · g goal · T run · P profile · S settings · ? help` through `kit::hints` (keys in the accent). Toasts carry a severity (`ToastLevel::{Info, Warn, Error}`): error toasts draw in `Failed`, warnings in `Attention`, info in the default colour. Every hint line in the status bar goes through `kit::hints`. ` STATS ` is an addition to §5.2's badge list (the spec has no stats badge).

### The action menu (§1)

7. **`ActionInfo` is in the snapshot, built by the daemon** (approach A, §0). `RunInfo.actions`, `StageInfo.actions` and `TaskInfo.actions` are `Vec<ActionInfo>` with `#[serde(default, skip_serializing_if = "Vec::is_empty")]`: an empty list costs nothing on the wire, which keeps `a_snapshot_of_fifty_terminal_runs_stays_small` (`run/snapshot_tests.rs:87`, 1.25 KiB a task) green with no change (decision 10). Every encoder of these types is `rmp_serde::to_vec_named` (`proto/src/codec.rs:23`) or JSON, both maps, so a skipped field decodes as its default.
8. **The one predicate.** `run::engine::actions::check(run: &Run, node: &ActionNode, kind: &ActionKind) -> Result<(), String>` is total: for every request-backed kind and every node it returns `Err(text)` exactly when the engine's handler for that request, given a valid input, refuses it, and `text` is that handler's reply text byte for byte. `available(run, node) -> Vec<ActionInfo>` lists the node's *relevant* kinds (decision 9) with `refused_why: check(..).err()`. The handlers call the same rule functions (`engine/actions/rules.rs`) instead of their inline checks (task 6), so equality holds by construction and the matrix test (task 7) proves it for every fixture state. `effect` and `refused_why` are `one_line`d and cut to `ACTION_TEXT_MAX` = 200 characters with `…` (the halted reason and block texts are git- or agent-written).
9. **Which kinds a node lists** ("relevant"), on a run that is not terminal (`accepted`, `discarded`, `failed`):
   - **Run:** `Approve` and `Reject` when `awaiting_approval`, `planning`, or `paused` from `planning`; `Submit` when `planning`, or `running` with an orchestrator whose plan is not submitted (`requests.rs:307-312`); `ApproveHold { hold }` and `RejectHold { hold }` for each hold in `Awaiting`; `Pause` when `running`; `Unpause` when `paused`; `Resume` when `halted`; `Cancel` when `running`, `paused` or `halted`; `Promote` when `path == fast` and not `complete`; `Accept` and `Discard` when `running`, `paused`, `halted` or `complete` (listed refused until complete: the spec's example of an action the user expects).
   - **Stage** (only a `Multi` run has stage nodes, M9.1 decision 55): `MessageStage { stage }` when the stage has an unfinished task.
   - **Task** (only an unfinished task: not `merged`, `cancelled` or `reported`): `Answer` when `blocked(question)` or `working`; `Message` unless it is a research or review task; `Refresh` when `working` or `paused(message)`; `Retry` when `blocked`; `Override` when `blocked` or `review`; `CancelTask` always.
   - A terminal run lists nothing at any node, and a finished task lists nothing. `Complete` runs list `Accept` and `Discard` only.
10. **Client-only kinds.** `ReviewPlan`, `Stats` and `OpenConversation` change nothing in the daemon and need no state the client lacks, so the TUI adds them itself (`app::actions::local_actions`): `ReviewPlan` first on a run awaiting approval or with an awaiting hold; `Stats` last on every run; `OpenConversation` first on a task that has an agent round. They are `ActionKind` variants so the menu is one list of one type. *(The spec has `available()` produce them; keeping them out of the snapshot keeps every complete run's merged tasks at zero bytes, decision 7. Recorded.)*
11. **Effect lines** name exact things, from the run alone (no git): Interfaces "Exact user-visible text" lists every one. Where the spec's examples need data the daemon does not hold without git, the line names what it does hold: `discard` names the `anthrex/<id>/*` prefix and the salvage refs instead of counting branches, and `retry` names the rung-2 route `roster::escalate` gives (`requests.rs:441`), not "rung reset to 0" (the code resets `failures` to 1 and sets rung 2, `requests.rs:450-456`).
12. **Opening the menu.** `.` on a selected run, stage or task node in tree mode (the sidebar tree, the overview and the run view all route through `on_tree_key`), and Enter on an alert (decision 17). Enter on a node keeps M8c decision 22's meaning (open the run view, focus the orchestrator's PTY, open a conversation, fold a stage), because the orchestrator's focus has no menu entry and every existing Enter test pins it. *(The spec says "`.` or Enter"; recorded.)* The menu is a `Modal::Action(Box<ActionFlow>)`, so it wins over every keymap mode as every modal does (`app/mod.rs:409`). `j`/`k` (and Down/Up) move, Enter picks, Esc closes. An entry with `refused_why` is drawn `Muted` with its reason after the label and Enter on it toasts the reason (`Warn`) and keeps the menu open. While `!app.connected()` the menu shows `not connected` and no entry; nothing is queued.
13. **The menu follows the snapshot.** After every snapshot an open `ActionFlow` re-reads its node's actions: a node that is gone closes the flow with the toast `<run name> is gone` / `<task> is gone`; a confirm page whose action is now refused shows the new `refused_why` in `Failed` and `y` only toasts it.

### Forms, confirmation and replies (§1.3)

14. **Every state change ends on a confirmation page** (`ConfirmPage`): the title is the action label, then the effect line, then the details rows of Interfaces "Exact user-visible text" (`Confirm details, …`), then the hints. A non-destructive page confirms on `y` or Enter; a destructive one (`ActionInfo.destructive`: `Reject`, `RejectHold`, `Cancel`, `Discard`, `CancelTask`) only on `y`. An input form's Enter goes to its page; Esc on a page goes back to the form (or the menu).
15. **Forms** (all kit-built, decision 5): **Answer** shows the task's `<id> <title>`, its question (`TaskInfo.block.text`, multi-line, sanitised), the first 3 lines of its brief (from one tagged `RunRequest::TaskDetail`, M9.0.5 decision 7; `loading…` until it comes, the refusal's first line if refused), and a 4-row text area; **Message** has `kind ‹ info ›` (`info`, `change`, `stop_and_wait`) and a 4-row text area; **Override** has a `reason` line that must not be blank (`type a reason first`); **Resume** has `rebaseline ‹ on ›`, on by default when `RunInfo.base_moved` is `Some`, with, when it is, `base moved <from7> → <to7> (<total> commits); rebaselining re-runs tier 3 against the new base`; **Promote** has `orchestrator ‹ configured ›` cycling `configured` then every enabled roster entry as `<tag> <model>` (from the settings cache, decision 24; with no cache only `configured`). Text areas reuse `crate::text_area::TextArea` (decision 22); every text sent is `trim`med and its control characters dropped as `run_goal::clean` does.
16. **Replies.** Every request the flow sends is tagged (`App::tagged_request`) and recorded in `App.replies: PendingReplies` with what it was and when. Its `Done` is an `Info` toast of the daemon's text (`capped`); its `Refused` an `Error` toast of `first_line_and_more` (the daemon's own text); `ConfirmNeeded` for a pending `Accept` with `base_moved: Some(info)` opens the moved-base page (decision 18); any other `ConfirmNeeded` (a pending accept or discard whose base did not move cannot produce one, since the flow sends `confirm` already) is shown as a `Warn` toast of its prompt. A pending request with no reply within its timeout (decision 19) is dropped with the `Error` toast `no reply from daemon` and changes no state; a late reply is still shown. A lost link drops every pending entry with no toast (the badge says it).
17. **Alert preselection** (§1.4). Enter on an alert opens the menu on the alert's node with this kind selected: ready to accept → `Accept` on the run; blocked → `Answer` when the block is a question, else `Retry`, on the task; halted → `Resume` on the run; plan awaits approval → `ReviewPlan`; hold awaits approval → `ApproveHold { hold }`; profile proposal ready → opens the Profile screen on that project's proposal (no menu); orchestrator needs you (P1) → unchanged (focus its window, M9.0.5 decision 18.1). If the preselected kind is not in the node's list (the state moved), the menu opens with its first entry selected.
18. **Accept with a moved base.** The accept page is sent as `Finish { action: Accept, confirm: Some(run_id) }`. The driver answers `ConfirmNeeded { base_moved: Some(info) }` when the base advanced (`driver/requests.rs:393-398`); the moved-base page then lists `info.commits` (one per line, sanitised, `… and <total − n> more`), `<base_branch> moved <from7> → <to7>`, and asks `type <short> to merge onto <to7>` (the run's short id, the last 4 characters of its id, principle 5). Typing exactly the short id and Enter resends `Finish { confirm: Some(format!("{run_id}@{}", info.to)) }` with the **full** `to` sha, the string the driver compares (`:385`). A wrong id shows `type <short> exactly` inline. *(The spec calls the typed id "the CLI's `--confirm`"; the CLI's accept has no `--confirm`, it asks a second yes/no or takes `--base <head>`, `cli/src/run_cmd/finish.rs:99-110`. The typed short id is the TUI's own friction step; the string sent is the one the driver checks. Recorded.)* Discard is sent as `Finish { action: Discard, confirm: Some(run_id) }` and reject as `Reject { run_id }`, each after its `y`.
19. **Reply timeouts.** `REPLY_TIMEOUT` = 30 s for requests answered in one engine step or one bounded file write (`Approve`, `Reject`, `Edit` without a refresh, `ApproveHold`, `RejectHold`, `Retry`, `Cancel`, `Stats`, `TaskDetail`, `Profile(Status|Show|Reject)`, `Settings(Get|Put)`; the longest is `Put`'s `SETTINGS_WRITE_TIMEOUT` of 5 s plus the engine step); `LONG_REPLY_TIMEOUT` = 660 s for requests that wait on git (`Finish`, `Resume`, `Override`, `Promote`, `Edit` with a `Refresh`, `Profile(Detect|Edit|Confirm)`): the largest `git_timeout_secs` the config allows (600, `config/src/orchestrator.rs:256-262`) plus 60 s. These are the user's patience, not test bounds: a late reply is still shown (decision 16), and no test sleeps on them.
20. **`ConfirmNeeded` and `base_moved` are handled, not dropped** (§4.3): `app/runs.rs:231-235` loses `ConfirmNeeded`, `Profile` and `Stats`, which now route to the flow, the Profile screen and the stats screen by `request_id`; `Started` and `ToolResult` stay ignored (the TUI sends neither `Start` nor `Tool`).
21. **Text safety in the TUI.** `kit::labelled_rows`, `kit::hints`, `kit::choice`, `kit::run_name` and the menu renderer call `safe_text::one_line` on every string they are given; panes call `safe_text::multi_line` and then `one_line` per wrapped line. Tests use `safe_text::tests::hostile_text()` and `first_hostile` as M9.0.5's do.
22. **A multi-line text area.** `tui/src/text_area.rs` (pure): `TextArea { text: String, cursor: usize (graphemes) }`, `on_key` (chars, Backspace, Delete, Left/Right/Home/End, Ctrl-J inserts a newline, Enter is the form's), `on_paste` (newlines kept, other control characters dropped), bounded at `TEXT_MAX_CHARS` (`run_edit.rs`), `text()`; `kit::text_area(&TextArea, rows, width) -> Vec<Line>` wraps at the width and scrolls to keep the cursor's row visible, with `↑`/`↓ n more` marks.

### The Settings protocol and live reload (§3, §4.1, §4.2)

23. **The document.** `proto::settings::SettingsDoc { models, orchestrator: OrchestratorDefault, limits: SettingsLimits }` holds exactly what Settings owns: the enabled roster (in order), the orchestrator agent's `runtime` and `model` (`[orchestrator.agent]`, `agent.rs:45-51`: the config's orchestrator default; `orchestrator.default_runtime` is the workers' default and is not a Settings key), and the limits: `budget.{s,m,l}.{tool_calls,minutes}`, `stall_after_secs`, `max_writers`, `max_readers`, `max_bounces`. Budget `tokens` is not owned (the screen shows the 1.5× hard stop beside tool calls and minutes only). The ranges move from `config/src/orchestrator.rs`'s literals to `proto::settings` constants that both the config parser and the screen read (task 5), so one range governs both.
24. **The settings cache in the client.** On every new connection (`lib.rs:83` and `on_reconnected`, `app/link.rs:225`) the TUI sends one tagged `Settings(Get)` and keeps the reply as `App.settings_cache` (doc, origin, path); every `Saved` replaces it. The goal form's model picker, the Promote form and the Settings screen read it; none of them sends a request of its own to read it.
25. **The wire.** `RunRequest::Settings(SettingsRequest)` and `RunReply::Settings { reply: Box<SettingsReply>, request_id }`, appended last, answered by `RunService::settings`; refusals inside the reply (`SettingsReply::Refused { problems }`), not as `RunReply::Refused`, so a problem list survives intact. `request::SETTINGS` = `"settings"`. *(The spec names `ClientMsg::Settings` and `ServerMsg::Settings`; there is no `ServerMsg` (`proto/src/messages.rs:93`, `DaemonMsg`), and a `RunRequest` variant reuses the tagged-request machinery (`ClientMsg::RunTagged`, `RunReply::tagged`, `server/run_api.rs:41-51`, which already answers each request on its own task off the connection loop) exactly as `RunRequest::Profile` does. Recorded.)* `SettingsReply::Current` also carries `path` (where `w` writes), and `Saved` carries the new `origin`, both additions to the spec.
26. **Origin.** `Origin::{File, Default}` per key path in `proto::settings::SETTINGS_KEYS` (13 paths, Interfaces). A key is `File` when the TOML table read at start (or written by the last save) contains it; `orchestrator.models` is `File` when the file sets `builtin_models` or has any `[[orchestrator.models]]`. The screen shows `(default)` after a `Default` value.
27. **Validation** (`config::settings::validate(&SettingsDoc) -> Vec<String>`, pure, shared by the daemon and the screen): no enabled model → `enable at least one model`; a Claude model with an empty name → `claude models need a name`; a duplicate `(runtime, model)` → `<tag> <model> is listed twice`; a note over `MODEL_NOTE_MAX` (`roster.rs:13`) → `note of <model>: at most 80 characters`; each limit outside its range → `<key>: must be between <a> and <b>` (or `must be at least 1` for budgets), the exact message config's parser gives (`orchestrator.rs:320`, `:345`, `:430`, `:444`); an orchestrator model with no runtime → `orchestrator.agent.model: choose a runtime first`; an orchestrator model not among the enabled models of its runtime → `orchestrator.agent.model: <model> is not an enabled <runtime> model`. `config::settings::warnings` adds, not refusing: for each strength that has an enabled model on exactly one runtime, `no <other runtime> model is <strength>: the cross-runtime reviewer cannot be chosen for <strength> tasks`.
28. **`Put`, step by step** (`RunService::settings`): (1) `validate`; problems → `Refused`, nothing touched. (2) Take `RunService.settings_write` (a `tokio::sync::Mutex<()>`, so two saves never interleave; it is never the manager or engine lock). (3) On `spawn_blocking`, under `tokio::time::timeout(SETTINGS_WRITE_TIMEOUT = 5 s)`: `config::settings::save(path, &doc, &cancel)` reads the file (missing: empty), edits it (decision 30), re-parses the result with `config::parse` and refuses unless every owned key reads back as the doc and every other key reads back as before, writes a temporary file in the same directory, fsyncs it, returns early without renaming if `cancel` is set, renames it over the original and fsyncs the directory. (4) On success, swap the live settings (decision 29) and reply `Saved`. On a timeout, set `cancel` and reply `Refused { problems: ["config.toml was not written within 5 s; nothing changed"] }`. A refused save leaves the file byte-identical and no temporary file behind.
29. **Live settings.** `daemon::live_config::LiveSettings` holds `Mutex<Arc<Live>>`, `Live { orchestrator: config::Orchestrator, origin }`. `RunContext.settings: Arc<LiveSettings>` replaces `RunContext.orchestrator`; every driver read of the orchestrator config takes `self.ctx.settings.current()` once per request (one `Arc` clone) and reads from it, so one run build sees one consistent config. A swap replaces **only the settings-owned fields** (`config::settings::apply_owned`) on the live value; every other `[orchestrator]` key stays as the daemon loaded it at start (a hand edit of, say, `worker_sandbox` still needs a restart, as today). Running runs are untouched by construction: a run freezes `limits` and `roster` at build (`run/plan.rs:165-191`, `:425`). The onboarding scout's roster (`ScoutContext.roster`) reads the live roster at each spawn (`scout/spec.rs:97`); `ProfileContext.orchestrator` keeps its start-time copy, since it reads no owned key (task 9's grep). Hard rule 3: the mutex is taken with `crate::lock`.
30. **The writer is line-based; no `toml_edit`.** `toml_edit` is not in `Cargo.lock` (only `toml`, `toml_datetime`, `toml_parser`, `toml_writer`, `Cargo.lock:2449-2490`); the spec allows adding it, but the owned key set is closed and small, and a line editor guarded by a full re-parse (decision 28 step 3) both keeps comments exactly and proves its own output, without a new dependency in the config crate that the TUI and CLI also link. The rules:
    - **Supported forms.** An owned scalar is edited only as a single-line `key = value` (optional trailing `# comment`, kept) directly under `[orchestrator]` (`builtin_models`, `max_writers`, `max_readers`, `max_bounces`, `stall_after_secs`), `[orchestrator.agent]` (`runtime`, `model`) or `[orchestrator.budget.s|m|l]` (`tool_calls`, `minutes`); the roster only as `[[orchestrator.models]]` blocks. Any owned key, or an owned table (`orchestrator.agent`, `orchestrator.budget`, `orchestrator.budget.<r>`, `orchestrator.models`), written any other way (a dotted key such as `budget.s.minutes = 5` under `[orchestrator]`, an inline table `agent = { … }`, `models = [ … ]`, a value spanning lines, an `[orchestrator.budget]` header) refuses the whole save with `<key> is written in a form the settings screen does not edit (a dotted key, an inline table or a multi-line value); edit config.toml by hand, or move it under [<table>]`. The check reads the parsed table (which keys exist) and the lines (which forms hold them).
    - **Scalars.** A supported line has only its value replaced (indentation and comment kept). A missing key is written only when its new value differs from the built-in default (so an untouched default keeps `(default)`), inserted after the last key line of its table, or, when the table has no header, under a new header appended at the end of the file. Values are written with `toml::Value`'s `Display` (strings quoted and escaped).
    - **The roster.** Every `[[orchestrator.models]]` block (its header through the line before the next header) is removed, comment lines inside it included; `builtin_models = false` is set; one block per model, in order, (`runtime`, `model`, `strength`, then `note` when not empty) goes where the first removed block was, or at the end of the file. Comments above the first block stay.
    - Everything else, byte for byte, including the file's line endings and a missing final newline.
31. **The path** is `ANTHREX_CONFIG` when set, else the default (`proto::paths::config_path()`, `proto/src/paths.rs:43`), resolved once by the CLI and passed to the daemon as `DaemonOptions.config_path` (`lifecycle.rs:21`); `RunContext` gains `config_path` from it.
32. **Shipped model lists** (`config/src/settings/shipped.rs`): `SHIPPED_CLAUDE: [ShippedModel; 3]` = `claude-haiku-4-5` fast, `claude-sonnet-5` standard, `claude-opus-5-5` frontier; `SHIPPED_CODEX: [ShippedModel; 8]` = `gpt-6.1-sol` frontier, `gpt-6-sol` standard, `gpt-6-astra` standard, `gpt-6-luna` fast, `gpt-5.6-sol` standard, `gpt-5.6-terra` standard, `gpt-5.6-luna` fast, and `""` standard labelled `Codex default`. A test pins that every `default_roster()` entry is shipped, so the built-in roster always shows as rows.

### Finishing the predicate refactor

41. **Driver checks before git.** `RunService::finish` (`driver/requests.rs:294`) calls `actions::check(run, &ActionNode::Run, &kind)` under the engine lock before any git read, and refuses at once with its text; today a non-complete run's discard first asks for confirmation and only then is refused. /// The engine event the driver sends for `kind` on `node`, with a valid input.
fn event_for(fx: &mut Fixture, node: &ActionNode, kind: &ActionKind) -> EventKind {
    let (reply, run_id) = (fx.reply(), RUN_ID.to_string());
    let edit = |edits: Vec<PlanEdit>, submit| EventKind::Edit {
        reply, run_id: RUN_ID.to_string(), edits, scope: EditScope::Run, refusals: vec![], submit,
    };
    let task = || match node { ActionNode::Task(id) => id.to_string(), _ => unreachable!() };
    match kind {
        ActionKind::Approve => EventKind::Approve { reply, run_id },
        ActionKind::Reject => EventKind::Reject { reply, run_id },
        ActionKind::Submit => edit(vec![], true),
        ActionKind::Pause => edit(vec![PlanEdit::Pause], false),
        ActionKind::Unpause => edit(vec![PlanEdit::Resume], false),
        ActionKind::Resume => EventKind::Resume {
            reply, run_id, rebaseline: Some(Rebaseline::from((BASE.to_string(), HEAD.to_string()))),
        },
        ActionKind::Cancel => EventKind::Cancel { reply, run_id },
        ActionKind::Promote => EventKind::Promote { reply, run_id, orchestrator: None },
        ActionKind::Accept => EventKind::Finish { reply, run_id, action: FinishAction::Accept },
        ActionKind::Discard => EventKind::Finish { reply, run_id, action: FinishAction::Discard },
        ActionKind::ApproveHold { hold } | ActionKind::RejectHold { hold } => {
            let approve = matches!(kind, ActionKind::ApproveHold { .. });
            fx.hold_event(reply, hold, approve) // `OrchEvent::{ApproveHold, RejectHold}` in `EventKind::Orch`
        }
        ActionKind::MessageStage { stage } => edit(vec![PlanEdit::Message {
            to: MessageTarget::Stage(u32::from(*stage)), text: "m".into(), kind: MessageKind::Info,
        }], false),
        ActionKind::Answer => edit(vec![PlanEdit::Answer { task_id: task(), text: "a".into() }], false),
        ActionKind::Message => edit(vec![PlanEdit::Message {
            to: MessageTarget::Tasks(vec![task()]), text: "m".into(), kind: MessageKind::Info,
        }], false),
        ActionKind::Refresh => edit(vec![PlanEdit::Refresh { task_id: task() }], false),
        ActionKind::Retry => EventKind::Retry { reply, run_id, task_id: task() },
        ActionKind::Override => EventKind::Override { reply, run_id, task_id: task(), reason: "r".into() },
        ActionKind::CancelTask => edit(vec![PlanEdit::CancelTask { task_id: task() }], false),
        ActionKind::ReviewPlan | ActionKind::Stats | ActionKind::OpenConversation => {
            unreachable!("client-only kinds are never request kinds")
        }
    }
}

## Risks and gotchas

1. **Keymap precedence.** Five bare-key modes now exist: screen > review > alerts > conversation > tree, and every modal (the menu included) wins over all of them because `on_key` checks the modal first. A mode left set after its state closed swallows every key; keep `screen_mode` in step with `App.screen` in one place (`app/screens.rs`), as `app/plan_review.rs` does for the review.
2. **A save that outlives its timeout.** The blocking job checks `cancel` before renaming, but a rename already under way when the timeout fires completes: the file then holds the new settings while the live config does not. The next `Get` shows the live values; a restart reads the file. Acceptable and rare (a 5 s write); documented here and in the reply text, which says nothing changed in the daemon.
3. **Hand edits between start and save.** The writer edits the file as it is on disk, so a hand edit of a non-owned key since the daemon started is kept in the file but not loaded live (decision 29). A hand edit of an owned key is overwritten by the screen's value: the screen shows the live values, not the file's. Say so in the Settings screen's help line if a user hits it (follow-up candidate).
4. **The discard reorder** (decision 41) changes what `anthrex run discard` prints on a non-complete run (a refusal at once instead of a confirmation, then a refusal). Search `cli/tests` for a test that typed an id into such a discard before changing expectations.
5. **Snapshot size.** `skip_serializing_if` keeps empty lists free, but a running run's every unfinished task now carries 3–6 `ActionInfo`s of about 150 bytes each in named MessagePack. A 50-task live run adds about 40 KiB per push, inside `MAX_FRAME`; the bound test covers complete runs only. If a live-run bound is wanted, add it under 9.0.7.
6. **`ActionKind` is internally tagged.** rmp-serde decodes internally tagged enums through `deserialize_any`, which named maps support; `ProposalState` (`#[serde(tag = "state")]`, `proto/src/profile.rs`) already relies on it. The round-trip test of task 5 is the check.
7. **Settings and the CLI.** No CLI command sends `RunRequest::Settings`; `anthrex` compiles against it (rule 4) and prints nothing new. A `anthrex config set` command is a follow-up, not this milestone.
8. **Destructive confirms take only `y`** (task 4). `Modal::Confirm` for reject, remove-task, reject-hold, kill and stop-daemon no longer confirms on Enter. Their message texts are unchanged, so the smoke's waits (`scripts/pty-smoke.py:1750-1753` waits for `Stop the daemon and kill every agent?` and sends `y`) still match; a Rust test that pressed Enter on one changes to `y` and is listed under "Implementation notes".
