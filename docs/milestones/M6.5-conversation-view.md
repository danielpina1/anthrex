## Goal

When this milestone is done, `C-b m` opens a full-area view of the focused window's
conversation: the user's prompts, the assistant's prose, each tool call folded to one line
with its name, a summary, its state and how long it took, `Enter` to unfold it into its
input and result, `Edit` and `Write` unfolding as tinted diffs, sub-agent spawns shown as
selectable rows that open that sub-agent's own conversation with a breadcrumb back, and
`/` to search prose and tool summaries. The timeline is built from hook events the daemon
already receives and is correct on its own; the runtime's transcript adds prose and full
tool detail when it can be read, and when it cannot the view says so in its footer and
keeps working. Conversations are capped from `config.toml` and the view says, in words,
when a cap dropped something. Nothing in the view can change a run.

## What the spec names that does not exist

Five places where the design spec names a thing that is not in the code. Each is resolved
by a numbered decision below rather than by writing the spec's name as though it were real.

1. **`fake-agent` is not a runtime.** Spec decision 10 gives badges to "Claude `◆`, Codex
   `◇`, shell `$`, fake-agent `·`". `proto::Runtime` has three variants and no fourth
   (`crates/proto/src/types.rs:8`); `fake-agent` is the program `ANTHREX_CLAUDE_BIN` /
   `ANTHREX_CODEX_BIN` point at, so it already renders as Claude or Codex and cannot be
   told apart on the wire. There are three badges. See decision A5.
2. **Nothing in the client detects unicode support.** Spec decision 10 says to use `[C]`,
   `[X]`, `[$]` "when the terminal reports no unicode support". `grep -rn "utf8\|UTF-8\|LANG"
   crates/tui/src` finds nothing of the kind, and `crates/tui/src/theme.rs` uses `◌ ⠋ ○ ◆ ✓
   ✕` unconditionally. This brief specifies the mechanism. See decision A5.
3. **`subprocess` is not a file reader.** Spec §7 says transcript reading sits "on the same
   hardened `subprocess`/timeout discipline the worktree code uses". `daemon::subprocess`
   runs child processes; a transcript is a file, and spawning `cat` to read it would be
   worse in every respect. The *discipline* transfers (`spawn_blocking`, a byte cap, a
   deadline, no lock held across it); the module does not. See decision A6.
4. **`Turn.at: SystemTime` is not the shape this protocol uses for absolute time.** Spec
   §4's struct writes `at: SystemTime`. Nothing on this wire carries a `SystemTime`;
   `WindowInfo` uses `since_secs`/`started_secs` (relative) and `state::WindowRecord` uses
   `created_at` (absolute Unix seconds). See decision A2.
5. **The spec's list of free prefix letters is wrong.** Spec §6 says "The free single
   letters at the time of writing are `a b e f g h i m n p u v`". `n` is `NextWindow` and
   `p` is `PrevWindow` (`crates/tui/src/keymap.rs`). The spec's actual choice, `m`, **is**
   free — checked against the full bound set in "Starting point" — so the binding stands;
   only the list around it is stale. Nothing to change beyond not trusting that list.

Two further gaps the spec leaves open rather than gets wrong, both settled below: §4's
`Block::ToolCall` has no field for the duration its own §6 mock renders (`✓ 0.3s`), and §5
names `DaemonMsg::ConversationDelta { .. turns: Vec<TurnPatch> }` without defining
`TurnPatch`. Decisions A2 and A3.

One sentence of §6 is out of scope rather than wrong: "During a run it opens on the
orchestrator by default." A *run* is milestone 8's concept and does not exist yet, so the
view opens on the focused window, full stop. When milestone 8 lands runs, it adds the
default; nothing here has to change for it to.

## Scope

In scope:

- `proto::conversation`: the model, `TurnPatch`, `DegradeReason`, and the five new messages.
  `PROTO_VERSION` 6.
- `anthrex hook` forwarding a **bounded** `tool_response` instead of stripping it.
- `[conversation]` and `[conversation.badges]` in `config.toml`.
- The daemon's conversation store: turns built from hooks, revisions, deltas, caps, and
  one conversation per (window, sub-agent).
- Transcript parsers for Claude and Codex behind one trait, driven by **captured golden
  fixtures**, with every failure degrading rather than failing.
- The transcript reader: tailing a file another process is appending to, on the blocking
  pool, only while someone is subscribed, plus a linger.
- The TUI view: badges, turns, folding, diffs, sub-agent descent with a breadcrumb, search,
  and the degradation and cap footers.
- `fake-agent` writing a transcript, so the whole pipeline runs in CI with no model.
- One smoke stage.

Out of scope: everything in the Header's "Out of scope" row.

## Design decisions

Spec decisions keep the spec's own numbers (1–11) so a reviewer can trace each one back.
Decisions this brief adds are lettered `A1`–`A13` and are **this brief's**, not the spec's;
each says why.

### The model and the protocol

**1. Hooks are authoritative; transcripts enrich.** (Spec decision 1.) The timeline,
ordering, turn boundaries and tool state come from hooks alone. A transcript record may
only *fill in* `Block::Text.text`, `Block::ToolCall.input` and `ToolResult.detail` on a
turn that already exists. Enrichment may never create, reorder, remove or re-state a turn,
and may never change a `ToolState`. This is a property, and task M6.5.8's tests assert it
by feeding records that would do each of those things and checking the timeline is
unchanged.

**2. A conversation degrades; it never fails.** (Spec decision 2.) Every transcript problem
— absent file, unreadable file, unknown format, a line that is valid JSON of the wrong
shape, a truncated final line, a file too large — sets `Conversation.degraded` and leaves
the hook-built timeline intact and rendering. No transcript problem may blank the view,
panic the daemon, return an `Err` to a client, or stall a run. The reason is logged at
`warn` **once per conversation per distinct reason**, not per line: the store keeps
`logged: Option<DegradeReason>` and logs only when the reason changes.

**3. One parser per runtime, version-tagged.** (Spec decision 3.) `transcript::claude` and
`transcript::codex`, both behind `TranscriptParser` with
`detect(&self, first_line: &str) -> Option<Version>`. An unrecognised first line yields
`DegradeReason::UnknownFormat`; nothing guesses. `Runtime::Shell` has no parser at all.

**4. Blocks, not lines.** (Spec decision 4.) The model carries structure; the view derives
rows from it. Row indices are a rendering detail and are never stored — see decision A10.

**5. `summary` is always present; `input` and `detail` are not.** (Spec decision 5.)
`Block::ToolCall.summary` is derived daemon-side from the hook's `tool_name` and
`tool_input`, both of which every `PreToolUse` carries, so a fully degraded conversation
still reads as `Edit parse.rs — 1 hunk` rather than as a blank. Task M6.5.4 fixes the
summary for every tool exactly.

**5a. `anthrex hook` sends a bounded tool result instead of stripping it.** (Spec decision
5a, confirmed against `crates/cli/src/hook.rs:97` for this brief.) The strip is replaced by
a truncation to `TOOL_RESULT_SUMMARY_MAX` (4 KiB) plus two new top-level flags,
`tool_result_truncated: bool` and `tool_result_stringified: bool` (the second added by task
M6.5.2's wave-1 review, finding F2: an over-limit JSON *object* keeps its own shape by
shrinking its string leaves rather than collapsing straight to a string, since collapsing
loses the `error`/`success` keys `ToolResult.ok` reads; the flag distinguishes that rare,
structure-losing fallback from ordinary truncation). The existing `HOOK_PAYLOAD_MAX` (8 MiB)
guard is untouched and still runs first, on the raw stdin bytes, before the JSON is parsed —
so a payload over 8 MiB is still dropped whole, exactly as today. What changes is only what
a payload *under* that limit carries onward. Task M6.5.2 gives the exact truncation rule.

**6. A sub-agent spawn is a block in its parent's conversation.** (Spec decision 6.) It
carries the `agent_id` of the existing milestone 3 sub-agent record. Selecting it opens that
sub-agent's conversation. Nesting is a link, not a tree.

**7. Conversations are capped.** (Spec decision 7.) `[conversation] max_turns` (500),
`max_bytes` (2 MiB) and `max_result_bytes` (16 KiB), from `config.toml`. Turns drop from the
front, `dropped_turns` counts them, and the view shows the count **and names the key that
caused it** — decision A9.

**8. A revision counter, not an event stream.** (Spec decision 8.) A client subscribing with
`from_rev` gets a `ConversationDelta` when the daemon still holds that revision and a
`ConversationSnapshot` otherwise. Decision A3 fixes how much history "still holds" means.

**9. One subscription per (window, sub-agent), independent of the PTY subscription.** (Spec
decision 9, narrowed by decision A1.) Reading a conversation does not attach you to its
terminal and attaching does not start parsing a transcript. The daemon reads a transcript
only while at least one client is subscribed to some conversation of that window, plus
`conversation.linger_secs` (30 s) so switching views does not re-parse.

**10. Runtime badges, not brand marks.** (Spec decision 10, amended by decision A5.) A badge
is a glyph and a colour, per runtime, from `[conversation.badges]`. Colour alone never
carries meaning: the badge's glyph is always drawn.

**11. The view is read-only.** (Spec decision 11.) No key in the view sends `Input`,
`Kill`, `Restart`, `Remove` or `Rename`. The only messages it can produce are
`SubscribeConversation` and `UnsubscribeConversation`. Task M6.5.12's acceptance criteria
assert this by enumerating every effect the view can emit.

### Decisions this brief adds

**A1 — A conversation is keyed by `(window_id, agent_id)`, and `agent_id` travels on the
wire.** *This brief's.* Spec §5 writes `SubscribeConversation { window_id, from_rev }`, but
spec §6 also requires `Enter` on a sub-agent spawn to open that sub-agent's conversation,
and the daemon receives a sub-agent's hooks on the *parent's* `window_id` with `agent_id`
set — there is no second window to address. Three ways out were considered: put every
sub-agent's turns in the parent's `turns` (destroys "the orchestrator's conversation", which
is what the view opens on by default); send a map of conversations in one snapshot (sends
fifty sub-agents' turns to show one); or key by `(window_id, agent_id)`. The third is
chosen. `agent_id: Option<String>` is added to both client messages, all three daemon
messages, and `Conversation` itself; `None` is the window's own root agent. Decision 9's
"one subscription per window" becomes one per key, and a client may hold several — the
breadcrumb needs the parent's conversation to still be there when `Esc` returns to it.

**A2 — `Turn.at_unix_secs: u64`, and `Block::ToolCall` gains `duration_ms: Option<u32>`.**
*This brief's.* Spec §4 writes `at: SystemTime`, which serialises over MessagePack as a
two-field struct nothing else in this protocol uses, and which a client cannot render as
`09:42` without knowing it is absolute. `state::WindowRecord.created_at` already established
absolute Unix seconds as this repo's on-wire absolute time, so `at_unix_secs` carries the
same information in the shape the codebase already has. Separately, spec §6's own mock
renders `✓ 0.3s` and `✓ 1.1s` beside tool calls while spec §4's `Block::ToolCall` has no
field to hold that; `duration_ms: Option<u32>` is added, filled from the wall-clock gap
between a tool's `PreToolUse` and its `PostToolUse`, and `None` while the call is `Pending`.

**A3 — `TurnPatch` is whole-turn, and the daemon keeps `DELTA_HISTORY = 64` revisions.**
*This brief's;* spec §5 names `TurnPatch` without defining it.

```rust
pub enum TurnPatch {
    Upsert(Turn),
    Drop { id: u64 },
}
```

Whole-turn, not per-block: a turn is already bounded (`max_result_bytes` per result,
`max_bytes` per conversation), and per-block patching multiplies the states a client can be
in without bounding anything further. The daemon keeps the last 64 revisions' patch batches
per conversation in a ring; a `from_rev` older than the oldest retained, or newer than the
daemon's own `rev`, gets a full `ConversationSnapshot` instead. 64 is this brief's number:
at one revision per hook event it covers roughly a minute of a busy agent, which is far
longer than the gap a view switch or a redraw can open, and a miss costs one snapshot, not
correctness.

**A4 — `ConversationDelta` carries `degraded` and `dropped_turns`.** *This brief's.*
Degradation can change with no turn changing at all (a transcript that becomes unreadable
mid-session), and `dropped_turns` changes on exactly the revisions that carry a
`TurnPatch::Drop`. A delta that omitted both would let a client's footer go stale while its
turns stayed current — which is decision 2's "degradation is visible, never silent" failing
quietly. The fields are on the message, not inferred by the client.

**A5 — Three badges, and ASCII is chosen by an explicit setting or an explicitly non-UTF-8
locale.** *This brief's;* see "What the spec names that does not exist" items 1 and 2.
There are three runtimes, so three badges: Claude, Codex, Shell. Their glyphs, ASCII forms
and colours are `[conversation.badges]` keys with the spec's glyphs (`◆`, `◇`, `$`) and
ASCII forms (`[C]`, `[X]`, `[$]`) as defaults; the colours have no spec value and are this
brief's (task M6.5.3's table). ASCII is used when `conversation.badges.force_ascii` is
`true`, **or** when the first set and non-empty value of `LC_ALL`, `LC_CTYPE`, `LANG` does
not contain `utf-8` or `utf8` case-insensitively. When none of those variables is set,
unicode is used — because the rest of the TUI already draws `◌ ⠋ ✓ ✕` unconditionally
(`crates/tui/src/theme.rs`), so an absent locale switching only the badges to ASCII would
produce a half-ASCII screen, which is worse than either whole. The env read happens in
`crates/cli/src/main.rs`; the decision itself is the pure function
`tui::ui::badge::prefers_ascii(force_ascii: bool, locale: Option<&str>) -> bool`.

**A6 — Transcript reading is `spawn_blocking` plus a byte cap plus a deadline, not
`daemon::subprocess`.** *This brief's;* see "What the spec names that does not exist" item
3. The spec's intent — an untrusted file another process is writing, read without holding
any lock and without an unbounded appetite — is carried by: the read runs on
`tokio::task::spawn_blocking` (AGENTS.md hard rule 2); one pass reads at most
`TRANSCRIPT_READ_BUDGET` (1 MiB) of new bytes; a pass is abandoned at
`TRANSCRIPT_READ_TIMEOUT` (2 s); a file over `TRANSCRIPT_MAX_BYTES` (64 MiB) is not read at
all and degrades with `TooLarge`; a single line over `TRANSCRIPT_LINE_MAX` (4 MiB) is
skipped and degrades with `BadRecord`; the manager lock is never held across any of it.
`grep -rn "subprocess" crates/daemon/src/transcript/` must find nothing — it is a
verification check.

**A7 — A truncated final line is "not yet", never corruption; a shrunken file is a restart.**
*This brief's,* making spec risk 2 operational. The reader keeps a `partial: String` of the
bytes after the last `\n` and never parses it; the next pass prepends it. If the file's
length is **less** than the reader's saved offset, the file was rewritten or rotated: the
reader resets `offset = 0`, clears `partial`, re-runs `detect`, and the store discards its
enrichment (not its hook-built turns — decision 1) and re-enriches from the start.

**A8 — Sub-agent conversations are capped by count, derived from `MAX_SUBAGENTS`.** *This
brief's.* `MAX_CONVERSATIONS_PER_WINDOW: usize = daemon::subagents::MAX_SUBAGENTS + 1` — the
tracker already refuses to hold more than 50 sub-agents, so 51 is the most conversations a
window can legitimately need. Written as that expression, not as `51`: a bound must be
derived from the constant it wraps (`docs/timing-budgets.md` standing rule 1, which is about
arithmetic relationships, not only about time). A hook for an agent id beyond the cap is
applied to the root conversation instead of creating a 52nd, and is logged at `debug` once.

**A9 — What the user sees when a cap bites.** *This brief's,* sharpening spec decision 7.
Silence is the failure mode to avoid, so each cap has a visible, worded consequence:

| Cap | What the view shows |
|---|---|
| `max_turns` or `max_bytes` trimmed turns | A first row, above everything: `⋯ {n} earlier turns dropped (conversation.max_turns)` — or `(conversation.max_bytes)` when the byte cap is what trimmed. `{n}` is `Conversation.dropped_turns`. |
| `max_result_bytes` truncated a result | The unfolded result's last line is `⋯ truncated (conversation.max_result_bytes)`, drawn in `theme::muted()`. Folded, the tool row's state glyph is unchanged — truncation is not failure. |
| `TOOL_RESULT_SUMMARY_MAX` truncated a hook-delivered result | Identical to the row above, because `ToolResult.truncated` is the one flag and either truncation sets it. |
| The conversation is degraded | A last row: `⚠ {reason}`, from `DegradeReason::message()`. |

A conversation is never trimmed to zero turns: if one turn alone exceeds `max_bytes` it is
kept and logged once at `warn`, because a blank view is what decision 2 exists to prevent.
Which cap bit is carried by `Conversation.dropped_by: Option<DropCause>` (`Turns` | `Bytes`),
so the row can name the right key.

**A10 — The view's fold set is keyed by `(turn_id, block_index)`, never by row index.**
*This brief's.* Rows are derived from the conversation on every frame and shift whenever a
delta lands or a turn is dropped; a fold set keyed by row index would silently unfold a
different tool call the moment the agent produced another turn. `BTreeSet<(u64, usize)>`.
The same rule applies to the selection, which is stored as a `Cursor` (decision A11), not as
a row number.

**A11 — Selection is stored as a stable cursor and resolved to a row each frame.** *This
brief's,* for the same reason as A10.

```rust
pub enum Cursor {
    Turn(u64),
    Block(u64, usize),
    Dropped,
    Degraded,
}
```

`ConversationView::rows()` returns `Vec<Row>`; `selected_row()` finds the row matching the
cursor, or the nearest following row when the cursor's target has been dropped, or the last
row when nothing follows.

**A12 — A delta the client cannot apply forces a resubscribe, it does not diverge.** *This
brief's.* If a `ConversationDelta`'s `from_rev` does not equal the view's current `rev`, the
view discards the delta and emits
`Send(SubscribeConversation { window_id, agent_id, from_rev: None })`, which the daemon
answers with a full snapshot. A client that applied an out-of-order delta would show a
conversation that never existed, and nothing downstream would ever notice.

**A13 — Transcript formats are captured from the real binaries, never invented.** *This
brief's,* and the one non-negotiable rule in task M6.5.7. Neither runtime's transcript JSONL
is documented, and no fixture for either exists in this repository today. The implementer
**runs the real `claude` and the real `codex`, captures their transcripts, redacts them, and
commits them as golden fixtures**, then writes each parser against the fixture it actually
has — exactly the way milestone 6's task M6.6 required `codex resume --help` to be run and
its output recorded rather than assumed. If a binary is not installed, that parser's
`detect` returns `None` for every input, a test asserts the resulting conversation degrades
with `UnknownFormat` and still renders, and the gap is recorded under "Implementation notes"

### M6.5.2 `anthrex hook` forwards a bounded tool result

**Files.** Modify `crates/cli/src/hook.rs` and `crates/cli/tests/hook_command.rs`.

**The exact rule.** Replace `object.remove("tool_response")` with a type-preserving bound.
Amended from the original strip-or-keep pseudocode by wave-1 review finding F2: a truncation
must never silently turn a failed tool into a successful one, and letting an over-limit JSON
*object* collapse straight into a JSON *string* does exactly that — M6.5.5's `ok` predicate
(below) only inspects an object's `error`/`success` keys, so an object standing in for a
string reads as `ok == true` no matter what it said.

For the extracted `tool_response` value:

```
match value {
    String(s) => {
        if s.len() <= TOOL_RESULT_SUMMARY_MAX {
            keep it; "tool_result_truncated": false, "tool_result_stringified": false
        } else {
            replace with the first TOOL_RESULT_SUMMARY_MAX bytes of s's own raw UTF-8
            content — not serde_json::to_string(&s)'s JSON-quoted form — truncated back
            to the nearest char boundary;
            "tool_result_truncated": true, "tool_result_stringified": false
        }
    }
    Object(map) => {
        if serde_json::to_string(&map) fits within TOOL_RESULT_SUMMARY_MAX {
            keep it unchanged; both flags false
        } else {
            repeatedly find the single longest string value anywhere in the object
            (walking arrays and nested objects too) and shrink it — by however many
            bytes the whole re-encoded object is still over budget, backed off to the
            nearest char boundary — until the object's compact encoding fits. Stays an
            object. "tool_result_truncated": true, "tool_result_stringified": false.

            If every string leaf is empty and it still does not fit (the object's own
            skeleton of keys, braces and non-string values already exceeds the bound —
            a pathological key count), fall back: JSON-encode the original, untouched
            object, truncate that text to the nearest char boundary at
            TOOL_RESULT_SUMMARY_MAX, wrap it as a plain string.
            "tool_result_truncated": true, "tool_result_stringified": true.
        }
    }
    other (Array, Number, Bool, Null) => {
        // no predicate downstream reads these, so no structure to protect
        if serde_json::to_string(&other) fits within TOOL_RESULT_SUMMARY_MAX {
            keep it unchanged; both flags false
        } else {
            replace with the first TOOL_RESULT_SUMMARY_MAX bytes of its JSON encoding,
            truncated back to the nearest char boundary, as a plain string.
            "tool_result_truncated": true, "tool_result_stringified": false
        }
    }
}
```

`tool_result_truncated` and `tool_result_stringified` are inserted **together, always**, both
at the payload's top level, overwriting any keys of those names the runtime happened to send
— but only when `tool_response` was present in the payload to begin with; a payload with no
`tool_response` (`SessionStart`, `UserPromptSubmit`, …) is untouched, keys and all. They must
be present whenever `tool_response` is, so the daemon can tell an old CLI (keys absent) from
an untruncated/unstringified result (keys `false`) — see `ParsedHook.tool_result_truncated`
and `ParsedHook.tool_result_stringified`'s three cases each.

```rust
/// Spec decision 5a: the bound on what one hook may carry back about a tool's result. Well
/// under `HOOK_PAYLOAD_MAX` (8 MiB, above), which still runs first on the raw stdin bytes
/// and is untouched by this — an over-8-MiB payload is still dropped whole. Also
/// `<= config::CONVERSATION_MAX_RESULT_BYTES_MIN` (amendment, review finding F3: the
/// original comment claimed this against only the *default* `conversation.max_result_bytes`
/// (16 KiB), which is false at the legal minimum — `max_result_bytes = 2048` was in range
/// before this amendment, and a 4096-byte hook result would trip it). Not yet compiled as a
/// static assertion here because `crates/config` does not define `[conversation]` until
/// task M6.5.3, which raises that range's floor to 4096 and adds
/// `const _: () = assert!(TOOL_RESULT_SUMMARY_MAX as u64 <=
/// config::CONVERSATION_MAX_RESULT_BYTES_MIN);` here to keep the two compiled together from
/// then on — see that task's acceptance criteria.
const TOOL_RESULT_SUMMARY_MAX: usize = 4 * 1024;
```

A `String` value is truncated on its own raw UTF-8 content, not on
`serde_json::to_string(&value)`'s JSON-quoted form. The reason is semantic: the field carries
the result's *text*, so the text is what gets truncated — matching M6.5.5's `summary` rule
below, which truncates the same field the same way. (This reasoning replaces an earlier, wave-
1-reviewed draft that argued from byte parity instead: a leading JSON quote shifts every
following multi-byte character off an even offset, which happens to distinguish the two
readings for a run of 2-byte characters like `é`, and inverts for a run of 3-byte characters
like `世`. The semantic argument holds regardless of character width; the parity argument does
not, and is not the reason for this choice.)

### M6.5.6 The store: revisions, deltas and caps

**Files.** Create `crates/daemon/src/conversation/store.rs` (or put `ConversationSet` in
`mod.rs` if both stay under 600 lines) and
`crates/daemon/src/conversation/store_tests.rs`.

**The exact rules.**

- `Turn.id` is assigned per conversation, monotonically, starting at 1, and is never
  reused — including after a trim, so a `TurnPatch::Drop { id }` can never be confused with
  a later turn. It is a `u64`; a conversation cannot produce enough turns to exhaust it.
  `dropped_turns` is a `u32` and saturates rather than wrapping.
- `rev` starts at 0. Each `on_hook`/`enrich`/`set_degraded`/`reset_enrichment` call that
  changes a conversation increments that conversation's `rev` by exactly 1 and records one
  patch batch. A call that changes nothing increments nothing and returns an empty key list.
- A patch batch holds a `TurnPatch::Upsert` for every turn that was created or modified in
  that revision, and a `TurnPatch::Drop { id }` for every turn the cap trimmed.
- After every change, while `turns.len() > caps.max_turns || byte_size() > caps.max_bytes`
  **and** `turns.len() > 1`, remove `turns[0]`, increment `dropped_turns`, set `dropped_by`
  to `Turns` or `Bytes` according to which predicate was true (checking `max_turns` first),
  and append a `Drop` patch. If the loop ends with one turn still over `max_bytes`, the turn
  is kept and the set records `oversize_logged` so the caller logs once at `warn` — decision
  A9's "never trimmed to zero".
- The patch ring holds `DELTA_HISTORY` batches. `delta_since(agent_id, from_rev)` returns
  `None` when `from_rev > rev`, when `rev - from_rev > DELTA_HISTORY`, or when the key is
  unknown; otherwise it concatenates the batches for revisions `from_rev + 1 ..= rev`,
  keeping only the **last** `Upsert` per turn id and dropping an `Upsert` for a turn a later
  `Drop` removed.
- A new key is created on the first hook that names it, up to
  `MAX_CONVERSATIONS_PER_WINDOW`; beyond that the hook is applied to the `None` conversation.

- `a_delta_replays_to_the_same_state_as_a_snapshot`: drive 12 hooks. Take a snapshot at

- `an_old_rev_gets_no_delta`: with `DELTA_HISTORY` at 64, drive 70 revisions and assert

- `the_turn_cap_drops_from_the_front_and_counts`: `caps.max_turns = 4`. Drive 6

### M6.5.8 `enrich.rs`: records onto the timeline

**Files.** Create `crates/daemon/src/conversation/enrich.rs` and

**The exact rules.** `enrich::apply(draft, records)` may do exactly three things and nothing
else:

1. `Record::UserText { ordinal, text, .. }` replaces the text of the `ordinal`-th `User`
   turn's first `Text` block, counting `User` turns from the front of the current (possibly
   trimmed) turn list. Out of range: ignored.
2. `Record::AssistantText { ordinal, text, .. }` sets the text of the `ordinal`-th
   `Assistant` turn's `Text` block, **inserting** a `Text` block at the front of that turn's
   blocks when it has none. Out of range: ignored.
3. `Record::ToolDetail { tool_use_id, input, detail, ok }` finds the `ToolCall` block in any
   turn whose `id == Some(tool_use_id)` and, when found, sets `input` (if the record's is
   `Some`), sets `result.detail` (if the record's is `Some` **and** `result` is already
   `Some`), and — **only when `result` is `None`** — does nothing with `ok`. It never changes
   `ToolState`, never sets `result` on a call that has none, and never changes `summary`. No
   match: ignored.

A `detail` longer than `caps.max_result_bytes` is truncated at a char boundary and sets
`result.truncated = true`.

**The bounds, each derived from what it wraps** (`docs/timing-budgets.md` standing rule 1).
`TRANSCRIPT_POLL` lives in `crates/daemon/src/conversation/watch.rs` (it is the task's
interval); the other three live in `crates/daemon/src/transcript/reader.rs` (they bound the
read itself). Anything citing one of them cites the file it lives in.

```rust
/// One pass over the file, on the blocking pool. Generous against a slow disk; a pass
/// that exceeds it returns what it has and the next poll continues from the same offset,
/// so overrunning costs latency, never correctness.
pub const TRANSCRIPT_READ_TIMEOUT: Duration = Duration::from_secs(2);
/// How often a subscribed conversation's transcript is re-read.
pub const TRANSCRIPT_POLL: Duration = Duration::from_millis(250);
/// The most new bytes one pass consumes. An overnight run's transcript is tens of MiB;
/// this keeps any one pass bounded while the poll interval keeps the view current.
pub const TRANSCRIPT_READ_BUDGET: usize = 1024 * 1024;
/// A file larger than this is not read at all: `DegradeReason::TooLarge`.
pub const TRANSCRIPT_MAX_BYTES: u64 = 64 * 1024 * 1024;
/// One line larger than this is skipped: `DegradeReason::BadRecord`. Sixteen times
/// `TOOL_RESULT_SUMMARY_MAX`'s 4 KiB is not the relationship here — a transcript line
/// can legitimately hold a whole file's contents — so this is bounded by memory, not by
/// a sibling constant.
pub const TRANSCRIPT_LINE_MAX: usize = 4 * 1024 * 1024;
```

The **linger** is `config.conversation.linger_secs` (30 s default), not a literal. The
reader's own stop deadline must exceed one poll plus one read: assert in a doc comment that
`linger_secs` may legitimately be 0, in which case the reader stops after the pass in
flight finishes, never mid-pass.

### M6.5.12 The view state: folding, selection, search and sub-agent descent

**Files.** Create `crates/tui/src/conversation.rs` and

**The exact keys**, handled by `ConversationView::on_key` while the view is open and no
modal is:

| Key | Effect |
|---|---|
| `j`, `Down` | Move the cursor to the next row. |
| `k`, `Up` | Previous row. |
| `g` | First row. `G` last row. |
| `Enter`, `o` | On a `Tool` row: toggle its fold. On a `Spawn` row: descend. Elsewhere: nothing. |
| `Esc` | While searching: leave search, keeping the cursor. Else with a non-empty trail: pop one crumb. Else: close the view. |
| `q` | Close the view outright, whatever the trail. |
| `/` | Start search: `Search { typing: true, query: "" }`. |
| printable, `Backspace` (while `typing`) | Edit the query; hits recompute on every keystroke. |
| `Enter` (while `typing`) | Commit: `typing = false`, cursor moves to the first hit. |
| `n`, `N` (while a committed search exists) | Next / previous hit, wrapping. |
| anything else | Nothing. **No key sends anything but `SubscribeConversation` / `UnsubscribeConversation`** — spec decision 11. |

Descending pushes `Crumb { agent_id, label }` taken from the `SubagentSpawn` block, emits
`Send(SubscribeConversation { window_id, agent_id: Some(id), from_rev: None })`, and clears
the fold set, the search and the cursor. It does **not** unsubscribe the parent — `Esc` must
return to a live parent conversation. Popping a crumb emits
`Send(UnsubscribeConversation { window_id, agent_id: Some(popped) })` and restores the
parent's key as the view's current key. Closing the view emits one
`UnsubscribeConversation` per key on the trail plus the root's.

`Search` matches case-insensitively against `Block::Text.text` and
`Block::ToolCall.summary` only — not against inputs, results or notices, which is what spec
§6 says.

## Testing

Spec §11 sketches this; this section is the actionable form. The project's hard-won rule
governs all of it: **a defect is found by constructing an input and running it, not by
reading code.** The M6 spec-gap audit (2026-09-22, recorded in
`docs/superpowers/plans/2026-09-17-anthrex-foundation-followups.md`) found three real gaps
that two prior readings had missed, and every one was found by constructing an input — a
config file with a `[git]` table, a `StateFile` handed to `restore`, an `App` with its view
moved. "Add tests for X" gets tests that cannot fail; each task above therefore names the
inputs to construct.

**What is pure and tested with plain values, no daemon and no files:**
`conversation/summary.rs`, `conversation/build.rs`, `conversation/enrich.rs`,
`conversation/store.rs`, both transcript parsers' `record`/`detect`,
`tui/src/conversation.rs`, `tui/src/ui/badge.rs`, `tui/src/ui/conversation/diff.rs`.

**What needs a real file:** `transcript/reader.rs`. Its tests construct files: a truncated
final line, a missing file, a directory, an unknown first line, a wrong-shaped line, an
oversized file, an oversized line, a file being appended to from another thread while it is
read, and a file truncated mid-session. Each must yield a rendering conversation with
`degraded` set — that assertion is the point, not merely that nothing panicked.

**What needs the daemon:** `crates/daemon/tests/conversation.rs`, driving a real
`WindowManager` and a real socket.

**What needs the real `anthrex` binary:** `crates/cli/tests/conversation.rs`, because hooks
arrive through `anthrex hook`.

**What needs a real terminal:** the smoke stage.

**Golden fixtures are the contract.** The two committed transcripts are the only statement
in this repository of what either runtime's format is. A new runtime version arrives as a new
fixture and a new `Version`, never as a change to an existing parser's behaviour for an
existing version. The fixture must contain same-typed records with **different** values, or
no transposition between them can fail a test — this is the failure that has recurred three
times in this project.

**Three test shapes this milestone forbids**, because each has shipped here before:

1. *Asserting through a private helper.* `crates/tui/src/ui/conversation_tests.rs` asserts on
   the `TestBackend` buffer's cells — text and style — not on a function that computes what
   the renderer "would" draw.
2. *Asserting on output the harness swallows.* The smoke stage reads the reconstructed
   screen, not the subprocess's stdout.
3. *Asserting a property weaker than the test's name claims.* `enrichment_never_creates_-
   reorders_or_removes_a_turn` asserts turn ids, order, count, roles, turn states **and**
   tool states — not merely that the turn count is unchanged.
   `a_delta_replays_to_the_same_state_as_a_snapshot` compares whole conversations, not
   lengths. `defaults_match_decision_4s_table` in `settings.rs` is the cautionary example:
   it once read `assert_eq!(f(x), f(x))` and passed for every possible body of `f`.

**Every wall-clock bound** in this milestone — `TRANSCRIPT_READ_TIMEOUT`, `TRANSCRIPT_POLL`,
the linger, and `CONVERSATION_VIEW_TIMEOUT` — is written as an expression over the constants
it wraps, or, across the Rust/Python boundary, as a comment doing that arithmetic explicitly.
No test may assert a deadline numerically equal to the budget it bounds. Read
`docs/timing-budgets.md` before writing a new one.

## Risks and gotchas

1. **Transcript formats change without warning** (spec risk 1). Decisions 1 and 2 are the
   containment: when it happens the prose is lost and the timeline survives, visibly. The
   golden fixtures make the change obvious rather than silent. Do not "fix" a detection
   failure by loosening `detect` until it matches — capture a new fixture and add a `Version`.
2. **Reading a file another process is writing** (spec risk 2). A partial final line is
   normal. Decision A7 is the rule; `a_truncated_final_line_is_held_not_parsed` is the test.
   Never take a lock on the file, and never hold the manager lock across the read.
3. **Memory** (spec risk 3). Decision 7 caps it. The cap is checked after every change, not
   periodically — a periodic sweep is an unbounded interval of unbounded growth.
4. **Parsing cost on a busy run** (spec risk 4). Decision 9 limits reading to subscribed
   conversations, so a run nobody is watching costs nothing. `the_reader_runs_only_while_-
   subscribed` is the test; without it this is an easy property to lose in a later refactor.
5. **A fold or a cursor keyed by row index.** Decisions A10 and A11 exist because rows shift
   on every delta. The two tests that catch it are
   `the_fold_set_survives_a_turn_being_dropped` and
   `the_cursor_survives_a_delta_that_inserts_a_turn`; if either is ever "simplified" away,
   the bug returns silently — the wrong tool call unfolds and nothing errors.
6. **`handle_hook` is keyed by window id with no per-spawn tag** (milestone 6's accepted
   residual). A hook from a replaced process can land on its successor, and now that means it
   can land in its successor's conversation. This milestone does not fix it — the real fix is
   a protocol-level generation counter — but a restarted window's conversation may briefly
   show a turn from its predecessor. Record it if you see it; do not invent a heuristic.
7. **The daemon's own `Instant`s are not the client's.** `duration_ms` is computed
   daemon-side from two `Instant`s; `at_unix_secs` is `SystemTime`-derived. Do not mix them:
   a duration derived by subtracting two `at_unix_secs` values would have one-second
   granularity and could go negative across a clock adjustment.
8. **A conversation is not persisted.** After a daemon restart a restored window's
   conversation is empty until new hooks arrive — its transcript is still on disk, but the
   hook timeline that gives it turns is not, and decision 1 forbids the transcript creating
   turns. That is correct behaviour for this milestone, and the restored window's
   conversation shows `NoTranscriptPath` until its first hook. Do not "fix" it by letting
   enrichment create turns; that is decision 1, and milestone 8 is where persisted runs get
   their own answer.
9. **Three model variants have no producer in this milestone**, all deliberately:
   `Role::System`, `NoticeKind::Error` and `NoticeKind::Compaction`. They are spec §4's own
   variants and exist for milestone 8's run notices and for a runtime that starts reporting
   compaction; the only `Notice` this milestone produces is `PermissionRequest`.
   `every_hook_kind_is_handled` asserts nothing here produces a `System` turn, so a future
   change that starts producing one has to say so rather than slipping in. Do not delete the
   unused variants to satisfy a lint — they are wire shape, and removing one is a protocol
   change.
10. **Two smoke-stage traps.** `ENV["FAKE_AGENT_TRANSCRIPT"]` must not be set globally: every
    earlier stage's fake agent would then start inserting `transcript_path` into payloads
    those stages assert on. Set it only for the new stage's own script run. And
    `ensure_config_path_absent` at the top of the script depends on `ANTHREX_CONFIG` pointing
    at a file that does not exist — do not create one for this stage.
11. **The read-only limit may chafe** (spec risk 5). If watching without being able to
    redirect turns out to be the wrong call, decision 11 is the cheapest thing here to
    reverse — the protocol already addresses windows by id, and the view already knows the
    window it is showing. Do not pre-build for it: an unused write path is a surface with no
    test behind it. Record the friction instead.
12. **Clippy on a large enum.** `Block` with a `serde_json::Value` and a `ToolResult` will
    trip `clippy::large_enum_variant` on some versions. Box the largest variant's payload
    rather than adding an `allow`, and keep the wire shape identical by boxing behind
    `#[serde(flatten)]`-free plain fields — a `Box<T>` serialises exactly as `T`.

### Amendments to the decisions in this brief

- **Task M6.5.1, `Block::byte_size` for `ToolCall` counts `id`.** The Interfaces
  section's original prose (and task M6.5.1's original acceptance criterion) excluded
  `id` from the byte count, on the theory that it is a correlation token rather than
  user-visible content. That reasoning does not hold: `byte_size` feeds `[conversation]`'s
  `max_bytes` cap, and `id` is `tool_use_id`, a string from the runtime's own hook
  payload — its length is set by the runtime, not by us. Excluding it makes the cap an
  under-estimate, which is unbounded (an over-estimate merely makes the cap bite a
  little early). Measured: a `ToolCall` block with `id: Some("x".repeat(100_000))` and
  every other field empty/`None` encodes to 100,129 bytes via `rmp_serde::to_vec_named`;
  the pre-amendment formula (excluding `id`) reported a `byte_size()` of 96.
  `id.as_ref().map(|s| s.len()).unwrap_or(0)` is now added alongside `name`/`summary`/
  `input`/`result`'s lengths. Reviewed and fixed in wave 1 of task M6.5.1 (finding F2).
- **Task M6.5.1, `TURN_OVERHEAD`/`BLOCK_OVERHEAD` raised from 64/32 to 80/144.** The
  original values were typed independently of what they stand for and measured 23%
  under the worst case they had to cover: an empty `ToolCall` turn (every field absent
  or `None`) encodes to 125 bytes via `rmp_serde::to_vec_named` against a reported
  `byte_size()` of 96. `byte_size` feeds the same `max_bytes` cap as above, so this was
  the same under-estimate defect as F2, one level up. The new values are derived from
  measuring the worst case directly — a `ToolCall` block with a populated `ToolResult`,
  every optional field present, and every string field long enough to need the largest
  MessagePack string-length header (5 bytes), which needs 73 bytes of pure turn-level
  structure and 125 bytes of pure per-block structure — plus roughly 10–15% headroom.
  `conversation_tests.rs`'s `byte_size_never_underestimates_its_encoded_size` pins the
  actual guarantee (`byte_size() >= rmp_serde::to_vec_named(turn).unwrap().len()` for
  every `Block` variant, empty/typical/long-id) rather than these two specific numbers,
  so a future change to either constant is caught by that test regardless of its exact
  values. Reviewed and fixed in wave 1 of task M6.5.1 (finding F3).
- **Task M6.5.3's `CONVERSATION_MAX_BYTES_RANGE` upper bound, changed before task M6.5.3
  was implemented.** The Interfaces section originally typed the upper bound as a
  literal `134_217_728` (128 MiB), independent of `proto::codec::MAX_FRAME` (16 MiB) —
  but `DaemonMsg::ConversationSnapshot` carries a whole `Conversation` in one frame, so a
  legally configured `max_bytes` at or above `MAX_FRAME` could produce a conversation
  that cannot be sent at all. The Interfaces section above now derives the upper bound
  from `proto::codec::MAX_FRAME` minus a `CONVERSATION_MAX_BYTES_HEADROOM` (1 MiB,
  reserved for the snapshot envelope and for `byte_size`'s over-estimate margin against
  the tighter actual encoding), giving 15 MiB. `crates/config` already depends on
  `anthrex-proto`, so this needs no new dependency. Not yet implemented as of task
  M6.5.1 — task M6.5.3 must use the derived form, not retype a literal. Flagged in wave 1
  of task M6.5.1's review (finding F3's forward risk).
- **Task M6.5.1, `Turn::at_unix_secs`'s doc comment.** `SystemTime` *is* `Serialize` (in
  `{"secs_since_epoch": .., "nanos_since_epoch": ..}` shape), so the original comment's
  claim that it "neither `Serialize` nor portable" was wrong. The accurate reason `u64`
  was chosen over it: that shape is a two-field struct, not the single integer the
  protocol wants, and it carries nanosecond precision this model has no use for. Fixed
  in wave 1 of task M6.5.1 (finding F8); the acceptance grep for this decision was also
  narrowed from the bare string `SystemTime` (which forbade even naming the type in the
  doc comment) to the fully qualified `std::time::SystemTime` (which forbids only using
  it).
- **Task M6.5.2, an over-limit JSON *object* `tool_response` now shrinks string leaves
  instead of collapsing to a string.** The original pseudocode truncated *any* over-limit
  JSON value — object, string, or otherwise — into a plain `Value::String`. Demonstrated
  broken: `tool_response = {"error": "x".repeat(5000)}` (5012 bytes compact-encoded, over
  `TOOL_RESULT_SUMMARY_MAX`) reached the daemon as a `Value::String` holding a truncated JSON
  *fragment*. M6.5.5's `ok` predicate only reads `error`/`success` off a `Value::Object`; a
  string, however JSON-shaped its contents look, is not one, so `is_object()` is `false` and
  the predicate falls through to its `true` default — a failed tool call reported as
  succeeded. Fixed by walking the object for its longest string leaf (recursing into nested
  objects and arrays) and shrinking that leaf — by however many bytes the whole re-encoded
  object is still over budget — until the object's compact encoding fits, keeping it an
  object throughout. Measured: `{"error": "x".repeat(5000)}"` shrinks in one pass (JSON
  overhead `{"error":"..."}"` is 12 bytes; target the leaf down to `4096 - 12 = 4084` bytes;
  re-encoded length lands at exactly 4096). Falls back to a stringified, still-truncated blob
  — flagged with a new field, `tool_result_stringified`, distinct from `tool_result_truncated`
  — only when the object's own skeleton (keys, braces, non-string values) still exceeds the
  bound with every string leaf emptied (a pathological key count; measured with 900 short
  keys, each contributing roughly `len(key) + 6` bytes of pure skeleton even at an empty
  value, totalling comfortably over 4096). `ToolResult.ok` (task M6.5.5, not yet implemented)
  is amended to read `Some(true)` on that flag as `ok = false`: `ToolResult.ok` is a plain
  `bool` in the already-merged `crates/proto` model (task M6.5.1), with no third state to
  spell "unknown" honestly, and the principle a truncation must never manufacture a success
  makes `false` the only safe choice when the discriminating keys are known to be lost.
  Reviewed and fixed in wave 1 of task M6.5.2 (finding F2). `crates/config`'s
  `CONVERSATION_MAX_RESULT_BYTES_RANGE` lower bound was also raised from 1024 to a new named
  `CONVERSATION_MAX_RESULT_BYTES_MIN` (4096), because the pre-amendment lower bound let
  `conversation.max_result_bytes` be configured smaller than `TOOL_RESULT_SUMMARY_MAX`,
  making the hook forwarder's own "never trips the daemon's cap" comment false at that
  legal minimum (demonstrated with the brief's own worked example, `max_result_bytes =
  2048`); task M6.5.3 gains an acceptance-criteria item to compile
  `const _: () = assert!(TOOL_RESULT_SUMMARY_MAX as u64 <=
  config::CONVERSATION_MAX_RESULT_BYTES_MIN);` in `crates/cli/src/hook.rs` once that config
  exists, since `crates/cli` already depends on `crates/config` but the constant it needs to
  check against did not exist when task M6.5.2 ran. Same review (finding F1) also replaced
  the multibyte char-boundary test's fixture: 3000 repetitions of the 2-byte `é` left byte
  4096 already a char boundary (3000 × 2 = 6000, and 4096 is even), so the entire back-off
  loop was provably dead code by that test's own construction — deleting it still passed
  every test in the file, and the resulting mutant panics (unswallowed only by `hook.rs`'s
  own no-op panic hook, which turns it into a silent zero-exit-status dropped event) on any
  3-byte-or-wider character whose byte length straddles 4096. Replaced with 3000 repetitions
  of the 3-byte `世` (9000 bytes; 4096 is not a multiple of 3, so the back-off loop must move,
  landing at 4095). The truncate-on-raw-string-content-not-JSON-text reasoning was also
  reworded (finding "right for the wrong reason" in the review): the original comment argued
  from byte parity (a JSON quote shifts multi-byte character offsets), which happens to
  distinguish the two readings for `é` and inverts for `世` — fixture-specific, not general.
  The actual, general reason is semantic: the field carries the result's text, so the text
  (not its JSON encoding) is what gets truncated, matching M6.5.5's `summary` rule, which
  already truncates the same field the same way. Two further gaps closed with one-line
  fixtures: finding F5 (nothing previously pinned the `<=` boundary at exactly
  `TOOL_RESULT_SUMMARY_MAX`; `<` in its place passed every other test) and finding F8
  (nothing previously pinned that `tool_result_truncated`/`tool_result_stringified` overwrite,
  rather than merge with, whatever the runtime happened to already send under those keys).
  Every fix here was verified by manually applying the mutation the review named, confirming
  the relevant test failed, then reverting and confirming it passed again.
- **Task M6.5.5's `ParsedHook` field count and grapheme-cluster input, amended before task
  M6.5.5 was implemented.** `ParsedHook` gains a sixth field, `tool_result_stringified:
  Option<bool>`, mirroring `tool_result_truncated`'s three-case `Option<bool>` shape (see
  above). Its own test fixture instruction is amended too: two `Option<bool>` fields cannot
  be given pairwise-distinct values the way four differently-typed fields can, so the fixture
  sets them to *opposite* booleans instead — the strongest same-typed-boolean-pair fixture
  available, since any transposition flips both assertions. Separately, M6.5.5's `summary`
  construction gains a stated input it must handle: `anthrex hook`'s truncation
  (`TOOL_RESULT_SUMMARY_MAX`) cuts on a UTF-8 char boundary, not a grapheme-cluster boundary
  (`crates/cli` does not depend on `unicode-segmentation`, and adding it there for a case
  nothing in task M6.5.2 tests would have been scope creep on a task bounded to `hook.rs`),
  so a `tool_response` string can arrive at M6.5.5 with its last grapheme cluster already
  split. M6.5.5's own grapheme truncation (`SUMMARY_MAX_GRAPHEMES`) only shortens a string; it
  does not repair a malformed trailing cluster already present in its input. Recorded, not
  fixed, in wave 1 of task M6.5.2's review — correct to handle at the M6.5.5 layer, where the
  grapheme-aware code already lives, not by adding a new dependency to `crates/cli`.
  (The review that raised this located the requirement at "M6.5.6"; corrected here to M6.5.5,
  the task that actually reads `hook.tool_response` and does grapheme-level truncation —
  M6.5.6 is the revision/delta/cap store and has no string-content logic of its own. Likewise
  the review located the `CONVERSATION_MAX_RESULT_BYTES_MIN` static-assert TODO at "M6.5.4"
  (Tool summaries, which never touches `crates/config`); corrected to M6.5.3, the task that
  actually defines `[conversation]`.)
