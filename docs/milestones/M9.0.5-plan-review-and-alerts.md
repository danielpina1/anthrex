## Goal

When a plan or a hold awaits approval, the user presses Enter on its alert and reads the whole plan on one screen: the task list with routes, sizes, test modes, dependencies and waves on the left, and everything about the selected task (the full brief, owned files, acceptance as a checklist, test mode and its reason, notes, dependencies, routes) on the right. `a`, `x`, `e` and `d` there do exactly what they do in the run view. The main screen's bottom-left corner shows an **Alerts** box under the agent list, listing only what needs the user, most urgent first: the orchestrator waiting for input, a plan or hold awaiting approval, a blocked task or halted run, a run ready to accept or a profile proposal ready to confirm. Each line jumps to where the user acts. Alerts clear themselves once resolved. In `C-b T`, the task panel is organised as GOAL, STATUS and RESULT: it shows what the task is for, what its worker is doing right now (a live "now:" line), how its last check and review went, and, once it is done, the worker's own summary of what it did, the reviewer's verdict, the diff and the merge commit.

## Scope

In: the plan review screen; the Alerts box with `C-b a`, and the status bar's `⚑ n`; the sectioned, scrollable task panel; the daemon's live activity line and worker summary; the on-demand task detail request; the three alert inputs the client lacks (a held wake-up, whether a window has signalled, ready profile proposals); protocol 11.

Out:

| Out | Why, or owner |
|-----|---------------|
| Dismissing or snoozing an alert | The user's design: alerts clear only when resolved. |
| Clicking an alert or a review row with the mouse | Follow-up; keys only here. |
| An alert when a worker finishes a turn | The user's design: not an alert. |
| Per-test check counts (`failed 1/5 (test_x)`) | The snapshot carries no test counts; decision 24 shows the check's summary line instead. A structured count belongs to 9.1's test scheduler. |

| Confirming a profile proposal from the TUI | Follow-up (M9's "a TUI form for the repository profile" stays open); the alert tells the user the CLI command. |

## Design decisions

Numbered and final. If one proves wrong or impossible, stop work on it, record the evidence under "Implementation notes", and continue with the tasks that do not depend on it.

### Protocol and daemon

1. **Protocol 11.** Every new field is `#[serde(default)]`; every new enum variant is appended last. An M9 `run.json`, window record and snapshot load unchanged. The additions are exactly those in Interfaces "proto".
2. **`TaskInfo.activity` is in the snapshot; the worker summary is not.** Decision 16a of milestone 9 keeps plan text out of every push, pinned by `a_snapshot_of_fifty_terminal_runs_stays_small` (1.25 KiB a task over 50 complete runs of 20 merged tasks). A 1500-character summary on every merged task would break that bound five times over, and the full brief the GOAL section needs is exactly what 16a removed. So: `TaskInfo.activity` (at most 160 characters) is published only while the task has a live round, and is `None` otherwise, so a terminal or complete run's tasks carry nothing new. The brief, the acceptance and `worker_summary` travel in a new on-demand reply, `RunReply::TaskDetail`, which the client asks for only for the one task its inspector shows (decision 23). *(The user's request named `TaskInfo.worker_summary` "for example"; this is the deviation, and why.)*
3. **What "activity" is.** One line, at most `ACTIVITY_MAX` = 160 characters, sanitised with `proto::safe_text::one_line`, cut with a trailing `…`: after a top-level tool call, `<tool> <target>`, where `<target>` is `conversation::summary::for_tool(name, Some(input))` and a `mcp__anthrex__` prefix is dropped from the tool name (`Bash cargo test -p calc`, `Edit src/stats.rs`, `task_done`); after top-level assistant text, `says: <its first non-blank line>`. It is the latest of the two. A sub-agent's tool calls and text (`parent: Some`) change nothing, as the window's `tool` ignores them today (`headless/status.rs:85`).
4. **What the worker summary is.** `TaskDetailInfo.worker_summary` is, in order: the accepted `task_done` summary (`Task.done.summary`) when it is not blank (`summary_source: TaskDone`), else the last top-level assistant text of the latest worker round whose turn is closed (`turn_open == false`, or the round ended) (`summary_source: LastMessage`), else `None`. Capped at `WORKER_SUMMARY_MAX` = 1500 characters on a character boundary with `…`, sanitised with `proto::safe_text::multi_line` (line breaks kept; every other control character becomes a space and every hidden format character is dropped, as `one_line` does). The `task_done` summary comes first because it is the worker's own account of the work, written for that purpose and already persisted; the last message covers the turn-end fallback, whose claim has an empty summary (`engine/fallback.rs:51`).
5. **Where the daemon derives them.** On the run engine's forwarder task, never under the manager lock (AGENTS.md rules 2 and 10): `run/driver/observe.rs::translate`, already pure and already on that path (`driver.rs:403-428`), maps `SessionEvent::ToolUse { name, input, parent: None }` to `AgentSignal::ToolUse { name, target }` (the new `target` field; a sub-agent's tool call keeps `target` empty), and a top-level `SessionEvent::AssistantText` to the new `AgentSignal::Said { text }`, with `text` cut to `WORKER_SUMMARY_MAX` before it crosses the channel. `Said` is **not** throttled by `ACTIVITY_EVERY`: a worker's last message usually lands within a second of its previous event and would otherwise be lost. A sub-agent's text stays `Activity`. The reducer (`engine/rounds.rs`, new functions `note_tool` and `note_said`, one call each from `signals::apply`) sets `AgentRound.activity` for every role, and `AgentRound.last_text` for worker rounds only. Both parsers already emit these events for both runtimes (`headless/claude_stream.rs`, `headless/codex_stream.rs`).
6. **They are counters.** `activity` and `last_text` are cleared by `without_counters` (through a new `AgentRound::clear_counters`, which also takes the three existing counter lines, so `engine/mod.rs` does not grow past 600). So a tool call or a line of text alone is never structural: it is persisted at most every 5 s (`COUNTER_PERSIST_EVERY`), published at most once a second, and never moves the orchestrator's digest (M9 Review focus 2). The "now:" line therefore refreshes at most once a second; the summary is final at the turn end, which is structural anyway.
7. **`TaskDetail` is read from memory.** `RunRequest::TaskDetail { run_id, task_id }` is answered by `RunService::task_detail` in `run/driver/requests.rs`: it takes the engine state lock only to call the pure `run::snapshot_detail::task_detail(run, task_id)`, and drops it before replying. No file, git or process access. Unknown run or task: `Refused` under `request::TASK_DETAIL` = `"run task-detail"` with `run <run> has no task <task>`.
8. **The held wake-up is a flag.** `OrchestratorInfo.wake_held: bool`, from `RunOrch.wake_held` (`snapshot_orch::orchestrator`). The attention line `WAKE_HELD` stays as it is; the client never matches attention strings.
9. **A startup prompt is visible through `WindowInfo.signals_seen`.** Grounded in `status.rs:87-91`: until a window's agent sends its first hook, notify or title signal, output makes it `Working` and quiet makes it `Idle`, so a Claude orchestrator stopped at the folder-trust prompt looks exactly like an idle one. Window status alone cannot tell them apart. `WindowInfo.signals_seen` (from `AgentState.signals_seen`, `Entry::info`) lets the client say "no agent signal yet, and not working". That Claude runs no hook before its trust prompt is answered is an external fact, checked in the manual check (step 3); if a hook does fire first, record it: the alert then cannot see the trust prompt, and nothing else changes.
10. **Ready profile proposals are pushed.** `ProfileService`'s `Table` gains `ready: BTreeMap<PathBuf, u64>` (project → `updated_at`) and a `ready_generation: u64`, updated right after every proposal write and delete that succeeds (`save_if_current`, `service_restore.rs:155`, `service_requests.rs:253` and `:355`, `service_run.rs:435`, `service_start.rs:183`) and seeded by `restore` from the proposals it loads. `RunService::with_scouts` (`driver/orch.rs:99`, used by both `publish` and `current`, so `RunRequest::List` sees it too) also overlays `RunsSnapshot.proposals` from it; `on_tick` publishes when `ready_generation` moved since the last publish. Memory only, under the table's own mutex, never across an `.await`.

### The plan review screen

11. **What it reviews.** `ReviewTarget::Gate` for a run in `awaiting_approval` (all its tasks), or `ReviewTarget::Hold(id)` for an awaiting hold (only that hold's tasks, in plan order). It is pure state, `App.plan_review: Option<PlanReview>`, and renders from the snapshot alone: at the gate and for an awaiting hold the snapshot already carries every task's brief and acceptance (decision 16a's `plan_text_shown`), so the review asks the daemon for nothing.
12. **Layout.** It takes the whole body, sidebar column included (`Layout.body`); the status bar stays. Title row: `<Plan|Hold <id>> review · <run id> · <goal>`, and right-aligned `<n> tasks · awaiting approval`. Left pane, width `clamp(body.width × 2 / 5, 30, 56)`: two rows per task — `▸ <id>  <title>` (`▸` on the selected one, bold), then, muted and indented two columns, `<runtime> <model> <effort> · <S|M|L> · <test mode>` plus ` · after <dep>, <dep>` when it has deps (explicit then implicit, deduplicated). The last row of the left pane is the waves summary, `waves  1 <ids> · 2 <ids> · 3 <ids>` (`TaskInfo.wave + 1`, ids in plan order), cut with `…`. Right pane, the selected task, scrollable: title line `<id>  <title>`, then the sections `brief` (wrapped in full), `owns` (one path a line), `done when` (one `☐ <criterion>` a line), `test mode` (`<mode> — <reason>`), `notes` (one a line; omitted when empty), `deps` (`after …`; `unblocks …`; omitted when neither), `route` (`<runtime> · <model> · <strength> · <effort> effort`), `review` (the review route the same way, or `none`). Every agent-written string goes through `safe_text` (decision 27).
13. **Keys.** `j`/`k` (and Down/Up) select, `PageUp`/`PageDown` scroll the right pane by its height minus one, clamped to its content, reset to the top on a new selection. `a`, `x`, `e`, `d` call the existing handlers with the review's selection (decision 16), so their confirms, the edit form, the hold rules and the stale-modal checks are M8c's and M9's, unchanged. `Esc` clears the review and its keymap mode and nothing else, so the screen underneath (the run view, the overview or the terminal, with its tree mode) is as it was. While the review is open, `C-b a` toasts `leave the plan review first (esc)`.
14. **Reaching it.** Enter on a priority-2 alert (decision 18) opens it over whatever screen was showing, which `Esc` gives back (decision 13). In the run view, **`p`** opens it for the view's run: `Gate` when the run awaits approval, else the selected held task's hold, else the oldest awaiting hold, else it toasts `run <id> has nothing awaiting approval`; `Esc` returns to the run view with its selection unchanged. The run view's gate and hold hints gain `p review`.
15. **It closes itself.** After every snapshot, a review whose run left `awaiting_approval` (for `Gate`) or whose hold is no longer `Awaiting` (for `Hold`), or whose run is gone, closes as `Esc` would, with no toast of its own (the approve or reject reply already toasts).
16. **The gate keys take an explicit selection.** `on_gate_key(run_id, key, selected: Option<NodeKey>)`, `on_hold_key(run_id, key, selected)` and `hold_target(run, selected)` read the node they are given instead of `self.tree.selected`. The run view passes `self.tree.selected.clone()`; the review passes `Some(NodeKey::Task { run, id })` for its selection. Behaviour in the run view is unchanged; M8c's and M9's gate and hold tests are the pinning tests.

### Alerts

17. **Pure and computed.** `app/alerts.rs::alerts(app) -> Vec<Alert>` reads only `App.runs` (shown runs, `tree::shown_runs`), `App.windows` and `App.runs.proposals`. It is recomputed on every draw and key; nothing is stored but the focus.
18. **The four priorities, exactly.** Per shown run, in `created_at` order:
    1. **Orchestrator needs you** (at most one per run). The run's `orchestrator` is `live` with a `window_id` listed in `App.windows`, and one of, first match wins: `wake_held` → `orchestrator wake-up held`; the window is `Attention` and `signals_seen` → `orchestrator asks for permission`; the window is `Claude` or `Codex`, `!signals_seen`, and `Idle`, `Done` or `Attention` → `orchestrator waits at a start prompt`. Enter: focus that window and leave tree mode, as `enter_run_root` does.
    2. **Plan or hold awaits approval.** `state == AwaitingApproval` → `plan awaits approval · <n> tasks` (tasks not cancelled); each hold with `state == Awaiting` → `hold <id> awaits approval · <n> tasks`. Enter: the review (decision 14).
    3. **Blocked or halted.** Each task with `state == Blocked` and not `is_paused`, whose block reason is `Human`, `Conflict` or `Environment`, or any reason when the run has no live orchestrator (`Question`, `MisSized` and `DepCancelled` are the orchestrator's to answer while it lives) → `<task> blocked (<reason text>): <first line of block.text>`. A run in `Halted` → `run halted: <first line of halted_reason>`, or `run halted`. Enter: open the run view and select the task (for a halted run, the root).
    4. **Ready to accept.** `state == Complete` → `ready to accept · <m>/<n> merged`. Enter: open the run view on the run. Then, after every run, each entry of `RunsSnapshot.proposals` → label `<project directory name>`, text `profile proposal ready`. Enter: toast `profile proposal for <project>: run anthrex profile show --proposed, then anthrex profile confirm or reject, in that project`.

    Sorted by priority, then run `created_at`, then the order above. A worker finishing a turn is never an alert.
19. **One line each.** `● <label>  <text>`, where `<label>` is the run id (or the project name), both through `safe_text::one_line`, cut to the box's width with `…`. `●` and the label take the priority's colour (`theme::alert_color`: 1 `Red`, 2 `Yellow`, 3 `Magenta`, 4 `Green`), the text the default colour; the focused selection is reversed.
20. **The box.** The sidebar column splits: the `agents` block on top, the `Alerts (<n>)` block (rounded border, title in the accent) at the bottom. Its height is its rows plus two borders: with no alert its interior collapses to one muted line, `no alerts`; otherwise `min(n, ALERTS_MAX_ROWS = 6, max(1, sidebar height / 3 − 2))` rows. More alerts than rows: while focused, the rows scroll to keep the selection visible; unfocused, the last row reads `+<k> more`. Sidebar hidden: no box, and the status bar shows `⚑ <n>` in the top priority's colour, right after the mode badge, when `n > 0`.
21. **Focus.** `C-b a` (`Command::FocusAlerts`) shows the sidebar if it is hidden, sets `App.alerts_focus = Some(AlertsFocus { selected: Option<AlertKey> })` and the keymap's new `alerts_mode`, in which bare keys arrive as `KeyAction::Alerts(key)`. `j`/`k` (and Down/Up) move, Enter jumps (decision 18) and leaves the focus, `Esc` leaves it. The selection is the alert's identity (`AlertKey`), not an index: when it resolves, the selection moves to the alert now at its old position, clamped. Alert keys take precedence over tree and conversation keys; the prefix still works. The border is `theme::border_focused` while focused; the status bar shows ` ALERTS ` and `j/k move  ⏎ go  esc back`.

### The task panel in `C-b T`

22. **Three sections.** The task inspection becomes `FieldLayout::Sections`: `Inspection.sections: Vec<Section { title, fields }>`, rendered by the new `inspector/panel/sections.rs` as a bold section title row, then each field as label and value, every value wrapping under itself, then the next section. Nothing the flat list showed is dropped:
    - **GOAL**: `brief` (the first 3 wrapped lines, then `… (b: more)`; the whole brief while `b` has expanded it), `owns` (joined `, `), `done when` (one `☐ <criterion>` a line). From the task detail (decision 23); until it arrives, `brief  loading…`; if it was refused, `brief  <the refusal's first line>`.
    - **STATUS**: `stage` in plain words (Interfaces "Stage words"); `worker` `<round label> · <runtime> <model> · <elapsed> · <n> tool calls` for the latest worker round (`tree::round_label`, `format_duration(app.run_age(started_at))`, frozen at `ended_at`); `now` (`TaskInfo.activity`, prefixed `reviewer: ` when the live round is a reviewer's; omitted when `None`); `check` (decision 24); `review` (`–` when the task has no review route, `in review · round <n>` during `Review`, else M8c's `review_text`, else `not yet`); then the existing `stages`, `route`, `deps`, `budget`, `tries`, `messages`, `notes` and `history` fields as they are today.
    - **RESULT**: `summary` (`worker_summary`, wrapped in full, with ` (task_done)` or ` (last message)` muted after its label); `verdict` (the last verdict's `approve`/`changes`, then its summary's first line); `diff` (M8c's `diff_text`); `merged` (the merge commit's first 7 characters, and `without approval: <reason>` when `merged_without_approval`). The section reads `nothing yet` while all four are empty.
23. **The detail is fetched on demand.** `app/task_detail.rs`: `App.task_detail: Option<TaskDetailCache { run_id, task_id, key, state }>`, `state` one of `InFlight(request id)`, `Ready(Box<TaskDetailInfo>)`, `Failed(String)`. `key` is `(state, rounds.len(), reviews.len(), Σ worker rounds' turns, the latest worker round's turn_open, done_signal.is_some(), merge_commit.is_some())` of the inspected `TaskInfo`. `on_tick` sends one tagged `RunRequest::TaskDetail` when the run view is open with the panel visible, a `Task` node is selected, the link is connected, and the cache names another task or another key, or is empty; nothing is sent while a request for the same task and key is in flight. The reply with the matching `request_id` fills it; a `Refused` with that id fills `Failed` and is not toasted; any other `TaskDetail` reply is dropped. A lost link clears an in-flight cache. So a task is asked for once when selected and once per turn, round, review or merge, never on a timer.
24. **The check line.** `✓ passed` or `✗ failed` (or `timed out`), ` · <first line of decider_summary, else of summary>` cut to fit, then ` → bounced (check <n>/<max>)` when the task went back to `Working` after it, ` → blocked` when blocked, ` → merge queue` when it moved on; `–` when the run is unverified; `not yet` when there is none.
25. **Scrolling and height.** In the run view with a task selected, `PageUp`/`PageDown` scroll the panel by its interior minus one and `b` toggles the brief. The scroll lives in `App.inspector_scroll: Option<(NodeKey, u16)>` and the expansion in `App.brief_expanded: Option<NodeKey>`, each honoured only while its key is the selection, so a new selection starts at the top, collapsed. The reducer clamps with the same pure row count the renderer uses (`inspector::task_panel_rows(app, width)`), from `App.graph_main`. The run view's panel gains a third height: `RUN_INSPECTOR_TALL_HEIGHT` = 18 when the overview's interior has at least `MIN_INTERIOR_FOR_TALL_RUN_PANEL` = 34 rows (a terminal of 37 rows or more); M8c's 12 and 8 steps are unchanged, so every existing render test at 30 rows or fewer keeps its output. The height still follows the view, never the node.
26. **The round panel's `doing`.** For the task's live round, `run_round.rs`'s `doing` reads `now: <activity>` when `TaskInfo.activity` is `Some`, else today's text (the followups file's "The run inspector's `doing` field has no tool target", M8c Risks 6).

### Safety of displayed text

27. **Worker text is untrusted display data.** `safe_text`'s `is_hidden_format` and `one_line` move to `proto/src/safe_text.rs` (pure, no dependency), which gains `multi_line`; `tui/src/safe_text.rs` re-exports them and keeps its test helpers. The daemon sanitises and caps `activity`, `last_text` and `worker_summary` when it stores or builds them; the TUI sanitises every agent-written string again when it renders it (`one_line` on a row, `multi_line` then `one_line` per wrapped line in a pane). A brief, an acceptance criterion, a note, an alert label and a summary can never move the cursor, break a row or reorder a line.
