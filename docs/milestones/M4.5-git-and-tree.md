## Goal

While you are looking at an agent, the bottom bar tells you what its checkout is doing: which branch, how much uncommitted work, how far it has drifted from its upstream, and whether it is mid-merge or mid-rebase. The number is kept honest by watching the filesystem, so it moves within a third of a second of the agent committing, and costs nothing while the repository is idle.

At the same time the project tree stops being indented text and becomes a real tree, with `├─`, `└─` and `│` connectors at every level, to any depth — so that when an orchestrator's worker has its own sub-agents, the shape is legible.

## Scope

**In.**

- Per-worktree git state in the daemon: detection, probing, filesystem watching, publication.
- `WindowInfo.worktree`, a new `DaemonMsg::Git`, protocol version 4.
- A git segment on the TUI bottom bar for the focused window.
- Box-drawing guides on every tree row, in both the sidebar and the full-screen overview.
- `ANTHREX_GIT=off`.

**Out.**

- Git state anywhere except the bottom bar. No git column in the tree, no git panel, no per-project rollup. (Spec §3, answered question 1.)
- Any git *action*. Nothing in this milestone stages, commits, fetches, pulls, merges or checks out.
- A configuration file. Milestone 6 adds the `[git]` table; until then the only knob is `ANTHREX_GIT=off`.
- A manual refresh key or a client-initiated probe.
- Worktree *creation*. That is milestone 5. This milestone only reports on worktrees that already exist.

## Design decisions

These are final. If one proves wrong, stop and record the evidence under "Implementation notes"; do not quietly choose differently.

1. **Git state is keyed by worktree root, not project root.** Milestone 4's project root is the parent of `--git-common-dir`, which is shared by every linked worktree of a repository. Git state is per checkout. Keying it by project would show every worktree the parent repository's branch, and milestone 5 makes that the normal case.
2. **`WindowInfo` gains `worktree: Option<PathBuf>`.** `None` means the window's directory is not inside a git working tree.
3. **Both roots come from the existing call.** `daemon::project::detect_root_with` already runs `git rev-parse --path-format=absolute --git-common-dir --show-toplevel` and discards the second line. It now returns both. No second git invocation.
4. **`worktree` is computed once, before the window exists, and never changes** — the same rule and the same reason as milestone 4's `project` (decision M4.6): a row that moves under the cursor breaks selection.
5. **One probe command:** `git -C <root> --no-optional-locks status --porcelain=v2 --branch --untracked-files=normal -z`. `--no-optional-locks` is mandatory: without it the probe can take the index lock while an agent runs git in the same worktree. `-z` makes records NUL-terminated so a path containing a newline cannot desynchronise the parser.
6. **`dirty` merges staged and unstaged.** One count of tracked files that differ from `HEAD`. The bar has no room for two numbers and the question is "is there uncommitted work here".
7. **The in-progress operation is found by `stat`, not by parsing.** Against the worktree's *own* git dir (`--git-dir`, not the common dir — rebase and merge state are per worktree), in this order, first match wins: `MERGE_HEAD` → `Merge`; `rebase-merge/` or `rebase-apply/` → `Rebase`; `CHERRY_PICK_HEAD` → `CherryPick`; `REVERT_HEAD` → `Revert`; `BISECT_LOG` → `Bisect`.
8. **Probe hardening is identical to `daemon::project`:** `GIT_DIR`, `GIT_WORK_TREE`, `GIT_COMMON_DIR`, `GIT_INDEX_FILE`, `GIT_PREFIX` removed from the environment; stdin and stderr null; stdout piped and drained non-blocking; the child terminated and reaped on timeout.
9. **Caps: 1 MiB of output, 5 seconds.** On either, stop, keep the counts parsed so far, and set `stale`. Fifty thousand untracked files must degrade, not wedge the daemon.
10. **One probe in flight per root.** A refresh requested while one runs sets a pending bit; exactly one more probe runs when the current one returns. Never a queue.
11. **The watcher is `notify`'s recommended watcher:** recursive over the worktree root, plus non-recursive over that worktree's git dir.
12. **Events are filtered by path only**, with no gitignore parsing. Rejected: any path component equal to `target`, `node_modules`, `.venv`, `dist`, `build`, `.next`; anything under `<gitdir>/objects` or `<gitdir>/lfs`; any file name ending in `.lock`.
13. **Debounce 300 ms, safety poll 30 s.** An accepted event schedules a probe 300 ms later; further accepted events push that deadline out. Every registered root is probed every 30 seconds regardless, and immediately on registration.
14. **Circuit breaker.** More than 200 accepted events within 10 seconds for one root: log once, and put that root on poll-only for 60 seconds. This is the `git checkout` of a large tree case, which the path filter does not catch.
15. **Watcher construction failure is not fatal.** Log once for that root and leave it on the 30-second poll.
16. **Root lifecycle follows windows.** A root is registered when at least one window records it and unregistered when the last such window goes. Registration and unregistration never happen while the manager lock is held.
17. **Protocol version 4.** New `DaemonMsg::Git { root, state: Option<GitState> }`, broadcast on change. Every known root is also sent to a client immediately after its `Welcome`, so a fresh client is never blank.
18. **There is no client-initiated refresh.** The daemon decides when to probe.
19. **Bottom bar format**, exactly (§3.6 of the spec):

   | State | Rendering |
   |---|---|
   | clean, in sync | `main ✓` |
   | dirty | `main ●3 ?1 ⇡2⇣1` |
   | conflicted | `main ⚠2 rebase` |
   | detached | `@a1b2c3d ●1` |
   | unborn branch | `main (unborn)` |
   | last probe failed | `main ●3 (stale)` |

   Head bold; `✓` green; `●`, `?`, `⇡`, `⇣` and `(stale)` muted; `⚠` and the operation name red. `?` and the divergence arrows are omitted when zero. **No branch glyph** — `⎇` and powerline glyphs are not reliably present in users' fonts.
20. **Truncation order as the terminal narrows:** key hints drop from the right, one at a time; then the git segment's parts drop right to left (operation, untracked, divergence, dirty); then the head name alone; then the segment is hidden. The toast is never truncated to make room for git.
21. **`ANTHREX_GIT=off` disables the subsystem entirely** — no watchers, no probes, no `Git` messages, and `worktree` still populated. The PTY smoke script and CI set it so screen comparisons do not depend on the working tree's state.
22. **`Row.indent: u16` is replaced by `Row.guides: String`** — the exact prefix drawn before the row's own marker.
23. **Guide alphabet, two columns per level:** for each ancestor above the parent, `"│ "` when that ancestor has a later visible sibling and `"  "` when it does not; then `"├─"` for a row with a later visible sibling and `"└─"` for the last. Project rows are roots and have empty guides.
24. **Guides are computed from the *visible* tree** — after collapse and after filtering. Hiding the last sibling of a group turns the `├─` above it into `└─`. This is the case most likely to be got wrong.
25. **Depth is unbounded.** Nothing in the row builder, the renderers, the geometry or the tests may assume a maximum.
26. **`RowKind::Subagent.guides` is removed.** Sub-agent guides come from `Row.guides` like every other row, produced by one shared routine.
27. **The sidebar and the overview use the same guide strings.** In the overview the guides live inside the name column and count against its width.
28. **Geometry is unchanged.** One row per node; `TreeGeometry`, `index_at`, hit-testing, selection, collapse, the filter, the viewport and the `C-b 1..9` numbering behave exactly as they do today.
29. **The window focus marker `▎` and the collapsed marker `▸` stay**, drawn immediately after the guides and before the status glyph.
30. **Time is injected in tests.** The debounce, the poll and the circuit breaker are driven by an injected clock, never by sleeping in a test.

### Protocol (`crates/proto`)

```rust

    /// True when there is nothing uncommitted and no divergence.
```

### M4.5.3 — The porcelain v2 parser

**Files:** create `crates/daemon/src/git/parse.rs` and `crates/daemon/src/git/mod.rs`; `crates/daemon/src/lib.rs`.

**Tests first**, all against byte literals, no git process:

- `parses_a_clean_branch_with_upstream` — `# branch.oid`, `# branch.head main`, `# branch.upstream origin/main`, `# branch.ab +0 -0` and nothing else gives `Head::Branch("main")`, ahead 0, behind 0, all counts 0.
- `counts_ahead_and_behind` — `# branch.ab +2 -1` gives 2 and 1.
- `no_upstream_means_no_branch_ab` — the `# branch.ab` record is absent: `upstream` is `None`, ahead and behind are 0.
- `detached_head_uses_the_short_oid` — `# branch.head (detached)` with `# branch.oid 1a2b3c4d5e6f…` gives `Head::Detached` holding the first 7 characters.
- `unborn_branch_is_recognised` — `# branch.oid (initial)` with `# branch.head main` gives `Head::Unborn("main")`.
- `ordinary_entries_count_once_each` — one entry with `XY` = `M.`, one with `.M`, one with `MM`: `dirty` is 3.
- `rename_entries_consume_both_paths` — a `2 ` record whose payload has two NUL-separated paths is counted once and does not shift the parse of the record after it.
- `unmerged_and_untracked_are_counted_separately` — two `u ` records and three `? ` records give `conflicts` 2, `untracked` 3, `dirty` 0.
- `a_path_containing_a_newline_does_not_desynchronise` — an untracked path with an embedded `\n` still yields exactly one untracked entry.
- `truncated_output_parses_what_it_has` — cut the byte stream mid-record: the function returns the records parsed before the cut rather than `None`.
- `empty_output_is_none` — no records at all gives `None`, since even a clean repository emits `# branch.*`.

**Change.** Write `parse_porcelain_v2_z`. Split the input on `\0`; `# ` records are whole lines; `1 `/`2 ` records take their path fields (two for `2 `); `u `, `? ` and `! ` take one path each.

**Acceptance.** `cargo test -p daemon git::parse`; the crate builds with `git` declared in `lib.rs`.

### M4.5.5 — The registry, the watcher and the circuit breaker

**Files:** `crates/daemon/src/git/mod.rs`; `crates/daemon/tests/git_registry.rs`; `crates/daemon/Cargo.toml` (add `notify`).

The registry's timing logic must be a pure state machine with an injected clock and an injected probe function, so the tests below never sleep.

**Tests first.**

- `registering_a_root_probes_it_immediately`.
- `an_accepted_event_probes_after_the_debounce` — an event at t=0 does not probe at t=299 ms and does at t=300 ms.
- `events_inside_the_window_push_the_deadline_out` — events at 0, 200 ms and 400 ms probe once, at 700 ms.
- `the_poll_fires_every_thirty_seconds_without_events`.
- `only_one_probe_runs_at_a_time_per_root` — while a probe is outstanding, two more requests result in exactly one further probe when it returns.
- `filtered_paths_do_not_schedule_a_probe` — events under `target/`, `node_modules/`, `<gitdir>/objects/` and for a `*.lock` file schedule nothing.
- `an_event_on_a_real_source_file_schedules_a_probe`.
- `the_breaker_drops_a_noisy_root_to_poll_only` — 201 accepted events within 10 s: no debounce probe follows, the poll still fires, and after 60 s debouncing resumes.
- `unregistering_stops_the_probes` — after `unregister`, neither the poll nor an event probes again.
- `a_disabled_registry_never_probes` — `GitRegistry::new(false, ..)` ignores `register` entirely.
- `state_changes_are_published_once` — an unchanged probe result does not publish a second identical message; a changed one does.
- `enabled_from_env_reads_anthrex_git` — `off` and `0` disable; unset, empty and `on` enable.

One integration test may use the real watcher: `a_real_write_triggers_a_probe` creates a repository, registers it, writes a file and waits up to 5 seconds for a published state with `dirty == 1`. It is the only test permitted to wait on wall-clock time.

**Change.** Implement `GitRegistry` with one tokio task per root, a `tokio::sync::watch` or `Notify` for wakeups, and `notify`'s recommended watcher feeding a filtered channel. Deduplicate publications by comparing the new state with the last published one.

**Acceptance.** `cargo test -p daemon --test git_registry --test git_schedule`; `cargo clippy` clean. (`cargo test -p daemon git_registry` filters on test *names*, not file names, and selects nothing — see "Implementation notes".)

## Risks and gotchas

- **The watcher is the dangerous part.** If `top` shows the daemon busy while nothing is happening, the path filter is letting build output through. Check the circuit-breaker log line first.
- **Forgetting `--no-optional-locks`** produces an intermittent failure that only appears when an agent runs git at the same moment. It is asserted by a test for exactly this reason.
- **Computing guides from the full tree instead of the visible tree** passes most tests and is wrong precisely when a filter is active. That test exists; do not weaken it.
- **`WindowInfo.branch` is not `GitState.head`.** Filling `branch` here would collide with milestone 5.
- **Linked worktrees have their own git dir.** Reading operation state from the common dir shows one worktree's rebase in all of them.
- **`notify` on macOS** coalesces and can deliver a directory rather than the changed file. The filter must therefore tolerate directory paths, and the debounce must not assume one event per change.

## Implementation notes

Deviations from the design decisions above, each recorded per `AGENTS.md`'s rule that
a brief's "Implementation notes" hold every place reality disagreed with a final
decision, with the evidence and the reason.

- **Decision 12 was narrowed to the portion of the path below the root.** As written,
  the deny list matched a component anywhere in the *whole* path, so a worktree that
  simply happened to live under a directory named `build`, `dist` or `node_modules`
  (for example `~/build/my-project`) had every event rejected — the root went silently
  deaf and fell back to the 30-second poll, with nothing logged to say why. `accepts`
  (`crates/daemon/src/git/watch.rs`) now scans only the path below the watched root (or
  below the git dir, for the worktree's own `.git`), which is what the deny list was
  always meant to catch. Caught in M4.5.5's self-review, fixed with a regression test
  that fails against the old, whole-path version.
- **A duplicate `.git` watch is skipped when the git dir already sits inside the
  recursive root watch.** Decision 11 asks for "recursive over the worktree root, plus
  non-recursive over that worktree's git dir." For an ordinary (non-linked) checkout,
  `<root>/.git` is already covered by the recursive watch on `root`, so a second
  `watch()` call there would only double-count `.git` events toward the circuit
  breaker for no gain in coverage. The second watch is added only when the git dir
  actually sits outside the root, which is exactly the linked-worktree case decision 11
  is really aimed at.
- **The poll deadline resets on any probe start, not only when the poll itself fires.**
  Read strictly, decision 13's "every registered root is probed every 30 seconds
  regardless" could mean a fixed cadence from registration. Resetting the deadline
  whenever *any* probe starts (debounced or scheduled) keeps the guarantee to what it's
  actually for — never more than 30 seconds without a probe — while avoiding a
  redundant near-duplicate probe moments after a debounced one already ran.
- **`probe` returns `None` whenever no `# branch.*` header was parsed**, including a
  timeout or an over-cap read that struck before any output arrived — not "any timeout
  returns `None`", which is the easy misreading. A timeout or cap hit *after* a header
  (and possibly some status records) had already been parsed still returns `Some` with
  `stale: true`, per decision 9. The reason `None` is the only option pre-header:
  `GitState` has no way to represent an unknown `Head`, so there is nothing to build a
  `Some` out of — inventing a branch name would be worse than reporting nothing. The
  registry compensates so this narrow rule doesn't read as data loss: a root with a
  last-known state that gets a `None` probe result republishes that last state with
  `stale: true` rather than publishing `None` (`Publisher` in
  `crates/daemon/src/git/schedule.rs`); only a root that has *never* successfully
  probed publishes `None`.
- **The second `git rev-parse` was removed.** Decision 5 allows exactly one probe
  command, but detecting an in-progress operation (decision 7) needs the worktree's own
  git dir, which milestone 4's `detect_roots` doesn't provide. Rather than spawn a
  second `git rev-parse --absolute-git-dir` on every probe — a real, recurring cost,
  since a probe runs on every debounced change plus every 30 seconds per root —
  `resolve_git_dir` (`crates/daemon/src/git/probe.rs`) reads `<root>/.git` straight off
  the filesystem: a directory *is* the git dir; a file containing `gitdir: <path>`
  points at it (resolved against `root` when relative), which is what makes a linked
  worktree's own git dir land under `<common-dir>/worktrees/<name>`. This keeps decision
  5's "one probe command" literally true and was caught and fixed in M4.5.4's review.
- **Root registration is reference-counted inside `GitRegistry`.** The first cut derived
  "is this the last window on this root" from a `manager.list()` snapshot taken in
  `server.rs`'s `Remove` handler. That snapshot could race a concurrent `CreateWindow`
  on the same root on another connection: a new window's `register` could run, followed
  immediately by the stale `unregister` from the already-in-flight removal, leaving a
  live worktree briefly unwatched with nothing to re-trigger registration until the next
  unrelated create/remove on that root. Found in M4.5.6's review. Fixed by moving the
  count into `GitRegistry` itself (`Slot::refs`): `register`/`unregister` only start or
  tear down the per-root task on the 0→1 / 1→0 transition, both operations hold the
  registry's own lock for their full duration, and two racing calls on the same root
  now commute to the same end state regardless of arrival order.
- **`(stale)`'s drop priority was raised to match conflicts.** Decision 20 names the
  drop order for the head, dirty, untracked, divergence and operation parts, but not
  `(stale)`. The first cut gave it priority 0 (dropped first), which let a narrowing
  terminal show a confident `main ●3 ?1 ⇡2⇣1` with nothing marking the read as possibly
  stale — worse than showing `main (stale)` with the counts gone, since `(stale)` is a
  trust flag on every number beside it, not another datum competing with them for
  space. Raised to priority 5 (same as conflicts) in M4.5.7's review, with a test
  (`stale_outlives_the_named_parts_when_the_budget_shrinks`) pinning the new order and
  confirmed to fail against the old value first.
- **Task M4.5.8's scope was extended to the minimal substitution in
  `crates/tui/src/ui/tree_view.rs` and `crates/cli/src/tree_cmd.rs`.** As scoped, task 8
  removes `Row.indent`, which both files read; leaving them untouched would have broken
  the plan's own rule that every task leaves the workspace compiling. Task 8 took on
  exactly the mechanical swap (`row.guides` where the indent spaces were) and nothing
  about rendering behaviour, alignment or the name-column width, which stayed task 9's.
  This was a pre-execution ruling recorded in the milestone's task-conflict scan, not a
  mid-task discovery.
- **`anthrex tree` output shifted one column.** `tree_cmd.rs`'s sub-agent line used to
  hardcode a `"│ "` stem before its own connector; that stem is now `row.guides` with
  the window's own guide level dropped (`chars().skip(2)`), and the connector itself
  changed from `"├ "` to `"├─ "` — one column wider, uniformly at every depth, matching
  the sidebar/overview alphabet exactly instead of approximating it. The four assertions
  covering this in `crates/cli/tests/tree.rs` were updated to the new text; nothing about
  the number of indent levels or which lines are printed changed.
- **A test named in the brief was dropped:** M4.5.6's
  `registration_does_not_run_under_the_manager_lock`, specified as "assert by
  construction". A test that asserts by construction asserts nothing at runtime — it
  would pass identically whether or not the property held, since there is no
  observable failure mode for it to catch. Decided before M4.5.6 started (recorded in
  the milestone's task-conflict scan) that the property — `GitRegistry::register` /
  `unregister` are called from `server.rs` after `create`/`remove` return, never from
  inside the closure that holds the manager lock — would be checked by review of the
  call sites instead, and the task's own self-review confirms both call sites do so.
- **The brief's own acceptance line for task M4.5.5 was wrong**, and is corrected above
  at that task's "Acceptance" line rather than only here. `cargo test -p daemon
  git_registry` filters on test *names* containing `git_registry`; the tests that task
  added live in files named `tests/git_registry.rs` and `tests/git_schedule.rs`, and
  `cargo test` filters do not match file names, so that invocation silently selects and
  runs zero tests. The corrected form, `cargo test -p daemon --test git_registry --test
  git_schedule`, names both test binaries explicitly.
