- **Two models brainstorm independently.** Neither sees the other's draft, and the orchestrator merges them into one report that shows agreement and disagreement (DF §3).

- **Nothing reaches the user's branch until the user accepts.** anthrex never merges or lands in `pr` mode. The documents commit is the engine's own, through the git write queue, never under a lock (AGENTS.md rules 2, 10, 11).
- **The client's state stays pure** (AGENTS.md rule 5).

## Goal

A planned goal goes:
1. Brainstorm: two independent drafts, merged into one report, approved by the user.
2. Spec: written, reviewed by the peer model, approved by the user.
3. Plan: a task graph whose coverage of the spec's requirements the engine checks, reviewed, approved by the user.
4. Then today's execution.

During execution, workers and reviewers work against their requirements, and REPORT.md shows each requirement's outcome.

### Mode and phases (DF §1, §2)

3. **`Run.design_mode: DesignMode { Full, Off }`** is frozen at start. Default `Off` for older runs.
   - **On by default:**
     - triage path `Plan` or `Large`;
     - every kind in `TriageInfo.kinds` is `Code` or `Docs`;
     - not from a plan file;
     - not a promotion.
   - **Overrides:** `--design` / the dialog row first, then `[orchestrator.design] default`.
   - A request for `Full` on a goal the table puts off is refused with the exact text: `the design flow runs only for planned code or docs goals; this goal is <fast|research|review|a plan file>`.
4. **Two states appended to `RunState`:** `Brainstorming` (label `brainstorming`) and `Specifying` (label `specifying`), **appended after `Planning`** (wire order).
   - A design run enters `Brainstorming` where 9.5 enters `Planning` (`orch/mod.rs::make_planned:477`). It enters `Planning` when the spec gate is approved.
   - Every exhaustive match that lists `Planning` gains the two new states with `Planning`'s arm. The code map in "Starting point" lists the sites.
   - **Scouts run in `Brainstorming`**, exactly as they run in `Planning` today (the `planners.rs:65` gate admits both).
5. **One gate record for all three gates:** `DesignState.gate: Option<DocGate>`.
   - `RunState::AwaitingApproval` stays the one waiting state. In a design run, the plan gate is `DocGate { kind: Plan, .. }`.
   - A non-design run keeps `gate = None`, and 9.5's plan gate is unchanged.
   - Names avoid 9.5's `GateKind` (a task's bounce gate, `proto/run.rs:441`): the types are `DocGate`, `DocKind`, `DocFinding`, `DocSeverity` and `DocAuthor`.
6. **`--yes` never skips a design gate.** `goal_rounds_end::skips_gate:25` returns false when `run.design_mode == Full`. The start logs once, exactly: `design flow: --yes does not skip the brainstorm, spec or plan gates`.
7. **Gate actions are one request**, `RunRequest::DocGate { run, kind, action }`, with:

   ```
   DocGateAction {
     Approve,
     Changes { note, review },
     Edit { text },
     Rethink { note },
     Back { note },
     Reject,
   }
   ```

   - **Validity:**
     - Rethink is valid only at `Brainstorm`.
     - Back is valid only at `Spec` and `Plan`.
     - An action at a gate the run is not at is refused: `run <id> is not waiting at the <kind> gate`.
     - An action while `revising` is set (other than Reject) is refused: `the orchestrator is revising <kind> v<n>; wait for it`.
   - **Plan-gate compatibility:** `RunRequest::Approve` and `RunRequest::Reject` at the plan gate of a design run are accepted as `DocGate { kind: Plan, Approve | Reject }`.
8. **Phase budgets.**
   - `phase_minutes` counts the wall-clock time of an orchestrator phase. It excludes gate waits, and pauses and downtime by 9.5's pause bookkeeping (`engine/pause.rs`).
   - Past it, the run is set to `Halted` with exactly `design flow: the <brainstorming|specifying|planning> phase passed its <n> min budget`.
   - `run resume` continues it and the phase clock restarts.
   - **When each clock starts** (DF §2.2): `brainstorming` from the moment both drafts are in (or the one surviving draft), not from the start of the phase; `specifying` and `planning` from entering the state. A `back` or `changes` restarts the clock of the phase it returns to.

### Brainstorm (DF §3)

9. **Two new roles, `AgentRole::Brainstormer` and `AgentRole::DocReviewer`**, appended after `TestWriter`.
   - Both follow the **sub-planner pattern**: `scout/planner.rs` `PlannerSpec`/`start_planner`, `OpKind::StartPlanner`, `OrchEvent::PlannerEnded`, `engine/planners.rs`. Their spec is `scout/design_spec.rs::DesignAgentSpec`, with a `kind` of `Brainstormer { label }` or `DocReviewer { doc }`.
   - **Both take a reader slot.** `schedule::readers_busy:206` adds `design_agents::readers(run)`. The agents are dispatched from `planners::dispatch:58`'s loop, after sub-planners and before run scouts.
   - Their sandbox, allowed tools and Codex sandbox are a scout's (`scout/spec.rs::headless_spec_on:197`), with `submit_doc` / `submit_findings` in place of `submit_scout_report`, and `get_doc` added for reviewers.
10. **Routes.**
    - `[orchestrator.routes.brainstorm]` is a new 9.5 route-list table; `config/orchestrator/routes.rs:16` gains `brainstorm`, and `RouteListsFrozen` grows to 9. Its picks are the first two entries on different runtimes, else the first two entries.
    - **Without a list:** the strongest installed model of each installed runtime (`roster::strongest_of(runtime)`).
    - **With one runtime:** its strongest model twice, with lenses `A` and `B`.
    - **Labels:**
      - two runtimes: the runtime names, `claude` and `codex`;
      - one runtime: `A` and `B`.
    - **The document reviewer's route** is `validate_patterns::peer_route:87(roster, orchestrator_route, installed)`, else the orchestrator's own route (`same_runtime = true`).
11. **The input pack** is built off-engine, in `run/design/pack.rs::pack`, which reads the scout reports. It holds:
    - the goal;
    - the answers;
    - each scout report's summary and findings;
    - the repo profile;
    - for a chained goal, the previous run's approved spec path and its Goal and Requirements sections, under `related earlier work`.

    It is capped at 48 KiB. Truncation is marked `[cut: <n> bytes]`.

    The lens lines, exact:
    - A: `Your angle: the smallest change that fully meets the goal.`
    - B: `Your angle: the most robust, long-lived design.`
12. **Documents are files; `run.json` holds their metadata.**
    - The engine never writes files. A submitted document is checked in the engine (pure), then the engine emits `Effect::WriteDoc { path, text }`, and `driver/design_io.rs` writes it with a temp file, fsync and rename.
    - `DesignState.versions: Vec<DocVersion { kind, n, author, reason, bytes, sha256, at }>` is the index.
    - `DesignState.requirements: Vec<Requirement { id, text }>` holds the **approved** spec's requirements only, plus `goal_section: String` (≤ 8 KiB). Workers and reviewers need these, and no file read happens under the engine.
    - **Paths:** `<data>/runs/<id>/design/` with `brainstorm/draft-<label>.md`, `brainstorm-v<n>.md`, `spec-v<n>.md`, `plan-v<n>.md`, `findings-<kind>-v<n>.json` and `versions.json`. The driver mirrors `versions` into `versions.json`.
13. **The merged report's appendix is attached by the engine.** It is `## Appendix: the drafts`, followed by each draft under `### <label>`, appended to the written file and never sent to the orchestrator.

### Spec and review (DF §4)

14. **Requirement parsing** (`design/requirements.rs::parse`):
    - Within the `## Requirements` section, lines matching `^R(\d+)\b` start a requirement. Its text runs to the next such line or heading, trimmed and capped at 2 KiB each.
    - Numbering must be `R1..Rn` without gaps, or the spec is refused: `requirements must be numbered R1 to R<n> without gaps; found <list>`.
    - An amendment (`amend: true`) must continue from the approved spec's last number. Changed requirements keep their number and carry `(changed in round <k>)`.
15. **The review protocol.**
    - **The orchestrator's submits.**
      - `submit_doc { kind: "spec", text, ready: false }` checks the template, writes the version as an internal draft (not a gate version), and dispatches the document reviewer.
      - The reviewer's `submit_findings` stores the findings and wakes the orchestrator: `spec review <k> is in: <n> findings (<b> blocking); answer each in your next submit_doc`.
      - `ready: true` needs `responses` covering every finding id of the latest review, else it is refused: `answer every finding of review <k>; missing: <ids>`.
    - **Limits.**
      - At most two reviews. After the second, `ready: false` is refused: `the spec has had its two reviews; submit with ready = true`.
      - A reviewer failure records `not reviewed: <reason>`, and `ready: true` is accepted without responses.
    - **Gate versions.** Only `ready: true` versions become gate versions (v1, v2, …).
    - **After the user asks for changes,** a revision is submitted `ready: true` directly. It is reviewed again only when the user's `Changes { review: true }`.
16. **Disputed findings** are those answered `kept: <reason>`. They are stored with the version and shown at the gate.

### Plan (DF §5.1)

17. **`PlanTask.covers: Vec<String>`**, with `#[serde(default, skip_serializing_if = "Vec::is_empty")]`, like `addresses` (`proto/run.rs:243`).
    - It is added to `mcp/src/tools_orch.rs::plan_task:223`'s closed schema and to `orch/tools_bounds.rs`, with at most 32 entries of at most 8 characters each.
    - Each entry must match `^R\d+$`, else it is refused at parse: `covers entries look like R4`.
18. **The submit-time checks** go in `engine/orch.rs::submit_refusal:564`. They are one call into the pure `design/coverage.rs::check(run) -> Option<String>`, applied only when `design_mode == Full`.
    - **Order:**
      1. coverage;
      2. dangling `covers`;
      3. brief shape.
    - The first failure is the refusal. The texts are under "Messages".
    - The user's `run edit --submit` passes the same checks.
    - Plan-gate approval re-checks coverage in `actions/rules.rs::approve:49`.
19. **Brief shape.** In a design run, every task's brief must contain the five headings, each on its own line and matched exactly:
    - `Files:`
    - `Tests first:`
    - `Steps:`
    - `Acceptance:`
    - `Verify:`

    A sub-planner's tasks are checked too.
20. **The plan review.**
    - The first passing `submit: true` of a design run does not open the gate. It dispatches the document reviewer on the rendered `plan.md` and replies `{ accepted: true, awaiting_review: true }`.
    - The reviewer's findings wake the orchestrator. The next `edit_plan { submit: true, responses }` must answer them all, and then it opens the gate.
    - The plan gets one review.
    - Edits between the two submits are allowed and re-checked.
21. **`plan.md`** is rendered by `design/plan_md.rs::render(run) -> String` for each gate version and for the commit:
    1. a title;
    2. per stage, then per task: `### <id> <title>`, then `Covers: R2, R5`, size, route, test mode and the brief;
    3. `## Coverage`, a table of requirement → tasks.
22. **Large path.**
    - Each sub-planner's first turn includes the approved spec's Goal and Interfaces sections and the requirements that its epic's interface tasks cite in `covers`.
    - If the orchestrator wrote no interface tasks for an epic, the sub-planner gets all the requirements.
    - Coverage is checked over the whole graph.

### The documents commit (DF §5.3)

23. **A new `OpKind::CommitDesignDocs { files: Vec<(String, String)>, message }`**, executed by `driver/design_commit.rs`.
    - **What it does:** through `GitQueue::write`, it builds a tree with the files added on top of `run_head`'s tree (`hash-object -w`, `mktree` via the existing `git/merge.rs::commit_tree:100` helpers), then makes a `commit-tree` whose parent is `run_head`, then moves the run branch with `refs_tx::cas`.
    - **Its reply** is `CommitDesignDocs { Ok(new_head) | Failed(message) }`.
    - **When it runs:** it is emitted on plan-gate approval. Then:
      - `stages::create_pass:212` and every `PrepareWorktree` wait while `design.commit_due`;
      - `run_head` advances on `Ok`, so local mode, pr Single and pr Multi all get it.
    - **On failure,** the run is set to `Halted` with exactly `design flow: could not commit the spec and plan: <message>`. `run resume` retries the commit.
    - **When it is skipped:** with `docs_dir = ""`, the op is not emitted.
24. **Paths and slug.**
    - `<docs_dir>/specs/<YYYY-MM-DD>-<slug>.md` and `<docs_dir>/plans/<YYYY-MM-DD>-<slug>.md`. The brainstorm goes to `<docs_dir>/brainstorms/…` only when `commit_brainstorm` is set.
    - **The slug** comes from the spec's `# ` title. It is lowercase ASCII alphanumerics and `-`, runs collapsed, at most 48 characters. If empty, it is the run id.
    - **The date** is the run's start date (UTC).
    - **The message:** `docs: spec and plan for <goal head>`, where `<goal head>` is the 60-character goal head.
    - **Round k:** the spec file gets `## Round <k> amendment` plus the amendment text appended, and the round's plan is written as `…-round<k>.md`. In pr mode this commit goes on the round's first new stage (DF §8.1), not the run's bottom stage.

### Contracts (exact)

The orchestrator contract gains rules **47–52** in `orch/contract_design.rs::design_rules!`, concatenated after `round_rules!`. They are included only in a design run's first prompt and handoff.

```
47. This run uses the design flow: brainstorming, then specifying, then planning. Each ends at a gate only the user opens; read verdicts with run_status, never assume one.
48. In brainstorming, ask the user at most {max_questions} short questions in your window, one at a time; when they answer or say skip, call start_brainstorm with their answers.
49. When both brainstorm drafts are in, read them with get_doc and submit one merged report with submit_doc kind "brainstorm": where they agree, where they disagree (each side, then your judgment), the approaches tagged [<label>] or [both], one recommendation naming a listed approach, and questions for the user. Never paste a draft wholesale.
50. In specifying, write the spec in the template you were given; every requirement is a line "R<n> …" with its acceptance check. Submit with ready false for review; answer every finding ("fixed" or "kept: <reason>") in the submit with ready true.
51. In planning, every requirement must be covered by a task's covers, and every brief has the headings Files:, Tests first:, Steps:, Acceptance:, Verify:. Answer the plan review's findings in edit_plan's responses when you submit again.
52. When the user asks for changes, revise and submit the next version; the user's note is in run_status. Never approve, and never call a gate approved.
```

**Other contracts** live in `scout/design_spec.rs` and are each under 1 KiB:
- **Brainstormer:** read-only; submit one draft with `submit_doc` kind `brainstorm_draft`, in the six-section template, under 12 KiB; cite `file:line` for constraints; never read another draft (it cannot).
- **Document reviewer:** read the document with `get_doc`; submit `submit_findings` once. Severity `blocking` is reserved for placeholders, contradictions, untestable requirements, scope beyond the approved approach, dropped brainstorm decisions, a requirement without an acceptance check, or a plan task that does not deliver its `covers`.

## Review focus

The five failure modes most likely to bite a user that no single task's tests fully exercise. Each one's test is added to the owning task.

1. **A gate the user cannot leave.** For example, `revising` stays set because the orchestrator's window died mid-revision. Test in M9.6.7: a lost window while revising goes through the 9.3 handoff, the fresh session gets the note, and `x` always works.
2. **Requirement drift between the approved spec and the plan.** The plan refers to requirements from an earlier, unapproved version. Coverage is checked only against `DesignState.requirements`, which is set at spec approval. Test in M9.6.11: a plan citing an R from spec v1 after v2 renumbered is refused.
3. **The documents commit racing a task branch.** A task branches from the old `run_head`. Test in M9.6.12: no `PrepareWorktree` or stage creation happens before the commit's reply, including across a restart between approval and the reply.
4. **Hostile document text.** A brainstormer or the orchestrator submits control characters, a 10 MB text, or markdown that breaks the TUI. Texts are cleaned by `safe_text::multi_line` before storage and capped before the check. Tests in M9.6.4 and M9.6.17 render a hostile document.
5. **Cost runaway.** Rethink or changes loops with no bound. Each rethink relaunches two brainstormers. A run's design phases are capped at 3 rethinks and 6 versions per gate. Past that, the action is refused: `the <kind> has had its <n> versions; approve, go back or reject`. Test in M9.6.7. **This is a brief ruling (BD-2) beyond DF.** The user is told with the brief.

## Risks and gotchas

- **Variant order.** The new `RunState`, `AgentRole`, `RunRequest`, `ActionKind` and `HistoryLine` variants must be appended, never inserted, because MessagePack carries variant indices.
- **Size caps.** `engine/orch.rs` and `run/contract.rs` sit at 599 and 575 lines, so new logic goes in `design*` files.
- **The appendix.** It is attached by the engine's write effect. The orchestrator never sees it, so its token cost is zero.
- **Codex orchestrators and questions.** A Codex orchestrator gets its first prompt on argv (9.5 C1), and questions work the same in its window.
- **`get_doc` replies run off-engine.** A slow disk never holds the engine lock.
- **Older binaries.** One that loads a 9.6 run.json would drop `design` (serde) and lose the gate. That is the same class as 9.3's followup on an older binary rewriting `run.json`, and it is recorded, not fixed.
