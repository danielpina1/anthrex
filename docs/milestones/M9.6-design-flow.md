## Goal

A planned goal goes:
1. Brainstorm: two independent drafts, merged into one report, approved by the user.
2. Spec: written, reviewed by the peer model, approved by the user.
3. Plan: a task graph whose coverage of the spec's requirements the engine checks, reviewed, approved by the user.
4. Then today's execution.

During execution, workers and reviewers work against their requirements, and REPORT.md shows each requirement's outcome.

### Mode and phases (DF §1, §2)

3. **`Run.design_mode: DesignMode { Full, Off }`** is frozen at start. Default `Off` for older runs.
   - **On by default:**
     - triage path `Plan` or `Large`;
     - every kind in `TriageInfo.kinds` is `Code` or `Docs`;
     - not from a plan file;
     - not a promotion.
   - *(M9.6.1 fact.)* A continued goal (`start_goal`, `continue_from`) is never triaged: it is built with `triage: None` (`driver/chain_goal.rs:233`) on the plan path (`orch/mod.rs::make_planned:477`).    - **Overrides:** `--design` / the dialog row first, then `[orchestrator.design] default`.
   - A request for `Full` on a goal the table puts off is refused with the exact text: `the design flow runs only for planned code or docs goals; this goal is <fast|research|review|a plan file>`.
4. **Two states appended to `RunState`:** `Brainstorming` (label `brainstorming`) and `Specifying` (label `specifying`), **appended after `Planning`** (wire order).
   - A design run enters `Brainstorming` where 9.5 enters `Planning` (`orch/mod.rs::make_planned:477`). It enters `Planning` when the spec gate is approved.
   - Every exhaustive match that lists `Planning` gains the two new states with `Planning`'s arm. The code map in "Starting point" lists the sites.
   - **Scouts run in `Brainstorming`**, exactly as they run in `Planning` today: the state gate in `planners::dispatch` (`engine/planners.rs:63-66`) admits `Planning`, `AwaitingApproval` and `Running` today and gains `Brainstorming` and `Specifying` by the rule above (`Planning`'s arm). The orchestrator's tool-call state gate (`engine/orch.rs::tool:205`, the match at `:223`) admits the two new states as it admits `Planning`.
5. **One gate record for all three gates:** `DesignState.gate: Option<DocGate>`.
   - `RunState::AwaitingApproval` stays the one waiting state. In a design run, the plan gate is `DocGate { kind: Plan, .. }`.
   - A non-design run keeps `gate = None`, and 9.5's plan gate is unchanged.
   - Names avoid 9.5's `GateKind` (a task's bounce gate, `proto/src/run.rs:441`): the types are `DocGate`, `DocKind`, `DocFinding`, `DocSeverity` and `DocAuthor`.
6. **`--yes` never skips a design gate.** `goal_rounds_end::skips_gate:25` returns false when `run.design_mode == Full`. The start logs once, exactly: `design flow: --yes does not skip the brainstorm, spec or plan gates`. *(M9.6.1 fact: `skips_gate` also decides whether a submitted hold is approved at once (`engine/gate_holds.rs::submitted:403`), so in a design run `--yes` approves no hold either. 7. **Gate actions are one request**, `RunRequest::DocGate { run, kind, action }`, with:

   ```
   DocGateAction {
     Approve,
     Changes { note, review },
     Edit { text },
     Rethink { note },
     Back { note },
     Reject,
   }
   ```

   - **Validity:**
     - Rethink is valid only at `Brainstorm`.
     - Back is valid only at `Spec` and `Plan`.
     - An action at a gate the run is not at is refused: `run <id> is not waiting at the <kind> gate`.
     - An action while `revising` is set (other than Reject) is refused: `the orchestrator is revising <kind> v<n>; wait for it`.
   - **Plan-gate compatibility:** `RunRequest::Approve` and `RunRequest::Reject` at the plan gate of a design run are accepted as `DocGate { kind: Plan, Approve | Reject }`.

### Spec and review (DF §4)

14. **Requirement parsing** (`design/requirements.rs::parse`):
    - Within the `## Requirements` section, lines matching `^R(\d+)\b` start a requirement. Its text runs to the next such line or heading, trimmed and capped at 2 KiB each.
    - Numbering must be `R1..Rn` without gaps, or the spec is refused: `requirements must be numbered R1 to R<n> without gaps; found <list>`.
    - An amendment (`amend: true`) must continue from the approved spec's last number. Changed requirements keep their number and carry `(changed in round <k>)`.
15. **The review protocol.**
    - **The orchestrator's submits.**
      - `submit_doc { kind: "spec", text, ready: false }` checks the template, writes the version as an internal draft (not a gate version), and dispatches the document reviewer.
      - The reviewer's `submit_findings` stores the findings and wakes the orchestrator: `spec review <k> is in: <n> findings (<b> blocking); answer each in your next submit_doc`.
      - `ready: true` needs `responses` covering every finding id of the latest review, else it is refused: `answer every finding of review <k>; missing: <ids>`.
    - **Limits.**
      - At most two reviews. After the second, `ready: false` is refused: `the spec has had its two reviews; submit with ready = true`.
      - A reviewer failure records `not reviewed: <reason>`, and `ready: true` is accepted without responses.
    - **Gate versions.** Only `ready: true` versions become gate versions (v1, v2, …).
    - **After the user asks for changes,** a revision is submitted `ready: true` directly. It is reviewed again only when the user's `Changes { review: true }`.
16. **Disputed findings** are those answered `kept: <reason>`. They are stored with the version and shown at the gate.

## Review focus

The five failure modes most likely to bite a user that no single task's tests fully exercise. Each one's test is added to the owning task.

1. **A gate the user cannot leave.** For example, `revising` stays set because the orchestrator's window died mid-revision. Test in M9.6.7: a lost window while revising goes through the 9.3 handoff, the fresh session gets the note, and `x` always works. *(M9.6.1: the relaunch path is `engine/orch_window.rs::launch:20` with the stored `OrchestratorRecord.first_prompt`; see task M9.6.14's Files.)*
2. **Requirement drift between the approved spec and the plan.** The plan refers to requirements from an earlier, unapproved version. Coverage is checked only against `DesignState.requirements`, which is set at spec approval. Test in M9.6.11: a plan citing an R from spec v1 after v2 renumbered is refused.
3. **The documents commit racing a task branch.** A task branches from the old `run_head`. Test in M9.6.12: no `PrepareWorktree` or stage creation happens before the commit's reply, including across a restart between approval and the reply. *(M9.6.1: today the plan gate's pre-warm prepares worktrees from `base_sha` before any approval, and dispatch re-points them once `run_head` has moved (decision 23's facts). Whether a design run keeps the pre-warm is open item O-2 in the notes.)*
4. **Hostile document text.** A brainstormer or the orchestrator submits control characters, a 10 MB text, or markdown that breaks the TUI. Texts are cleaned by `safe_text::multi_line` before storage and capped before the check (`proto::safe_text::multi_line(text: &str) -> String`, `proto/src/safe_text.rs:70`: keeps `\n`, turns `\r\n`/`\r` into `\n` and every other control character, a tab included, into a space, drops hidden format characters; the TUI re-exports it from `tui/src/safe_text.rs:11`). Tests in M9.6.4 and M9.6.17 render a hostile document.
5. **Cost runaway.** Rethink or changes loops with no bound. Each rethink relaunches two brainstormers. A run's design phases are capped at 3 rethinks and 6 versions per gate. Past that, the action is refused: `the <kind> has had its <n> versions; approve, go back or reject`. Test in M9.6.7. **This is a brief ruling (BD-2) beyond DF.** The user is told with the brief.

## Risks and gotchas

- **Variant order.** The new `RunState`, `AgentRole`, `RunRequest`, `ActionKind` and `HistoryLine` variants must be appended, never inserted, because MessagePack carries variant indices.
- **Size caps.** `engine/orch.rs` and `run/contract.rs` sit at 599 and 575 lines, so new logic goes in `design*` files.
- **The appendix.** It is attached by the engine's write effect. The orchestrator never sees it, so its token cost is zero.
- **Codex orchestrators and questions.** A Codex orchestrator gets its first prompt on argv (9.5 C1), and questions work the same in its window.
- **`get_doc` replies run off-engine.** A slow disk never holds the engine lock.
- **Older binaries.** One that loads a 9.6 run.json would drop `design` (serde) and lose the gate. That is the same class as 9.3's followup on an older binary rewriting `run.json`, and it is recorded, not fixed.
